# Decisions

- D1 (owner): Preserve the currently working Spotify/Apple experience; centralize management, do not replace product behavior.
- D2 (owner): One common application-facing music library and two production adapters; especially queue/playback state must have clear common ownership. UI and non-React tools share the same manager.
- D3 (owner): Strict implementer and independent reviewer roles; specifications-based tests for each adapter, shared behavior tests and regression coverage required.
- D4 (repo): No Neuve/Kanban exists; this workstream folder is the tracker. Generic skills' Neuve/Kanban workflows are inapplicable, not missing approval gates. No cert/env contents, useState, non-bun package managers, or force pushes.
- D5 (lead scope): No new product features/capabilities, auth rewrite or deployment in this refactor. Library state and queue semantics may be reorganized; provider-native restrictions remain explicit. Retain fixture adapter for test/demo usage.
- D6 (lead verification): Baseline is production commit 36f0b97. Live account availability is not assumed; mock contracts must match canonical types/specs and live limitations must be recorded. Routine module naming and extraction boundaries are logged in architecture.md, then incorporated into Ready scope before coding.

- D7 (lead accepted architecture): Add @webpod/music-management with Jotai vanilla and providers dependencies only; expose a stable managed facade and domain queue/playback selectors, migrate UI/tools/control paths and neutral progressive browsing. Native SDK readiness/relinking/window mechanics stay adapter-specific. Spotify submitted-context application policy moves common. Preserve explicit supersession instead of naive FIFO waiting for playback confirmation. See Ready scope dispatch packet.

- D8 (lead, protocol evidence): SDK events do not universally carry application command IDs. Reject attributable stale command completions, queue reads, polls and adapter transactions using generations/revisions. Do not invent an event command ID or permanently suppress legitimate external playback merely because it resembles an earlier track. While a selection is pending, mismatched observations must not confirm it; once authoritative external playback differs, invalidate known submitted context honestly. Tests must distinguish deterministic stale-work rejection from inherently ambiguous untagged events. Pause fencing must not become a permanent veto on external playback. This clarifies criterion 2 within actual adapter evidence rather than claiming impossible event attribution.

- D9 (owner follow-up): Login failures must not transition into the player. SDK authorization alone is insufficient: navigation requires the selected runtime to finish its initial required library load successfully. Use the same readiness decision for explicit login, restored sessions and callback/direct-entry paths, including a recheck after exit animation. Stale attempts cannot borrow a newer provider/session's success. Preserve valid empty libraries, partial background pagination and optional sticker independence. Show actionable error/retry on the login surface. This explicitly scopes a narrow login-transition correction; it does not authorize changing server credentials or expanding OAuth permissions.

- D10 (owner): Auth must have a proper namespace separate from playback/queue, with Apple Music and Spotify specific flows and session management. This supersedes D5's auth-refactor exclusion within that boundary. Accept architecture addendum with native auth behavior behind a common lifecycle interface, no duplicate session truth, explicit playback retirement, and preserved product behavior.
- D11 (lead evidence): Public MusicKit consumes JSON and throws an error whose data is the consumed Response; tests must match this rather than invented data.errors. Live core-library40300 plus successful catalog establishes rejected personalized authorization. Scope recovery to documented core personalized-library403/native ACCESS_DENIED, exclude generic catalog/licensing/500, fence and deduplicate reset by authorization generation. Do not inject headers or alter server credentials.
