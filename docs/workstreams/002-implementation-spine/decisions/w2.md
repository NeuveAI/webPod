## 2. Deviations from a 001 number

### 2.1 `Shift+Arrow` is one viewport of rows, not a flat 7

001 §4.4 says `Shift+Arrow` = **7 rows (one page)**. 001 §4.6 says
`Shift+↓`/`Shift+↑` = **one page (8/6/4 rows by density)**, and 001 §4.3 says
`⏭`/`⏮` page by "one full viewport of rows (8 / 6 / 4 by density)". Two of the
three agree with each other and with the words "one page"; the third does not.

**Chosen:** the density-based page — 8 / 6 / 4. `⏭`, `⏮` and `Shift+Arrow` all
land on exactly one viewport, which is what makes the gesture legible ("the
list moved by one screenful"), and it keeps the keyboard and the transport
buttons doing the same thing.

The likely origin of the 7 is visible one column to the left in the same §4.4
table: 7 is the top *acceleration* multiplier. A flat 7 would also be wrong at
`airy` density, where it skips 3 rows past the end of the viewport.

`⚠ DEVIATES` from 001 §4.4. Reversible in one line: `pageRows` is a parameter
of the key input, not a constant.

### 2.2 Announcement urgency for `source: 'system'`

001 §11.8 gives the human sentence and the agent sentence. It gives no system
sentence. `describeMovement` renders a system movement in the **human** form —
`Row 4 of 18. …` — rather than inventing a third voice.

Reason: a system-caused move (a queue advancing, a screen restoring) is
something that happened *to* the device, not something an actor did to it.
Naming an actor would invite the listener to look for one, which is the exact
failure class 001 §8.2.4 documents. Logged because it is a gap I filled.

### 2.3 `agent:unknown` when no origin is supplied

001 §8.4 specifies `actor: 'agent:<agentOrigin>'`. The platform supplies no
agent identifier — a page learns an agent exists only when a tool executes —
so the origin can only be whatever the tool layer knows about its caller.
`DetentInput` carries an optional `agentOrigin`, and when it is absent the tag
reads `agent:unknown`.

This asserts nothing about presence. It is a label on a movement that already
happened, and "unknown" is the honest value. Nothing in this stage emits it.

## 3. Choices made under uncertainty

### 3.1 `jotai` pinned to exactly `2.20.3`

The rest of the repo uses caret ranges. This one is exact because 2.20.3 is the
version of the clone I grounded against, and because of the hazard in §4.1.
`bun.lock` gained one entry; nothing else in it moved.

### 3.2 Device state is derived, not assigned

`deviceStateAtom` is a read-only derived atom over four primitives
(`holdEngagedAtom`, `connectionAtom`, `agentThrottledAtom`, `agentActiveAtom`)
rather than a writable atom the reducers set.

Deriving it makes "exactly one state at a time" structural: there is no
combination of the primitives that yields two, and no writer that can leave a
stale one behind. 001 §8.2.2 requires the property but does not say how.

**Precedence, which 001 does not specify:** `HOLD_ENGAGED` > `DISCONNECTED` >
`AGENT_THROTTLED` > `AGENT_ACTIVE` > `USER_ACTIVE`. Hold is the human's
physical override and outranks everything; disconnection outranks the agent
states because it changes what is *possible* rather than who acted last;
throttling is documented as a sub-mode of agent activity, so it sits directly
above it.

### 3.3 `AGENT_THROTTLED` is a plain boolean with no deadline

001 §7.4 is the rate limiter, and it is not in this stage. `agentThrottledAtom`
is a boolean the limiter will write. It deliberately carries **no** countdown:
a second copy of a deadline is a second thing to keep true, and the exact
seconds go to the caller in the refusal payload rather than to the screen.

This is also why there is no timer anywhere near it. The only `setTimeout` in
the package is the announcement debounce, and it lives in `startAnnouncer`.

### 3.4 The highlight and the scroll window live *inside* the frame

001 requires that `Menu` restores the exact prior highlight. Storing the
highlight and the window on the `ScreenFrame` makes that free: popping is a
stack pop and the position comes back because it never left. The alternative —
one global highlight plus a map of saved positions — has to choose a key, and
drifts the first time a screen is reachable by two routes.

### 3.5 `Center` is declined by the machine

`pressActionAtom` fully handles `menu`, `next` and `previous`, and returns
`handled: false` for `center` without changing anything.

This is a boundary, not a gap. The machine owns the stack; the layer holding
the data owns what a row points at. A row on the main menu descends into a
known screen — `MENU_ROOT`, `findMenuNode` and `menuFrame` are exported for
exactly that — but a row on an album is a track, and descending means playing
it. Guessing here would put half the navigation model in the wrong module.

### 3.6 The pure machine returns a bump *direction*; the store stamps the event

`ScreenTransition.bump` is `BumpDirection | null`, not a `BumpEvent`. The
machine has no clock and no counter, and `BumpEvent.seq` must be monotonic —
two identical bumps in a row have to be two distinct values or the second one
is swallowed as a no-change and the human concludes the button is broken. The
store is the only place that can guarantee that, so it stamps `seq` and `at`.

### 3.7 The announcer is pure; the one timer is in the store binding

`noteMovement` records a due time and `flushAnnouncer` asks whether it has
arrived. Neither schedules anything. `startAnnouncer` owns the single
`setTimeout`, re-aims it on every movement, and cancels it on teardown.

This is what lets the 30-detent gate be proved with plain numbers and no fake
timers, which makes the test evidence about the code rather than about a mock.
There is also a real-timer test of the driver itself, so the wiring is not
taken on trust.

### 3.8 Invented values, both flagged

- **`KEY_REPEAT_WINDOW_MS = 250`.** 001 §4.4 says a keypress announces
  immediately, "debounced only during auto-repeat", without saying how
  auto-repeat is recognised. Two key detents closer together than 250ms are
  treated as a repeat. 250ms sits below every OS auto-repeat *delay*
  (typically 250–500ms) and far above every repeat *interval* (30–50ms), so it
  separates the two cleanly. It is a constant in `contract.ts`, not a literal.
- **Empty-screen sentence: `"<title>. No items."`** 001 §11.8 has no row for
  an empty list. `Row 0 of 0` is a sentence about the implementation.

### 3.9 The window slides by the minimum, and lists clamp rather than wrap

Neither is specified. Minimum-slide rather than recentring, because recentring
makes a one-row movement look like the whole list jumped and forces the eye to
re-find the highlight after every press. Clamping rather than wrapping, because
a list that wrapped would make counted navigation ambiguous about where it
landed — "down four" from row 2 of 3 would be unanswerable — and 001 §4.3
already specifies hard stops with an elastic bump for the rating wheel.

### 3.10 A fifth commit for gate vocabulary

The plan named four commits. A fifth, `refactor(state): keep the universal gate
greps clean`, follows them: it renames the announcer's `pending` field to
`settling` and rewords comments so that 001 §15.0's U8 and U9 greps come back
clean. It is comment-and-identifier only, no behaviour, isolated per the
scope's rule that mechanical changes never ride along with behaviour.

## 4. Hazards handed forward

### 4.1 ⚠ W3: depend on `jotai@2.20.3` exactly, or do not depend on it at all

`packages/state` is React-free by construction — no `react` dependency, and a
test asserts React is not even resolvable from the package. The atoms are
created by *this* package's copy of Jotai.

Bun 1.4's isolated linker gives each workspace its own `node_modules`. Two
workspaces asking for the same exact version share one physical path in the
store and therefore one module instance, so atom identity holds. **Two
different versions would be two Jotai instances**, and `<Provider store={…}>`
from one would not be found by `useAtomValue` from the other. The symptom is
not a type error; it is a component reading a default value forever.

So: `apps/web` and `packages/panel` should pin `jotai@2.20.3` on the nose. If
that turns out to be fragile in practice, the fix is for this package to export
a bridge hook — the dispatch permits exactly one — and for nobody else to
import `jotai` at all. I did not build it pre-emptively, because keeping this
package React-free is the stronger proof of the property the slice exists for.

### 4.2 U8 has three standing hits in `contract.ts`, pre-cleared

`grep -rniE '\b(allow|deny|…|permission|granted|…)\b' packages/state/src/`
returns three lines, all inside TSDoc, all of them prose stating that the
permission model does **not** exist and why the states that assumed it were
deleted (§8.2.4, and the note that `B10` "granted standing permission for
actions that were never gated").

U8 is a manually-cleared gate. These are cleared: they are not agent-flow copy,
they are not strings any human will read in the product, and deleting them
would delete the warning that prevents the bug. Nothing else in the package
matches. `useState` returns 0; the agent-presence grep returns 0 repo-wide.

### 4.3 What is *not* built, and is not missing

No tool is registered and no `document.modelContext` call exists — the seam is
`DetentSource` and the `direct` input path, both unused by anything in this
stage. No haptics or clicker audio: `DetentOutcome` reports counts, and the
30/sec clicker limiter belongs with the sound layer when it lands. No React
bridge hook. No `pod-read-screen`; `readScreen` is the projection it will use.

## 5. Incident — `55b34dd` contains six files belonging to the Apple spike lane

Full write-up in `diary/w2.md`. Summary: I staged with an explicit pathspec and
then ran a plain `git commit -m …`, which writes the entire index rather than
the paths I staged, so files another lane had staged in the shared index in the
meantime rode along. No content was lost or altered; the defect is that six of
that lane's files carry my commit message. That lane has not committed since
and still holds newer uncommitted edits to two of them.

Checked and clear: no credential material was committed. The one key-shaped
match in `scripts/spikes/mint-apple-dev-token.ts` is a regex stripping a PEM
header. Nothing under `cert/` was read or committed; `cert/` is gitignored with
no tracked files.

**Recommendation: leave it.** Three of my commits and several other lanes'
commits sit on top of `55b34dd`, and four lanes are actively committing to this
branch. A rebase to fix six commit-message attributions costs more than the
defect, and every lane with local work would have to recover.

**Prevention, already applied:** my last three commits use
`git commit --only -- <pathspecs>`, which builds its tree from HEAD plus the
named paths and therefore cannot absorb a neighbour's staging. This is worth
promoting to a standing rule: `git add <pathspec>` scopes the add, not the
commit, so `add` + plain `commit` is unsafe in a shared tree even without
`--amend`.

### If the owner decides to rewrite anyway — owner-only, do not run as an agent

Not to be run by any agent, and not while other lanes hold uncommitted work.
Have every lane commit or stash first.

```sh
# 1. Safety net.
git branch backup/pre-55b34dd-rewrite

# 2. Interactive rebase from the commit before the bad one.
git rebase -i 55b34dd^

#    Mark 55b34dd as `edit`. When the rebase stops there:
git reset HEAD^                                   # unstage everything
git add packages/state/src packages/state/package.json
git commit -m "feat(state): screen state machine"
git add docs/workstreams/002-implementation-spine/decisions/s1.md \
        docs/workstreams/002-implementation-spine/decisions/s2.md \
        docs/workstreams/002-implementation-spine/evidence/apple-capability-spike.md \
        docs/workstreams/002-implementation-spine/evidence/apple-empirical-probe.md \
        scripts/spikes/mint-apple-dev-token.ts \
        scripts/spikes/probe-apple.ts
git commit -m "docs(spike): apple capability findings and probe scripts"
git rebase --continue

# 3. Verify nothing changed in the final tree.
git diff backup/pre-55b34dd-rewrite HEAD          # must be empty
```

Step 3 is the one that matters: if that diff is not empty, the rewrite dropped
something and `backup/pre-55b34dd-rewrite` is the way back.

## 6. Review response — what changed, and the principle underneath it

The review returned REQUEST_CHANGES with four Major and five Minor findings and
found one shape under all four Majors, which the lead promoted as **D-049**:
*enforce the invariants you own at the boundary you own.*

The observation is exact and I had no answer to it. I derived `silenced` and
`actor` inside `detent()` so that no call site could forget them, wrote the
argument for doing so in three places — and then handed three other invariants
I equally owned to a consumer that does not exist yet, with no gate and no
documentation. Nothing separated the two groups. The clock domain, the page
size and the effective density were all delegated to W3 in the same breath as
an essay about why delegation is how rules get lost.

The correction is uniform: each of those three is now decided inside this
package, at the seam W3 actually calls.

### Major 1 — two clock domains, and U13 inverting in a browser

`startAnnouncer` defaulted `now` to `Date.now()` and compared it against
`timestampMs + 350`, where `timestampMs` was whatever the caller passed. The
idiomatic browser value for that field is `event.timeStamp`, which is on the
`performance.now()` origin: ~1e4 against ~1.8e12. Every due time therefore
looked long past, and the reviewer measured a 30-detent flick producing **30
announcements**. U13 did not merely fail, it inverted — and it failed in the
loud direction, which is the one this whole module exists to prevent.

My tests missed it because the driver test wrote `const start = Date.now()` and
fed `start + i`. I knew a shared clock was required and encoded that knowledge
in a fixture. A fixture is not a design.

**Fixed structurally rather than documentarily.** There is one clock per
device, in `clockAtom`; `detentActionAtom` stamps movements with it and
`startAnnouncer` reads it. No caller-supplied timestamp reaches any comparison,
so a mismatch is unconstructible. `AnnouncerDriverOptions.now` is **removed** —
a second injection point for a clock is how the two halves came apart in the
first place; a test supplies one clock to `createDeviceStore` and it governs
everything. `DetentInput.timestampMs` is now documented as intra-gesture only.

⚑ Jotai footgun found on the way and worth passing on: `atom(someFunction)`
does not create an atom holding that function. Jotai reads a function argument
as a derived atom's read callback, so the atom computes a number and every
`get(clockAtom)()` throws. A function has to be boxed in an object to live in
an atom.

### Major 2 — constants asserted only through themselves (D-050)

The reviewer planted `VISIBLE_ROWS = {7,7,7}` — the exact flat 7 ruled against
in D-042 — and got 93 pass, 0 fail, `tsc` exit 0. Same for
`ANNOUNCE_DEBOUNCE_MS: 350 → 50`. Both survived because every assertion
computed both sides from the symbol, so the test moved with the bug.

What makes this sharp rather than a generic complaint is that my own arc
geometry *is* gated — falsifying it turns seven tests red, because those tests
feed literal degrees and assert literal counts. One package, both patterns, and
only one of them a test.

**Fixed:** `gates.test.ts` asserts every ruling-shaped constant against a
literal transcribed from the source, with the § cited. Falsifying any of them
now goes red — see `evidence/w2-review-fixes-go-red.txt`.

**And the compounding half:** `detentActionAtom` forwarded the caller's
`pageRows` untouched while holding the atom that knew the right number, so a
flat-7 page on an 8-row viewport went straight through the public API.
`pageRows` is **deleted from `DetentInput`**. The page size is now a parameter
of the reducer call that the store supplies from `visibleRowCountAtom`. A
caller cannot pass one, which is stronger than a caller being told not to.

### Major 3 — `densityAtom` was inert, and its TSDoc said otherwise

The atom claimed to be the effective density that Dynamic Type forces;
`visibleRowCountAtom` read `frame.density` instead and nothing rewrote frames.
Setting it to `airy` over a `compact` screen left the viewport at 8 rows —
silently, no error, no test. A TSDoc that contradicts the code is worse than no
TSDoc, and this one contradicted it 80 lines apart.

**Fixed by wiring, not by deleting the claim.** Three inputs, one derived
answer:

- `ScreenFrame.density` is now documented as the screen's **preference**
  (001 §3.1), which is what it always actually was.
- `densityOverrideAtom` is the human's Display & Feel setting, `null` by
  default — and `null` is *not* the same as `medium`, which is why the default
  changed. Conflating them would flatten the §3.1 per-screen choices.
- `dynamicTypeScaleAtom` plus `AIRY_FORCING_TYPE_SCALE = 1.3` implements U11's
  forced `airy`.
- `effectiveDensityAtom` reconciles them, in that precedence, and is what
  `visibleRowCountAtom`, `screenSnapshotAtom` and paging all read.

`setDensityActionAtom` and `setDynamicTypeScaleActionAtom` additionally
re-clamp every frame's scroll window across the whole stack, because a
`compact` window of 8 rows starting at row 40 is out of range once `airy` cuts
the viewport to 4 — including on screens the human will only see again on the
way back down.

### Major 4 — the inertial coast was absent *and undisclosed*

001 §4.4's Release row: *"remaining angular velocity decays at 0.94/frame,
firing a detent every 15° until |ω| < 60°/s. Every coasted detent still
clicks."* `endGesture` returned the idle accumulator, discarding
`speedDegPerSec` — the one quantity a coast needs — so no consumer could have
implemented it either.

The finding is the non-disclosure, and it is fair: my diary has a section
listing three omissions with reasons and this fourth was not in it, with no
principle dividing them. An omission that is disclosed is a plan.

**I implemented it rather than deferring it,** because §4.4 is the table the
dispatch names as the engineering contract and because deferring would have
left "every coasted detent still clicks" as an unowned invariant — exactly the
D-049 shape I was being corrected for. `endGesture` now keeps the momentum and
`coastStep` decays it; the physics is pure, so a whole coast replays in a test
at any frame rate. What is *not* here, and is disclosed in the diary: the
per-frame driver. `requestAnimationFrame` belongs to whoever owns a frame loop,
exactly as the announcement timer belongs to the store — but the rules the
frames obey live here.

### Minor 1 — `multiplier` was documented "always 1 on the key path" and was 8

True and measured: `Shift` on a compact screen makes it 8. It is the field a
consumer would read to assert "the keyboard did not accelerate", so being
wrong there costs something.

Fixed by correcting the doc **and** adding `DetentOutcome.accelerated`, which
is the question `multiplier` could not answer: did the device move further than
it was told? `false` for every keyboard event including `Shift+Arrow`, `false`
on scroll always, `false` for programmatic movement, `true` only when an arc
was fast enough to earn extra rows.

### Minor 2 — the silence predicate existed twice

`source !== 'human'` appeared verbatim in `detent.ts` and `store.ts`, while the
diary claimed no call site re-derived it. Both copies were correct and presses
genuinely cannot route through `detent()`, so it was not a §15.2 violation —
but it was two places to change a rule whose entire design argument is that
there is one.

Fixed with `silence.ts`: `isSilenced`, `actorFor` and `feedbackFor`, called by
the reducer, the coast and the press handler. A test greps the sources and
fails if the predicate is written out more than once.

### Minor 3 — an early timer stranded the announcement permanently

`flushAnnouncer` returns the **same state object** when the due time has not
arrived. Setting an atom to the value it already holds is a no-op to jotai, so
the driver's subscription did not fire — and the timer callback had already
cleared its own handle. Nothing armed, nothing would re-arm, summary dropped.

The reviewer hedged reachability honestly (400 probes of Bun's `setTimeout`,
zero early fires) and then noted that the natural fix for Major 1 —
`performance.now()` — puts it on a clock browsers deliberately coarsen, where
reading back a value below the due time is ordinary. Fixing Major 1 without
this would have *created* the bug. One line: re-arm when a flush says nothing.

### Minor 4 — `popScreen([])` bumped as though it were the root

`stack.length <= 1` covered both the root and the empty stack, so `Menu` on a
device with no screens published an elastic "this is the top" for a stack with
no top. Split into two cases, and the `screenStackAtom` TSDoc corrected — it
claimed "never empty" while the atom's own default was `[]`.

### Minor 5 / D-051 — one device per document

The reviewer downgraded their own endorsement here and was right to. My proof —
React unresolvable, 18 React-free tests — shows the package does not *need*
React. The dispatch's requirement is that tool callbacks reach **the same state
the UI renders**, and nothing stopped W3 handing its `Provider` a fresh
`createDeviceStore()`: two stores, both valid, both React-free, every test
green, tools moving a screen nobody is looking at.

Under D-049 the enforcement is mine. `deviceStore` is the singleton;
`createDeviceStore` is documented as test-only and **throws** outside a test
runner; and a test greps `packages/` and `apps/` and fails on any call to it
from a non-test file. The runtime guard catches the second device; the static
gate catches the line that would write it, in review, in packages this one
cannot import.

### Minor 6 — `menuRows` promised a filtering seam it did not have

The comment said `Radio` is absent rather than greyed when stations are
unsupported, "see `menuRows`, which takes the visible children as given" —
and `menuRows(node)` mapped `node.children` unconditionally. A guarantee that
was a description of an intention.

`menuRows` and `menuFrame` now take a `MenuVisibility` predicate, defaulting to
admitting everything, which is the honest answer before a provider has been
asked. Filtered rows are re-indexed, because a row's `index` is what a
navigation tool is told to move to and an index counting invisible rows would
send it elsewhere. The comment now says plainly that a default-seeded device
shows both rows and must be re-seeded once the truth is known.

## 8. Re-review response — four new Majors, four commits

All four round-1 Majors verified fixed; four new ones, three of which are the

### R1 — the D-051 guard was off by one, and its test was green for the wrong reason

`deviceStore` is built through a private path that did not increment
`devicesBuilt`, so in a real document the counter was **0** when a consumer
called the factory: `1 > 1` is false and the first call succeeded. D-051's own
motivating case, `<Provider store={createDeviceStore()}>`, is exactly one call.
The guard missed the only thing it existed to stop.

And the test that certified it was green because **25 earlier calls in the same
file** had already pushed the counter past the threshold — right assertion,
reason that does not support it. That is D-058.

**Fixed both halves, and D-054 says prefer the shape change, so both were
done:**

- The guard now throws whenever `!underTest()`, on the first call. The counter
  is deleted; a count was never the right question.
- `createDeviceStore` is **no longer reachable from `@webpod/state`**. It lives
  at `@webpod/state/testing`, and `index.ts` enumerates `./store`'s exports
  rather than re-exporting it wholesale — so the import a consumer would
  actually write does not resolve, and a name added to `store.ts` does not
  become public by accident.

**The test now runs in a fresh subprocess** with a fresh module registry and no
test runner, so the call under test is genuinely the first one and nothing this
file did can make it pass. A companion test asserts the singleton still builds
in that same fresh process — otherwise the first two would pass if importing
the package threw.

The static gate is also fixed for the narrowness the reviewer flagged: it used
to exclude three of this package's files *wholesale*, so a real call added
inside `store.ts` or `menu.ts` would have been invisible to the gate meant to
catch it. It now filters by what the line **is** — a comment, the definition,
the one sanctioned re-export — rather than by which file it is in.

### R2 — two clocks rebuilt in `BumpEvent.at`

The announcer fix was complete and the reviewer could not break it. The same
defect was sitting one field over: `BumpEvent.at` has three writers, and two of
them stamped whatever the caller passed. Measured, on one device: `500000` from
the wheel and `1700000000000` from `Menu` and the transport — one atom, one
published field, two time bases, chosen by which control the human touched.

This is the finding I am least comfortable with, because I had already been

`clockAtom`; the `at` parameters are deleted from `moveHighlightActionAtom` and
`popScreenActionAtom`; and `PressInput.timestampMs` is **removed from the

caller's clock, and leaving the field would leave somewhere a second time base

### R3 — the density write the TSDoc blessed left the highlight off-screen

> *"Writing `densityOverrideAtom` directly works too, and is deliberately left
> possible…"*

It did not work. Highlight on row 60, window at rows 53–56: the highlighted row
not among the rows rendered. That is the exact *"row you can never scroll to"*
that `visibleRowCountAtom`'s own comment names, reachable through the route my

The sentence got the mechanism right — the derived readers *do* move together —
and the conclusion wrong, because the scroll windows are **stored per frame**,
not derived, and re-clamping them is a stack edit no derived read can perform.

**Fixed by making the route unconstructible, per D-054.** The writable
primitives moved to `internal.ts`, which `index.ts` does not re-export and the
package's `exports` map does not expose. `contract.ts` publishes read-only
`Atom` views, so a bare `store.set(densityOverrideAtom, …)` does not typecheck.
The only route is the action atoms, which re-clamp every frame on the stack.

The gate for it proves both halves: two `@ts-expect-error` directives establish
that the write is a type error (an unused directive is itself an error, so the
file compiling is the proof), and the test then performs the suppressed write
and demonstrates the broken window it produces — so a later reader can see why
the route is banned rather than being asked to trust it.

**Type-escape invariant, recorded as the scope requires:** those two
`@ts-expect-error` directives in `gates.test.ts` are the only ones in the
package. Each suppresses a deliberate misuse whose *presence as an error* is
the thing being asserted. They are in a test, never in shipped source, and
`tsc` fails if either stops being necessary.

### R4 — the coast was 4× refresh-rate dependent (D-060)

Full evidence in `evidence/w2-coast-frame-rate.txt`. 30fps travelled 491.9° and
120fps 123.0° on one identical flick, with the frame *count* to rest identical
at 46 — decay counting frames while travel counted seconds.

**⚑ This was a transcription gap, not an under-specified constant, and the gap
is mine.** design-system §9.4 states the normalisation outright — *"`ω *=
0.940` at 60fps (normalised to `ω *= 0.940^(dt/16.67ms)`)"* — and I had not
read §9.4. I worked the coast from pm-spec §4.4's Release row and treated it as
the whole specification of a motion behaviour, when the motion system has its
own section in the other primary. The lead's D-060 ruling and the design
system's own text agree.

Implemented as three changes, each independently gated:

1. `0.94 ** (elapsedSeconds × 60)` — §9.4's normalisation, with 60fps still
   seeing exactly 0.94.
2. Distance is the closed-form integral of that decay across the frame. A
   rectangle under an exponential curve is frame-rate dependent by
   construction — the same bug in a smaller costume.
3. Each coasted detent is scored at the speed the wheel was doing when it
   fired, computed exactly rather than interpolated: `dv/ds = −λ` gives
   `v = v₀ − λ·s`, speed as a function of *distance*, which no frame rate can
   change. Plus the coast stops when the speed reaches the floor rather than at
   whichever frame boundary comes next, so a long frame cannot overshoot.

Result is **exact**, not within a tolerance: 16 detents, 74 rows, 240° at every
rate from 15fps to 240Hz, and under a jittering variable-rate interval. The
frame count still scales with the rate, which is what distinguishes this from
an invariance that holds because nothing moves.

The smoothing window is deliberately not used during a coast: it exists because
a *hand's* speed jitters, and a coast's velocity decays monotonically so the
multiplier can only step down. Using it would have put the display back into
the row count one level below the distance.

## 11. D-063 — design-system §9.4 governs wheel motion

The conflicts raised in §9 are ruled. §9.4, *The wheel inertia and detent
model*, beats pm-spec §4.4's summary table wherever they disagree: acceleration
physics is §9.4's subject and §4.4's aside, the same shape as §12.0's geometry
re-derivation beating §7.3's stale column.

Five behaviours changed, in five commits. Every value is gated against a
literal with the § cited, and every one has been planted wrong — twice where a
plausible wrong value exists, once reverted to the pm-spec figure it supersedes
and once nudged the way a value drifts. `evidence/w2-d063-go-red.txt` has all
nine plants; 37 test failures across them, none staying green.

| # | Behaviour | Was (pm-spec §4.4) | Now (design-system §9.4) |
|---|---|---|---|
| 1 | Fast-scroll curve | ×1/×3/×7 at 240/540 °/s | **×1/×4/×12 at 720/1080 °/s** |
| 2 | Precondition | *(none)* | **list must exceed 40 rows** |
| 3 | Velocity ceiling | *(none)* | **1440 °/s** |
| 4 | Detent hysteresis | *(none)* | **±1.8° on a reversal** |
| 5 | Coast floor | 60 °/s | **21 °/s** = 0.35 °/frame |

### What §4.4 keeps, and why the ruling does not touch it

The four input paths converging on one `detent({delta, source})`, per-path
measurement, detent sizes, dead zones, the mouse ×1.4 threshold scaling,
per-path FX, release-versus-keyup, and the 3-detent smoothing window. §9.4 is
silent on input path, and per-path adjustment is §4.4's own subject.

Above all: **arrow keys never accelerate, one keydown is one row, always.**
§9.4 does not cover the keyboard at all. A gate asserts explicitly that the new
hysteresis does not reach the key path — an arc-geometry rule must not touch a
path that has no geometry, and that is the invariant this slice guards hardest.

### Notes on each

**1. The curve.** The gate names the rejected values (`not.toBe(3)`,
`not.toBe(7)`, `not.toBe(240)`, `not.toBe(540)`) so a later reader can see the
assertion settles a conflict rather than restating a number, and a behavioural
sweep asserts that no speed from 100 to 50,000 °/s can produce a ×3 or ×7.

**2. The 40-row precondition** needed a shape change, not just a constant: the
reducer is pure and did not know how long the list was. `detent()` and
`coastStep()` now take an optional `ScreenMetrics { totalRows }`, and
`detentActionAtom` supplies it from the current frame — the same pattern as
`viewportRows`, and for the same D-049 reason. **Omitting it disables
fast-scroll**, which is the safe direction to be wrong in.

The gate sweeps a 39-row list at ten speeds up to 50,000 °/s, asserts 40 is
still too short (§9.4 says *exceeds* 40), and drives the real main menu through
the store to confirm an eight-row menu cannot fast-scroll however hard it is
flicked. That last one is the case the precondition exists for: without it a
brisk flick on a twelve-row menu jumps four rows per detent through a list four
rows long.

**3. The velocity ceiling** is applied to ω rather than to the detent rate, so
it bounds the acceleration tier and the coast length together. A gate drives
360,000 °/s — a thousand revolutions a second, which a trackpad fling or a
synthetic event can genuinely produce — and asserts the recorded speed is 1440,
then asserts the resulting coast is bounded rather than proportional to the
input.

**4. Hysteresis is charged on reversals only**, which is where §9.4's chatter
case lives: a thumb parked near a threshold crosses it on tremor alone, and
without hysteresis each crossing fires a detent, so the highlight oscillates
and the clicker machine-guns while the hand is not moving. Charging it on every
detent instead would tax ordinary scrolling — planted, and it turns four tests
red including two that have nothing to do with reversal.

This also required fixing direction bookkeeping: the accumulator's `direction`
now comes from the *drain* rather than from the event's net detents, because an
event that both advances and reverses must leave the direction of the **last**
detent or the next reversal is charged the wrong way.

**5. The coast floor** is corroborated twice inside the design system: §9.4's
`0.35 °/frame` and §14.1's frame-budget table terminating the wheel's render
loop at *"inertia ‖ω‖ < 0.35°/frame"*. Two design-system sections against one
line of pm-spec. The consequence is a materially longer glide — a 1000 °/s
release now runs 63 frames rather than 46 — and it means the state layer and
whatever owns the render loop stop on the same condition rather than one idling
frames after the other has given up. Gated behaviourally as well as by
constant, since a constant assertion alone would not have caught a floor that
was right in the table and wrong in the loop.

**D-060's frame-rate invariance survives all five changes**, re-measured: 17
detents, 32 rows, 255° at every rate from 15fps to 240Hz.

### Still deferred, and deliberately not implemented

The haptic conflict — §4.4 *"suppressed above 12/sec"* against §9.4 *"only
every 3rd vibrates"* — is not ruled. §4.4 defers to §4.9, §4.9 is the haptics
specialist, and haptics are out of scope in this stage. **Neither behaviour is
implemented.** `feedbackFor` still reports a suppression count and the layer
that owns the actuator will decide; the seam is left and the conflict is
recorded here rather than settled by whichever section I happened to read.

### What I should have done in the first place

Nothing in D-063 was undiscoverable. §9.4 is a numbered section titled *The
wheel inertia and detent model* in a primary source the scope names, and I
built a wheel inertia and detent model without reading it — from a table in the
other primary whose subject is input paths. The lead's D-061(b) correction
applies to me at least as much: I did not merely miss a line, I missed the
section whose title is the thing I was building.

The general form, for whoever reads this next: **when a spec has a section
named after the thing you are building, read that section, even when another
document already told you a number.** A summary table containing a value is not
evidence that the value is the specification.
