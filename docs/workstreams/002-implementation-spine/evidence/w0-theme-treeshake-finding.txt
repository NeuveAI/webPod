=== FINDING: Tailwind v4 tree-shakes @theme, so the §12.1 FX block does not reach the browser ===

§12.1 declares the FX geometry inside '@theme' with the comment:
    /* -- FX geometry (consumed by JS/SVG, exported here as one source of truth) -- */

Tailwind v4 only emits an @theme variable when a utility that references it is
actually used. Nothing generates a utility from --fx-*, --dur-*, --ease-* or
--radius-panel-*, so they are dropped from the stylesheet. A later lane calling
getComputedStyle(root).getPropertyValue('--fx-wheel-r') gets an empty string, and
so does any hand-written CSS rule that says var(--dur-tick).

Both colourways DO ship - the runtime layer is plain CSS and is never shaken:
$ grep -a -o 'data-mode=dark\]' <built css> | head -1
data-mode=dark]

$ grep -c 'prefers-reduced-transparency' <built css>
1

--- What was NOT done about it ---
globals.css is left byte-identical to §12.1. The one-word fix is '@theme static',
which forces every variable to be emitted, but that is a change to a file the
packet says to transcribe exactly, so it is raised rather than taken.
Mitigation already in place: packages/tokens exports the same numbers as typed TS
(geometry.ts, fx.ts), which the packet also required, and that is the reliable
source for any JS/SVG consumer. The gap only bites CSS-side var() references.
