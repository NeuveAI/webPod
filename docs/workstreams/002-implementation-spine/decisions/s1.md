## D1 — Labelling a *negative* finding `VERIFIED` when Apple never states the negative

**The tension.** The dispatch defined `VERIFIED-docs` as "Apple's published docs state it plainly." Apple nowhere writes "you cannot remove a track from a library playlist." What Apple publishes is a *complete endpoint index* in which no such endpoint appears.

**Original decision.** `VERIFIED-docs`, with the evidentiary shape written out at each affected row.

**Reasoning (still stands).** The Apple Music API reference is an exhaustive enumeration of a closed surface, not prose. Downgrading to `LIKELY` would imply the doc set might be incomplete, making every negative in the capability table permanently unresolvable and inviting a future reader to hope a hidden `DELETE` exists — which is worse than the overreach, and is inflation in the other direction.

> ### CORRECTION (revision 2) — the vocabulary was underspecified, and the reviewer was right that the tripwire was disarmed
>
> The reviewer found that this label conflicted with H-2, which required these rows to stay `UNVERIFIED-docs-only`, and that as written it disarmed 001 §15.3 failure mode 14: a future reader grepping `UNVERIFIED` on rows 10/11/18/21/30 would find nothing.
>
> **D-022 ruled, and I have applied it.** Labels now carry **two axes** — evidential strength (`VERIFIED` / `LIKELY` / `UNVERIFIED`) and provenance (`docs` / `live`). The five rows are now **`VERIFIED · docs`**: same evidence, honest provenance, tripwire re-armed. The operative rule is now stated in the deliverable itself: **`docs` provenance is never "settled"; only `live` closes a row.**
>
> **My reasoning above was not wrong — it was answering only the evidential-strength question and silently asserting an answer to the provenance question.** Two axes were needed and I collapsed them into one. The reviewer could not have resolved it either; two binding contracts genuinely disagreed and only the lead could rule.

> ### CORRECTION (revision 2) — two counting errors in the enumeration I offered as proof

> - **"it contains exactly three entries" → the topic group holds five.** Three *endpoints* plus `LibraryPlaylistCreationRequest` and `LibraryPlaylistTracksRequest`.

## D2 — Contradiction: Apple staff say removal IS supported (Jun 2022), the docs say no endpoint exists

**The two sources.**
- Apple staff, thread 707759, Jun 2022: *"Editing playlists does support removing tracks from a playlist."*
- Apple Music API reference: no removal endpoint.

**Decision.** Not a contradiction — a scope mismatch, resolved in favour of both. The reply is about **Swift MusicKit's `MusicLibrary.edit(_:…items:)`**, a different framework from the REST API, and the same reply says so: *"currently only available on Apple platforms."* Verified independently: availability iOS 16 / iPadOS 16 / tvOS 16 / visionOS 1 / watchOS 9, no web, no macOS.

**Why it does not rescue row 10 even in principle.** The follow-up adds a second lock: *"You cannot edit playlists created via Apple Music API."* Two independent blocks — wrong platform, wrong provenance.

**Recorded because** a future reader who finds thread 707759 before this document will think row 10 was answered wrongly. It was not. *(Independently confirmed in review.)*

## D3 — Undocumented `Queue.splice()` in Apple's shipped `musickit.js` v3

**The tension.** The published v3 reference documents `Queue` as seven properties and zero methods. Apple's shipped runtime contains `splice`, `append`, `updateItems`, `removeQueueItems`, `clearAfterCurrent`, `clear`, and a `remove` that fires `deprecationWarning("remove", …)`. Apple's code contradicts Apple's docs.

**Decision.** Row 18 headline stays **not supported**; the runtime methods are recorded as a separate `LIKELY · docs` sub-finding; `supports("queueRemove")` and `supports("queueReorder")` stay **`false`**.

**Reasoning.** Three independent reasons, any one sufficient:
1. §14.4 rule 1 — *"Never invent parity"* — an undocumented method is not a capability the provider offers.
2. Apple's own code deprecates `remove`, so even the undocumented path is being withdrawn.
3. There is no `reorder`/`move` method at all, so `queueReorder` would be emulation on top of an undocumented primitive — two layers of unsupported.

**Not taken, deliberately:** I did not propose a runtime feature-probe (`typeof queue.splice === "function"`) to flip `supports()` to `true`. Real option, real risk; it is a product decision about shipping on undocumented API. **Flagged to the lead, still open.**

## D4 — Row 20 held at `LIKELY` rather than upgraded

**Decision.** `LIKELY`, and `supports("stationSeedFromTrack") = false`.

**Reasoning.** The question is not "can I play a station associated with a song" — it is "is there an API for a station **seeded from** a specific track." Apple's total documentation is five words: *"The station associated with the song."* An "associated" station could be the artist's or a genre station; the identical relationship name `station` exists on `Artists`, which is a live reason to doubt. Upgrading would inflate an unstated semantic into a stated one — 001 §15.3 failure mode 14.

> ### CORRECTION (revision 2) — ⚠ my settling probe could not answer its own question
>
> **This is the most serious defect in revision 1, and it was found by the empirical-probe slice, not by me.**
>
> I specified: *three songs by three different artists*, with the failure condition *"if the same artist's songs all return one identical `ra.*` id, it is an artist station."*
>
> **The design and the decision rule are not the same experiment.** The fixture never places two songs by one artist side by side, so my own stated failure condition is **unobservable in it**. And the success condition is not diagnostic either: three songs by three *different* artists produce three different station ids under **both** hypotheses, because the artists differ too. Distinct ids across distinct artists is exactly what the artist-station hypothesis predicts.
>
> **Run as I specified it, three distinct ids would have flipped `supports("stationSeedFromTrack")` to `true` on a false positive** — the precise failure 001 §14.4 exists to prevent. Reading `attributes.name` for a "song-shaped" name is no rescue; it is a naming heuristic presuming Apple's copy convention.
>
> Sharpest detail: I correctly identified `Artists.station` as *the reason to doubt* — and then designed an experiment that never measured it. **Naming the confound and not controlling for it is worse than missing it**, because it looks rigorous.
>
> **The corrected design is the probe slice's** — three artists × two songs each (the within-artist comparison, which is decisive), plus `GET /v1/catalog/us/artists/{artistId}/station` as the control. I have not touched that slice's files. The deliverable now opens row 20 with a warning block so **a reader who finds my version first does not run it**.
>
> **The verdict is unchanged and was never at risk:** `LIKELY · docs`, unproven, `supports()` `false`. Only the experiment was mis-specified.

## D5 — 001 §14.3 row 21 asserts a lyrics endpoint "exists"; I could not find it

**The tension.** §14.3 row 21 says *"`/v1/catalog/{sf}/songs/{id}/lyrics` — **UNVERIFIED**: exists, but third-party display entitlement and time-sync availability must be confirmed."* That framing treats existence as settled and only entitlement as open.

**Decision.** **Existence is not settled — it is documented as absent.** I corrected the premise rather than answering the narrower question 001 asked.

**Reasoning.** Answering only the entitlement question would carry an unverified premise forward as fact — precisely the failure mode the reviewer is told to hunt. §14.3 was authored without primary-source access (§14.0 says so), so the premise was always provisional.

**Where the URL comes from:** third-party private-API projects, named in the deliverable and capped at `LIKELY`.

**Sub-questions:** entitlement and time-sync stay `UNVERIFIED · docs`. For the entitlement I recorded that **no API call can settle it** — it is a licensing question. Saying "call this endpoint to find out" would have been a fake action item.

**Status: accepted.** Attacked four ways in review — 0 `lyric` hits across the Apple Music API index (608 nodes), 0 in the Feed index, 0 across all 19 MusicKit-web modules, 1 in Swift MusicKit (`var hasLyrics: Bool`). **001 should be amended.**

**Not taken:** dropping `ratingStars` from the union. That is the clean fix and it is a **001 amendment — the lead's to record, not mine to make.**
