## 2. Deviations from §14.2

001 is read-only, so a deviation is only visible if it is written down here.
Anyone diffing this package against §14.2 will find exactly these.

### 2.1 `LocalKey` is a branded string, not a bare alias — **⚠ deviates**

§14.2 writes `type LocalKey = string` with the comment *"UUIDv7 minted by us.
Our structures hold ONLY this."* The packet requires that this be verified **by
type, not by convention**. A bare alias cannot do it: `catalogId` is a `string`
too, so the compiler accepts a provider id in every key position and the comment
is the only thing standing between §14.5 and a structure that dies at a provider
switch.

`LocalKey` is therefore `string & { readonly [brand]: true }`. It is still a
string at runtime and still assignable **to** `string`; it is not assignable
**from** one. `mintLocalKey()` produces one and `asLocalKey()` narrows at an
edge, throwing on anything that is not a canonical UUIDv7.

Proven by three `@ts-expect-error` assertions in `identity.test.ts` — a bare
string, a `catalogId` and a `libraryId` are each rejected. Those are the
*strongest* available form of this test rather than a suppression: if the brand
ever stops rejecting them, `tsc` fails on the directive that is no longer
needed. **Invariant, as the type gate requires: `LocalKey` is assignable to
`string` and `string` is not assignable to `LocalKey`.**

### 2.2 `ProviderId` gains `"fixture"` — **⚠ deviates**

§14.2 has `"apple" | "spotify"`. D-006 makes the fixture provider what the
product actually renders from, so it is a real provider with real `TrackRef`s,
and `TrackRef.provider` has to say truthfully where a ref came from. The
alternative was to let it claim `"apple"`, which puts a lie in the single field
§14.5 exists to keep honest, and would corrupt any provenance record built on it.

Widening costs nothing at call sites precisely because §14.4 forbids branching
on this value. That is the rule paying for itself on its first test.

### 2.3 Every reference type carries a `kind` discriminant

§14.2's own `libraryAdd(ref: TrackRef | AlbumRef | PlaylistRef)` cannot be
narrowed without one, and §14.2 defines neither `AlbumRef` nor `PlaylistRef`.
`kind` is added to `TrackRef` too, so the four are uniform. Additive; nothing
in §14.2's `TrackRef` was changed or removed.

### 2.4 `ratingStars` and `offline` are absent

Not my decisions — D-026 and D-019 respectively. Recorded here only so the
25-member union is not read as a transcription slip. Both are asserted by test.

## 3. Types invented to fill §14.2's gaps

§14.2 names ten types in its signatures and defines none of them. Every shape in
`domain.ts` is invented and is listed here so a reviewer can separate
transcription from invention without reading the spec side by side:

`Unsubscribe` · `Session` · `Cursor` · `Page<T>` · `LibraryKind` · `EntityKind` ·
`SearchQuery` · `SearchResults` · `PlayTarget` · `ShuffleMode` · `RepeatMode` ·
`PlaybackState` · `ProgressTick` · `LyricLine` · `Lyrics` · `QueueSnapshot` ·
`StationSeed` · `Rating`; plus `ArtistRef`, `GenreRef` and `ComposerRef` in
`identity.ts`, which `LibraryKind` needs in order to be total over §4.2's Music
menu.

Three of these carry a judgement worth stating:

- **`Session.canPlay` is separate from `Session.status`.** §14.3 rows 2 and 3
  make the paid tier a different axis from being signed in — a free Spotify
  account authorises fine and cannot play a note, and §11.5 has its own copy for
  that state. Collapsing them would make "signed in but silent" unrepresentable.
- **`ProgressTick.interpolated` is on the tick, not on the provider.** It is the
  honest channel §14.3 row 25 requires, and it is per-report because a Spotify
  session alternates between reported and interpolated positions.
- **`Page.total` is `number | null`.** §11.6 renders an empty slice as a count
  (`Playlists 0`), so an invented total would put a wrong number on a screen.
  `null` where the provider does not report one.

## 4. `artworkUrl` — two contract decisions

**`actualPx` is the largest width at which the returned URL is still sharp**, not
"the size you asked for, clamped". Requesting 1400 against Spotify's 640/300/64
returns 640 — §14.3 row 26's own example. Requesting 100 against the same array
returns **300**, not 64: handing back a 64 for a 100px slot is an upscale, which
is the same prohibition read from the other side. §14.2's own comment says the
provider returns *"the nearest >= requested, or the largest available, and
reports what it actually gave you"*, and that is what is implemented.

**A `template` artwork that also carries `sizes` treats the largest as a native
ceiling.** Apple substitutes arbitrary sizes so there is normally nothing to
clamp against, but an adapter that knows the source's real dimensions can record
them in `sizes` and get upscale protection with no extra API.

**The URL is root-relative**, so same-origin is a property of its construction
rather than of configuration. D-014: cross-origin artwork will not paint into a
canvas under read-back-allowed rendering, and under T1 the panel *is* painted
into a canvas, so a raw provider URL renders as a hole rather than as an error
anyone would see. `ARTWORK_PROXY_PATH` is exported so `packages/server-core`
binds its route to this constant and the two cannot drift.

**A malformed `Artwork` throws.** `artwork` is optional on every ref, so "there
is no art" is already expressible; a present-but-empty `Artwork` came from a
parse that should have rejected it and is an adapter defect, not a data state.

## 5. The fixture provider

- **Default matrix is all-25-true, and that is honest** — the fixture holds its
  own data and can genuinely do everything. §14.4 forbids inventing parity, not
  having it.
- **`supports` is overridable per instance**, and `APPLE_SUPPORTS` /
  `SPOTIFY_SUPPORTS` are exported, so W3 can render the launch provider's parity
  gaps — and prove a missing capability produces **no control** — without a
  network, an account, or a second provider.
- **A method whose capability is off throws `CapabilityUnsupportedError`.** That
  should be unreachable from the UI under §14.4, so it is a tripwire for a
  missing `supports()` check upstream rather than an error path to handle.
- **No timers.** Position moves only when the host calls `tick()`. A fixture
  running its own interval would make every progress test race the clock; a test
  asserts that 25ms of real time moves nothing.
- **Keys are minted per catalogue, never hardcoded.** Two catalogues share titles
  and share no keys, which is the correct model — two libraries holding the same
  record are not the same library — and it stops a test from asserting on a key
  literal, which would be testing the fixture rather than the code.
- **Fixture artwork points at `/artwork-source/…`, which nothing serves yet.**
  The proxy is `server-core`'s and lands later, so the panel renders its
  placeholder. That is the honest day-one state and is recorded so it is not
  chased as a bug.

## 6. The Apple and Spotify stubs

Both providers ship with **real matrices and no behaviour**. The stub distinguishes
two failures rather than collapsing them: an unsupported capability throws
`CapabilityUnsupportedError` carrying the same copy a human would be shown, and a
supported-but-unwritten method throws `NotImplementedError`. "This service cannot
do that" and "we have not built it yet" have different fixes, and a stub that
merged them would make the capability matrix — the only finished part — look
untested.

**The stub's methods declare no parameters.** A function of fewer parameters is
assignable to one of more, so `MusicProvider` is satisfied. The alternative was
twenty `_`-prefixed arguments plus either twenty lint suppressions or a change to
the root `eslint.config.js`, which this lane does not own. An absent parameter
also reads correctly: this body genuinely does not look at its arguments.

**Rows 10, 11, 18 and 7 are labelled `LIKELY · docs`, never `VERIFIED`** (D-029),
in the comment beside each value. The value does not move either way; the label
is the whole point, because someone will later reopen `pod-edit-playlist` and say
"we verified this."

**The lyrics comment records the reason, not just the value** (D-015 retraction):
the endpoint exists and returns `400`/`40012` to our developer token, gated
rather than absent, entitlement unresolved, and `40012` must not be routed
around. A `false` with a wrong reason is a trap with a delay on it — that exact
trap was already sprung once in this project, on this row.

## 7. The include hazard (D-029), contained in `apple/relationships.ts`

Apple **silently ignores** an invalid `include` / `views` / `extend` and answers
`200`. A typo'd `include=station` therefore succeeds with a payload merely
missing the relationship, which reads as *"this song has no station"* — a
plausible data condition, and a lie.

- `readSongRelationship(resource, name)` **takes no HTTP status.** There is no
  parameter through which a `200` could be supplied and quietly relied upon;
  a test asserts the arity is 2, so the enforcement is structural rather than a
  comment. Key absent from `relationships` → `RelationshipNotHonouredError`.
  Key present with `data: []` → `[]`, a legitimate empty state. **The two are
  never collapsed.**
- `assertKnownSongRelationship(name)` refuses an unregistered name **before the
  request is built**, because the response cannot tell you the name was wrong.
- `SONG_RELATIONSHIPS` labels each name `live-exists` / `live-gated` /
  `live-absent` / `docs-only`, per D-022's two axes. Its docblock states
  explicitly that it is a **typo guard and not an existence oracle** — building a
  closure claim on a name list is precisely what D-029 and D-035 falsified, and
  the same registry could invite the same mistake a second time.
- `classifyRelationshipResponse(status, code)` implements S2's four-state oracle
  and returns **`inconclusive`** for anything outside it, so an unrecognised
  response is never read as an absence.

## 8. Two questions for the lead

**(a) §14.2 has no way to set shuffle or repeat.** §14.3 row 27 puts both at
full parity on Apple and Spotify, §11.1's B02 lists `Shuffle: Off / Songs /
Albums` and `Repeat: Off / One / All` as settings a user changes — and the
interface supplies no method that changes either. `PlaybackState` carries both
as read-only fields and the fixture holds them at their defaults with a `const`
and a comment. Adding `setShuffle` / `setRepeat` would be redesigning §14.2, so
it is logged rather than done. **It will block B02 and the transport half of
S13.**

**(b) The branded `LocalKey` and the widened `ProviderId` are §14.2 deviations
made under an explicit instruction to verify identity by type.** Both are
defensible and both are visible; if the lead would rather the transcription stay
literal, §2.1 and §2.2 are each a one-line revert and the identity guarantee goes
with them.
