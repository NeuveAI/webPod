## 1. RULING WANTED — Tailwind v4 tree-shakes `@theme`, so §12.1's FX block never reaches the browser

**What 001 says.** §12.1 puts the FX geometry, the durations, the easings, the panel
dimensions and the non-`--color` radii inside `@theme`, with the comment
`/* -- FX geometry (consumed by JS/SVG, exported here as one source of truth) -- */`.

**What the clone does.** Tailwind v4 emits an `@theme` variable only when some generated
utility references it. Measured on the real build of `apps/web`, `--fx-wheel-r`,
`--fx-halo-blur`, `--fx-agent-blur`, `--panel-w`, `--dur-tick`, `--ease-agent`,
`--radius-device` and the rest are all absent from the stylesheet, while `--font-panel`
and `--text-panel-row` survive only because `index.tsx` uses the matching classes. Full
measurement in `evidence/w0-theme-treeshake-finding.txt`.

**Consequence.** `getComputedStyle(root).getPropertyValue('--fx-wheel-r')` returns an
empty string, and a hand-written rule saying `var(--dur-tick)` resolves to nothing. The
"one source of truth" the comment promises is not there at runtime.

**What I did.** Nothing to `globals.css` — it is byte-identical to §12.1, proven by
`diff` and `shasum` in `evidence/w0-tokens-test.txt`. The fix is one word,
`@theme` → `@theme static`, but that edits a file the packet says to transcribe exactly,
so I am raising it instead of taking it.

**Mitigation already in place.** `packages/tokens` exports the same numbers as typed TS
(`geometry.ts`, `fx.ts`), which the packet required anyway. That is the reliable source
for any JS or SVG consumer. The gap only bites CSS-side `var()` references, which is a
W3/W4 concern rather than a W0 one.

**Both colourways are unaffected** — the `:root` / `[data-mode="dark"]` layer is plain
CSS, is never shaken, and both blocks ship. Verified.

## 2. §7.3 and §12.0 disagree on the label-band constant. §12.0 wins, per §12.0.

§7.3 ends with a correction stating the printed label band is `innerR + ringW × 0.57`.
§12.0 states it is `innerR + ringW × 0.493`, and calls ×0.57 out by name as wrong
("which would give r 83.6").

§12.0 is the canvas-reconciled reconciliation table and says canvas wins, so it is what I
transcribed. The arithmetic corroborates it: with `innerR` = `SELECT_R` 42 and
`ringW` = 115 − 42 = 73, `42 + 73 × 0.493 = 77.99`, landing inside the measured r77–79
band, while ×0.57 gives 83.6, outside it. There is a test asserting both halves of this
so the superseded constant cannot come back unnoticed.

No value was changed. Recording it because a reader of §7.3 alone would transcribe the
wrong number.

## 3. §7.3's desktop geometry column is stale and is deliberately NOT exported

§12.0 re-derives only the mobile column at `wheelR` 115. §7.3's desktop column
(`wheelR` 125, Select r46, label band r91–93, body 390×653) is derived from the superseded
0.642 ratio; carrying the 0.697 correction across would give `wheelR` ≈ 136, and nothing
in 001 sanctions that number.

`packages/tokens/src/geometry.ts` therefore exports the mobile/built figures only. I did
not invent a desktop column. **Flagging for whoever owns the desktop layout** — it needs a
re-derivation in 001, not a guess here.

## 4. "wheelR/bodyW === 0.697" is wheel *diameter* over body width

The packet's acceptance criterion is written `wheelR/bodyW === 0.697`, but 115/330 = 0.348.
§12.0 states the ratio as "Wheel/body = 230/330 = **0.697**" — i.e. diameter over width.

Implemented as the diameter form, exported as `WHEEL_TO_BODY_RATIO` and derived from
`WHEEL_R` and `BODY_W` rather than written down, so it cannot drift from the radii. The
test asserts `0.697` to 3dp and goes red at the pre-R5 `wheelR` 106 (giving exactly the
0.642 §7.3 records as the drift). Reading it as radius-over-width would make the stated
target unsatisfiable, so this is a reading of the packet rather than a deviation.

## 5. Assertions rounded to the precision §12.0 actually quotes

§12.0's tiling table gives step arcs as 8.10px and 8.25px and the trail radius as
0.660 × `wheelR`. Computed exactly they are 8.098, 8.253 and 0.6609. The tests round to
the 2dp the table quotes rather than asserting invented precision. The 0.218× agent-blur
ratio and the 0.697 wheel ratio are asserted at the 3dp §12.0 gives them at.

## 7. Shared config choices, made freely but worth stating

- **`exactOptionalPropertyTypes` is off**; everything else strict is on, including
  `noUncheckedIndexedAccess`, `noImplicitReturns` and `noUnusedLocals`. It interacts badly
  with React prop spreading and would tax four lanes for little safety. Reversible in one
  line if the lead wants it.
- **Geometry constants are annotated `: number`** rather than left as literal types.
  Literal types on a dimension make every arithmetic comparison against them a type error
  and buy nothing. `HALO` and `TRAIL` keep `readonly` members via explicit types.
- **`useState` is banned by lint**, not only by review: `no-restricted-syntax` catches the
  call, the `React.useState` member form and the import. Verified to go red on a planted
  violation.
- **`bun run gates` exits 1** with "not implemented" until W5a lands. A placeholder that
  exited 0 would report "no findings" for checks that never ran.

- `/global-patterns` and `/bun-http` both say to read `~/code/agent-context/<file>.md`.

it because it silently affects every agent on this repo, not just this slice.

## 9. Things I did NOT do, on purpose

- **No history rewrite, no push, no force of any kind.** `evidence/w0-history-rewrite-plan.md`
  contains the prepared commands and stops there. `git-filter-repo` is not even installed
  on this machine. The plan also flags a delete/create collision on `AGENTS.md` at the tip
  commit that would silently produce a wrong tree, with the check that catches it.
- **No `useState` anywhere**, including in the example route.
- **`packages/*/src/index.ts` are stubs with no dependencies.** A package's own
  `package.json` is not shared config, so each lane adds its own deps without collision.
- **`.gitignore` was edited by the lead mid-slice** to cover `cert/`, `*.p8`, `*.pem`,
  `*.key`, `*.p12` after a MusicKit signing key appeared untracked-but-unignored. I kept
  that block, verified `git check-ignore` matches it and that `git status` no longer shows
  it, and did not read, copy or log any key material. **That `.gitignore` change is still
  uncommitted** — see the diary; it needs a commit that is not one of my three.
- **Nothing under `docs/workstreams/002-implementation-spine/` is in any of my commits.**
  All three were staged with explicit pathspecs.
