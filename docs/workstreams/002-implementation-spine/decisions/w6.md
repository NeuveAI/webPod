## W6-D1 · No React state, and therefore no Jotai atom either, in W6.0

**The tension.** Repo law bans `useState` and directs state to a Jotai store. The
route needs a browser-only value, and `apps/web` server-renders.

**Decision.** `ssr: false` on the route, and the report resolved once at module
scope by `getCapabilities()`. Zero React state of any kind, and no store.

**Why not a Jotai atom.** Jotai is not installed anywhere in the repo yet, and W2
is building `packages/state` concurrently. Adding the dependency to satisfy a
value that never changes after boot would put a lockfile edit and a second store
into a lane that was told to keep its state local. The law's stated purpose —
"tool callbacks live outside React and must read and write the same state the UI
renders" — is not engaged by a diagnostic that no tool callback touches.

**Where the tier atom actually belongs.** W6.1. `preview-validation.md` says the
tier is "a single value in the Jotai store, set once at boot and on context
events". W6.0 deliberately does not create it, because creating it here would
mean creating it twice.

**How to falsify me:** if the reviewer holds that `getCapabilities()`'s module-level
cache is itself banned state, the fix is one atom in `packages/composite` once
Jotai lands, and nothing else changes.

## W6-D2 · `_probe.capabilities.tsx` serves at `/capabilities`, not `/_probe/capabilities`

**The dispatch specifies the filename** `apps/web/src/routes/_probe.capabilities.tsx`
and the guardrail "routes prefixed `_probe.`". It never states the URL. The URL it
implies — by analogy with `preview-validation.md`'s `/_spike/device` — is not what
that filename produces.

**The fact.** In TanStack Router's file conventions, a `_` prefix marks a *pathless
layout route*, which is excluded from URL matching
(`~/code/agentic-context/tanstack/router/docs/router/routing/file-naming-conventions.md`).
So `_probe.capabilities.tsx` generates route id `/_probe/capabilities` and full
path **`/capabilities`**. Verified in the generated tree, not assumed:

```
apps/web/src/routeTree.gen.ts
  id:   '/_probe/capabilities'
  path: '/capabilities'
```

**Decision.** Keep the mandated filename; report the discrepancy rather than
silently renaming a file the dispatch names explicitly.

**The one-line fix if the lead wants the namespaced URL:** rename to
`[_]probe.capabilities.tsx`. Square brackets escape a character that would
otherwise have routing meaning, giving a literal `/_probe/capabilities`. This
also matters for W4, whose route is documented as `/_spike/device` and which will
hit the same thing.

**Cost of leaving it:** `/capabilities` occupies a clean top-level path in the
product's namespace. It is dev-gated (see W6-D3), so nothing ships, but it is not
free.

## W6-D4 · I reported, and did not patch, that `updateElementGeometry` does not exist

**What I found.** Chrome 151 with the flag on exposes `layoutSubtree`, `onpaint`,
`captureElementImage`, `getElementTransform`, `requestPaint`, `texElementImage2D`,
`drawElementImage` and `ElementImage` — and nothing else. `updateElementGeometry`,
`clearElementGeometry`, `getCanvasTransform`, `onelementgeometryupdate`,
`texElementSubImage2D`, `PaintEvent` and `ElementGeometryUpdateEvent` are all
absent. Established by exhaustive `Object.getOwnPropertyNames()` enumeration over
the four relevant prototypes plus `window`, not by probing my candidate list — the
list could have been wrong, the enumeration cannot be.

**Why it matters.** The W6 packet's "property that must not be lost" section makes
`updateElementGeometry({ canvasTransform })` mandatory and calls it "the difference
between the thesis holding and not". It is not implementable today.

**What I did.** Added a `geometryApi` field to the report that names which
generation shipped, surfaced it as a third headline card, and raised it. I did not
redesign W6.2 around `getElementTransform` — that is a scope decision for the lead,
and W6.0 was told to build the probe and nothing else.

**Why I think the thesis survives anyway** (for the lead to check, not to take from
me): `getElementTransform` returns the matrix you write to `element.style.transform`,
which makes the panel a genuinely CSS-transformed DOM element. Hit-testing, focus,
selection and a11y geometry then come from the transform natively. three.js's own
`InteractionManager` already works this way and never calls `updateElementGeometry`.
The a11y re-review in W6.4 is what should decide this, and it should not be skipped
on my say-so.

## W6-D5 · Arity is read through property descriptors, never by reading the member

Reading `HTMLCanvasElement.prototype.layoutSubtree` *invokes* the IDL getter with
the prototype as `this`, which throws `Illegal invocation` and took the whole page
down. The fault is only reachable **when the flag is on** — with it off the member
does not exist and nothing is read — so the first flag-on run was the first run
that could ever have caught it.

Recorded because it is the argument for having built the probe at all: a detection
function that crashes exactly when the feature is present is worse than no
detection, and nothing short of running it against a real flagged browser finds it.

`arityOf()` now walks the prototype chain with `Object.getOwnPropertyDescriptor`
and only reads `descriptor.value`, which never triggers an accessor.

## W6-D8 · One generic boundary; one concrete T1 strategy

`PanelPixelSource` receives a DOM element, renderer, camera, and W4 screen handle.
It has no Panel props, menu assumptions, or W3 state shape. This is deliberate
while W3 remains under REQUEST_CHANGES. Exactly one implementation exists:
`HtmlInCanvasPixelSource`, using Three `HTMLTexture` and `InteractionManager`.
Our source contains no raw `texElement*` call. T2–T4 have no implementation.

## W6-D9 · Geometry writes are not pixel writes

`InteractionManager.update()` writes `style.transform` on the panel host. Treating
that as a pixel mutation creates transform → invalidate → render → transform.
The observer ignores exactly that host-style mutation while retaining descendant
style/content changes. A deterministic test locks the distinction. A flagged
browser recorded zero requested animation frames over two idle seconds.

## W6-D10 · Dimensions come from the device boundary

The route knows neither authoring nor active-screen dimensions. On attach the
strategy sizes the host from `ScreenMeshHandle.panel`; shader dimensions come
from the live host. W3 layout and W4 geometry do not leak into the interface.

## W6-D11 · BLOCKING W4 visual seam defect; reported, not patched

The DOM upload succeeds and the same DOM remains focusable and represented below
the Canvas in the accessibility tree. The visible screen shows clamped bands.
W4 constructs the material slot with Three `ExtrudeGeometry`; Three's default
`WorldUVGenerator.generateTopUV()` returns shape-space x/y directly, not normalized
0…1 screen UVs. That exactly explains the clamped sample.

W6 did not edit `packages/device/src`. W4 must provide normalized front-face UVs
or a normalized screen quad. Until then API, DOM, keyboard, a11y, and idle behavior
are browser-verifiable, but visual acceptance is blocked.

## W6-D12 · Geometry is resynchronised from every projection input

Three's `InteractionManager.update()` consumes the canvas CSS viewport, camera
projection, and mesh world matrix. The strategy now observes canvas resize and
the React bridge resynchronises after committed camera/viewport changes; the
coordinator also resynchronises from the current `ScreenMeshHandle` on demand.
No animation-frame polling was introduced. In flagged Chrome, resizing from
1280×720 to 800×500 changed the host bounds from 252.39×189.29 to
153.94×115.45 CSS pixels. The old screen point hit `BODY`; the new visible point
focused the native `application`.

## W6-D13 · Renderer and camera identity define one attachment lifetime

Replacing either renderer or camera detaches and discards the old strategy,
removes context listeners, and reconciles a fresh source. A failed partial attach
is detached before the error escapes, and a later call with the same context can
retry. Repeated clear, reattach, context loss/restore, and dispose are idempotent.
The lifecycle lives in `coordinator.ts`, separate from React component exports.

## W6-D14 · Tier state is one Jotai value owned by composite

`compositeTierAtom` and its vanilla store are the sole mutable tier state. Boot,
context loss, restore, React rendering, and external subscriptions all read or
write that value. The direct `jotai` dependency is pinned to `2.20.3`, matching
the state and panel packages; an isolated resolution test proves
`jotai/vanilla` resolves from `packages/composite` without a transitive import.
Tier comparisons remain inside this package; the capability route calls a
composite-owned predicate.

## W6-D15 · The public component is SSR-safe; server truth is T4

Server rendering returns a stable T4/pending shell and never touches `document`.
The client runtime subscription creates the portal host only after hydration.
The public contract therefore does not depend on every route remembering
`ssr:false`, although the experimental preview remains client-only.

## W6-D16 · The strategy seam represents renderer-less T4 without building it

Pixel requirements and attachments are discriminated by renderer kind.
`PanelPixelSource<'none'>` accepts only a DOM panel attachment; T1 accepts the
WebGL renderer, camera, and screen handle. A compile-time fixture implements the
renderer-less shape without fake Three or device values. Only the T1 runtime
strategy ships.

## W6-D17 · A panel becomes a texture only after Chrome confirms paint

`HTMLTexture` marks itself dirty immediately, while Chrome refuses
`texElementImage2D` until the drawable child has a cached paint record. A queued
second render could therefore throw during first mount. The host is now adopted
by the `layoutsubtree` canvas before texture construction, the browser is asked
to paint, and the screen material remains detached until the corresponding
`paint.changedElements` includes this panel. Pre-paint mutations request paint
but never upload. Three still owns every experimental WebGL call.

## W6-D18 · Cross-lane raster and artwork blockers were consumed, not bypassed

The W4 normalized-UV boundary, W3 raster-compatible artwork CSS, and server/app
same-origin `/artwork` route landed independently. W6 imports only public package
boundaries and contains no panel/device/server patch. The final flagged render
shows real fixture artwork and a legible panel in both device colourways.

## W6-D19 · Accessibility comparison uses the same route and panel instance

The preview has `mode=bare|composited`; every other query input is identical.
Both colourways produce zero axe violations in both modes. Axe leaves four
contrast checks incomplete because two backgrounds are gradients and two nodes
are too short/non-text for inference. Exact endpoint calculations settle the
actual text cases: minimum ratios are 13.46:1 (dark title), 5.93:1 (dark selected),
14.04:1 (light title), and 10.71:1 (light selected). The CDP accessibility tree
retains the focused application, named listbox, options, and selected state.

## W6-D21 · CSS geometry and physical pixels are separate contracts

The 330×552 device remains a CSS-pixel layout contract. Its drawing buffer is a
physical-pixel contract resolved from `devicePixelContentBoxSize` when that API
is truthful and from `window.devicePixelRatio` as the required fallback. The
higher valid ratio wins because Chrome device emulation can expose a CSS-sized
device-pixel box while still reporting the real device scale factor. Rendering
is capped at 3×. A numeric `dpr={1}` remains an explicit measurement override;
only the normal tuple mode installs the observer.

R3F's public `setDpr` owns renderer resizing. Canvas resize still invokes the
existing `getElementTransform` synchronization; DPR support does not replace or
approximate that geometry path. `visualViewport.resize` covers browser zoom and
the same resolver handles fractional ratios.

## W6-D22 · HTMLTexture receives its own 1×/2×/3× source raster

A high-resolution WebGL drawing buffer cannot recover detail from a 320×240 DOM
upload. The drawable host and its first content child are therefore rasterized
at a quantized 1×/2×/3× source density matching the renderer, while the shader
and screen mesh retain the logical 320×240 panel dimensions. Three 0.185.1 still
owns `HTMLTexture`, `texElementImage2D`, and `InteractionManager`; mipmaps are
disabled and both filters are explicitly linear for the continuously projected
LCD plane.

Raster-density writes are idempotent. This is a correctness requirement, not an
optimization: assigning the same child transform repeatedly retriggered the
panel MutationObserver and caused a paint/resize feedback loop in flagged
Chrome. Detach restores the pre-attachment child styles.

## W6-D23 · The composite boundary owns narrow-viewport containment

The public composite root is a contained, border-box, 100%-wide boundary with a
zero intrinsic minimum and clipped overflow. This keeps the 330px authored
device centered within a 390px viewport without allowing its experimental
canvas descendants to enlarge the grid track. The app route remains untouched.
