# Worker renderer and native screen implementation dispatch

Read-only CPU-004 follow-on proposal on codex/gpu-worker-rendering. Read the complete current gpu-worker-scope.md, renderer/worker audits, CPU-006 prepared data and CPU-008 material contracts; refreshed CPU-004 show/context. No host application changes or browser calls. The separate reviewer-requested CPU-008 lifecycle corrections are recorded in its own diary. This proposal is ready to turn into explicit CPU-009 ownership after its parent contracts pass review (CPU-006 accepted at88ecc44; CPU-008 accepted at67478ad).

## Architecture decision

Use one imperative Three scene/render owner in a dedicated renderer worker, with the exact shared device assembly description and CPU-008 node factories. Keep React, Jotai, the actual Panel DOM, input capture, haptics/audio and media activation on main. Do not place WebGPURenderer into Fiber's WebGL-typed RootState through a cast, and do not reconstruct a second ad hoc device from approximate meshes. Existing main Fiber/WebGL remains the complete fallback on a fresh canvas.

CPU-006 already supplies data rather than serialized Three objects: device-preparation-data.ts exports PreparedDeviceData, PreparedTextureData, restorePreparedDevice and preparedDeviceBuffers; immutable-shell-transfer.ts preserves all attributes/index/groups/drawRange/bounds. These are the static assembly resource source. Its current public entry is a React hook returning already-restored wrappers, so CPU-009 must extract a non-React resource lease interface from immutable-shell-preparation.ts rather than call the hook in a worker or serialize live Three wrappers.

The worker scene must include body/back, every hardware part, control assemblies and legends, display well/cover/LCD, equipped stickers, sleeve/liner stock and sticker carry. Shipping an activated renderer that omits any of these is forbidden. CPU-010/011 can subsequently optimize query/deformation transport without allowing CPU-009 to silently remove existing behavior.

## Shared assembly, data and ownership contract

Extract the exact declarative hierarchy now in Device.tsx, DeviceHardware.tsx and StickerPackScene.tsx into immutable named descriptors. Each item has stable ID/parent ID, geometry resource ID, material recipe ID(s), original local position/quaternion/scale, visibility, renderOrder and frustum/depth/side flags. Geometry keys include all CPU-006 inserts and hardware part names, not just front/back. Preserve existing names consumed by queries (device-model/content, device-body, device-steel-back, device-equipped-stickers, sticker-ID, wheel/select assemblies). Both the existing R3F fallback and worker assembler consume these same descriptors; event callbacks bind by semantic ID on main, never enter the wire description.

Material recipes are a closed discriminated union: stock basic/standard/physical, polycarbonate transport, cover glass with explicit key/aligned lamp IDs, LCD transfer variant, sticker front/back appearance and paper part. Values are the existing plain parameter types, enum constants, IDs and finite tuples; no Color/Texture/Material/functions/Object3D instances cross postMessage. Ordinary node materials preserve every stock physical field. Apply renderer-defaults.ts exactly: AgX tone mapping, exposure1 and transmissionResolutionScale1, plus the original output precision and physical resolution; constructor defaults are not accepted as parity. CPU-008 factories own the six custom categories. Light descriptors preserve original order, dimensions, transforms, intensity/color and scene environment; both authored PMREM rooms use createBackendStudioMaps with the original sigma. Screen environment remains distinct from body environment.

Prepared assembly version is DEVICE_PREPARATION_VERSION plus complete form/recipe identity. A renderer resource lease contains its private PreparedDeviceData buffers; a query lease contains the exact geometry/alpha/index data needed on main. The producer/broker creates necessary private copies in the preparation worker before transferring them. Never run preparedDeviceBuffers over a mounted cache lease and detach its backing store. Transfer through a MessagePort from preparation to renderer where possible; main receives small identity/adoption messages and its separate query payload. A fallback GL generation may adopt an existing main lease or request a fresh private lease, never steal the render worker's buffers.

Current CPU-006 completed cache uses byte accounting and owner lifetime. Extend that single accounting owner to include render and query leases rather than add another unbounded cache. At most one admitted replacement assembly per renderer while the current assembly is live; cancel superseded queued forms, release unused images/buffers and retain no unlimited historical generations. Compute/preparation workers stay brokered; renderer creation must not create independent duplicate preparation jobs.

Main-only raster work is explicit: textures.ts createWheelLabelTexture uses native canvas/font raster; backplate-finish.ts combines prepared 1024×2048 base pixels with Arial engraving and a bump mask. Keep those native browser font results, export completed canvas images as transferable ImageBitmap with explicit orientation/premultiplication/color-space handling, and validate pixels against the original CanvasTexture. This is a one-time native raster transfer per recipe/colourway. Do not rerun dense deterministic noise/aluminum/steel loops on main. CPU-006 RGBA maps already carry wrap/filter/colorSpace/mip/repeat/flip/premultiply/anisotropy/unpack metadata and must retain it. Do not replace engraving or legends with worker text until actual font-pixel parity is demonstrated.

Artwork similarly has stable texture ID/revision and exact alpha/damage resource ID. Prepared damage is required by createStickerNodeMaterials; do not call DOM alpha extraction from worker material construction. Existing worker paper/carry geometry snapshots may be routed directly to renderer, with a separate immutable main query lease until CPU-010/011 optimize them. A geometry adoption message includes source/topology/gesture/pose revisions; frame completion does not authorize saving a sticker.

## Wire protocol and backpressure

Define a versioned tagged union, with runtime validation at both boundaries and no unchecked renderer casts:

- init: rendererEpoch, transferred associated OffscreenCanvas, CSS/backing size, resolved DPR, exact camera configuration, preparation/asset ports and immutable scene version.
- resource/adopt/release: resource ID/revision/byte count, explicit payload ownership and acknowledgement. Resource admission is separate from frame/projection credit.
- scene: immutable descriptor revision and references to already-admitted resources. Missing references reject readiness; no partial scene is declared ready.
- pose: monotonically increasing poseSeq plus model/content/wheel/select/pack matrices or scalar recipe values and camera/layout revision. Only this replaceable state may be coalesced to the latest pending sample.
- command: ordered commandSeq for gesture start/release/cancel, animation start/interruption, visibility and disposal. Every release/cancel carries its exact final pointer sample and final poseSeq plus the scalar pose itself (or an explicit acknowledged pose barrier). The worker applies that sample before the ordered action; it cannot consume whichever newer/older value happens to remain in the latest-only pose slot. This also holds across separate MessagePorts, which provide no shared ordering. Never drop final pointer/release or command records into latest-only pose coalescing.
- panel-paint: rendererEpoch, rasterRevision, snapshotSeq, dimensions/format and transferred ElementImage. One in flight plus one uncaptured dirty state. Do not capture an unlimited queue of native snapshots. Capture credit has a unique captureId and is tied to rendererEpoch, layout/raster generation and source paint revision. A queued paint callback or asynchronous wrapper completing after hide/resize/dispose must close its result without publishing; only a matching current capture/upload acknowledgment releases the current credit. Old acknowledgments cannot reopen a new generation or strand its credit. Pixel byte limits derive from the admitted raster size, not unbounded viewport changes.
- projection: rendererEpoch, scene/resource/layout revisions, poseSeq, screen matrix/corners, camera/model/control/pack transforms required for exact main query projection. One unacknowledged notification plus one replaceable pending latest result; no worker animation waits for that acknowledgement each frame.
- ready/failure/disposed: precise generation/reason. Ready requires adopted complete resources, initial native paint upload and successful compile of the complete current scene, followed by render submission. Shader support alone is insufficient.

Do not encode live Three objects, serialized scene JSON per pose, callbacks, Jotai stores or user/media commands in resource messages. Worker identity is checked in addition to rendererEpoch so a late message from a replaced worker cannot match a reused number.

## Associated native canvas allocation and upload

Create the actual presentation HTMLCanvasElement with layoutsubtree and the real Panel descendant before taking any context. Main retains the DOM node and existing React portal. CompositeDevice currently gates its portal on tier==='T1', so backend loss can unmount Panel: explicitly remove that lifecycle coupling. Create one stable panel host/portal/input boundary outside the renderer generation; park and reparent that same host during replacement, never render a second Panel. Preserve focus/selection where valid, with a focus-generation guard so delayed recovery cannot steal newer user focus. Cancel held captures/physical presses through the existing cancellation path before removing their canvas; do not leave a held wheel, drag, haptic or audio release orphaned. Transfer it exactly once to the renderer worker; obtain WebGPU context only on that associated OffscreenCanvas. The observed foreign-canvas lineage failure forbids detached staging. Existing GL canvas cannot be retroactively transferred; selection/recovery creates a fresh canvas generation and reparents the same Panel owner.

Native texture allocation uses installed Three APIs: create a StorageTexture at the exact admitted raster dimensions, RGBA/UnsignedByte, NoColorSpace, LinearFilter for min/mag, no mipmaps, same orientation/premultiplication contract; await renderer initialization, then renderer.initTexture once. Installed WebGPUTextureUtils creates TEXTURE_BINDING|COPY_DST|COPY_SRC and render-attachment usage for this color allocation. Read the allocated GPUTexture from the selected concrete backend's data map only after initialization. A narrow pinned backend adapter must validate the concrete WebGPU backend and GPUTexture handle; do not overwrite Three's allocation or reassign arbitrary GPUTexture objects to a Texture.

The installed @types Backend omits parts of this data map and WebGPU device surface. Use canonical WebGPU types (official @webgpu/types if needed) and exact Chromium152 IDL declarations for ElementImage/copyElementImageToTexture, backed by checked runtime capabilities. A tiny source-backed adapter may validate the omitted runtime get method/returned GPUTexture; do not cast RootState.gl, generic objects or unknown data into WebGPURenderer. Own the GPUDevice explicitly if passing it into renderer options; Three does not destroy externally supplied devices. Otherwise the renderer backend owns it and normal teardown uses the reviewed backend service.

On a current main onpaint record affecting Panel, captureElementImage using the associated canvas, transfer only when paint credit is available, then worker executes the observed API:

`queue.copyElementImageToTexture({ source: image }, { destination: { texture: allocatedTexture, colorSpace: 'srgb', premultipliedAlpha: false }, width: rasterWidth, height: rasterHeight })`.

The current Chrome probe verified this family; drawElementImageToTexture does not exist there. Render through createLcdNodeMaterial(texture,'unorm-srgb'), so native unorm bytes receive exactly one EOTF. Do not set texture.needsUpdate every paint (which asks Three to upload its ordinary source again); write the allocated native texture and request render. Consume/close the native snapshot using the current IDL ownership methods even on stale epoch, upload failure or cancellation. No recurring CPU readback or ImageBitmap staging is part of this pixel path.

A raster-size change allocates a new texture generation, invalidates paint/compile readiness and requires a fresh corresponding paint; old-size snapshots are rejected/released. Preserve resolvePanelRasterDensity/resolvePanelRasterFrame and the unified physical-pixel observer exactly. Main keeps CSS measurements/DPR publication; worker sets its drawing-buffer size once per accepted layout revision, never from orientation frames. Texture replacement may require recompile before swapping the ready scene.

## Projection and actual main interaction consumers

Do not forward a fake WebGL renderer to InteractionManager. Installed InteractionManager.update only needs the associated DOM canvas dimensions, element dimensions, geometry extent and MVP. Extract its exact viewport × projection × view × model × pixel-to-local matrix calculation into panel-projection.ts and test it against the installed manager's matrices. Main applies matrix3d to the same real Panel element and preserves wpScreenClip* functional data used by touch sizing. Carry viewport/size/DPR revisions; CSS transforms use CSS pixels, not backing pixels.

ScreenMeshHandle's local contract currently includes immediate readTransform, change notification and a Material setter. Keep that contract for the GL source and add a genuinely distinct worker-screen attachment using data projection and material recipe IDs; do not pretend a remote handle can synchronously read a worker Mesh or accept a transferred Material. CompositeCoordinator/pixel-source need a discriminated local-GL versus worker-WebGPU attachment. Replace screen and renderer context atomically by generation: current setScreen ignores replacements while attached, so sequentially retaining its old handle with a new context is invalid. Detach the complete old attachment before admitting a new screen/context pair.

Synchronous consumers that must be served explicitly on main:

- Device orientation shell raycasts and outer grab band; exact prepared shell query geometry plus current committed transforms, camera and viewport. Preserve control-hole exclusions and touch band expansion. Main pointer capture remains immediate.
- CompositeInputController/clickwheel: same store, event admission, physical click/haptic/audio pathways and provider transport handling. Canvas generation replacement must not create a second controller/audio runtime.
- StickerRearProjection from StickerPackScene: project/hit/screen/bounds/quad/contour/grab/beginTransform and optional fit/resolveDrop. production-device-view.tsx's stickerCommands calls these synchronously, including place→fit. Keep an exact main query view using admitted immutable geometry/alpha/provenance and pose-stamped matrices. Do not substitute null, rear-only fallback pickup or a guessed rectangle when a visible-print query is required.
- Frozen grab/transform-plane handles retain their source geometry/camera/layout/gesture generation and invalidate on incompatible changes, preserving existing isValid semantics.
- onProjectionReady/onSurfaceReady, onPrepared, onArtworkReady/onArtworkError must cross as typed identity/status messages and update existing main callbacks/Jotai atoms. A worker texture arrival alone does not mark a collection usable before all actual assets/materials are ready.

The query view contains prepared query objects and scalar matrices only; it must not retain a second full render hierarchy or repeat whole-scene traversal each frame. CPU-009's query mirror is a correctness bridge, not an exemption for repeated dense main work. It adopts prepared data without reconstruction loops; CPU-010 replaces its object-heavy collision representation and CPU-011 moves fitting/contour/damage transactions. CPU-012 moves autonomous pose/reveal/control stepping. Until those slices finish, report the remaining work on main honestly.

Projection and query state adopt the same accepted pose/layout/resource revision atomically, applying the DOM matrix immediately on message receipt rather than another RAF. Reject all obsolete epochs. The worker continues animation without waiting for main projection credit. This does not prove a physical display acknowledgment; current Chrome152 has no updateElementGeometry event path. Actual resumed-input alignment under main-thread stalls is a required existing-route measurement against the current renderer baseline. If the protocol fails that gate, keep existing GL preference while correcting it; do not declare exact hit parity solely from matching sequence numbers or suppress the feature to hide the mismatch.

## Lifecycle and activation sequence

1. Select capability before context creation; preserve existing loading/reveal readiness. Spawn one renderer generation, acquire admitted resource leases and transfer the associated canvas. Input/media authority remains on main throughout.
2. Initialize core WebGPU with authored MSAA/output precision, create complete scene and both studio environments, upload real panel paint, compile current material generation and render. Only then report ready and begin the existing entry trajectory. CPU-008 rejects incomplete compatibility mode and implicit GL-node fallback.
3. On hide, cancel scheduled worker submission and new captures, retain one dirty latest state and no unbounded image backlog. Resume with current layout/resource/pose plus a fresh paint if invalidated. Renderer scheduling remains demand-based when there is no animation or dirty pixels; stop autonomous physics at settlement.
4. Device loss, compile/upload error, timeout, stale worker or unsupported transport retires the generation. Close ports/snapshots, dispose textures/materials/geometry leases/PMREM and renderer through the owner, explicitly destroy an externally owned GPUDevice, acknowledge disposal, then terminate normally. A hard deadline permits termination of a hung native owner. Ignore late events unconditionally.
5. Recovery creates a fresh canvas and the original full GL/Fiber renderer, reconnects the same Panel/input/store without duplicate media requests, rebuilds paint readiness and preserves user state. No attempt to reverse transferControlToOffscreen. Retry native only by explicit controlled generation selection, not an infinite failure loop.
