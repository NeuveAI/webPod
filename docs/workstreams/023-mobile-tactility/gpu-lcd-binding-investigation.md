# LCD binding diagnostic proposal (read-only)

Matched Silver/light captures supplied by the lead show a darker/flatter native LCD while chassis and wheel match. The healthy exact PR5 GL reference has full tier and prepared packet; GL artwork warmup failure is therefore not an adequate explanation of this visual difference. Screenshots alone cannot distinguish capture/color transfer from glass/transmission/lighting.

Source shows intended equality, not actual rendered equality: current GL `Device.tsx` and native `device-render-worker.ts` both feed the cover glass the separate `screenTexture`; `StudioEnvironment.tsx` and `render-backend-services.ts` both build `createProductStudioEnvironment(true)` for that PMREM. Both renderers use AgX, exposure1, transmission scale1. GL LCD uses `HTMLTexture` tagged SRGB plus the explicit map-fragment decode in `html-in-canvas.ts`; native uses rgba8unorm/NoColorSpace plus explicit EOTF in `lcd-material-nodes.ts`. Native upload requests sRGB, straight alpha. These intended metadata paths need actual binding inspection before any shader edit.

## Proposed first stage: scalar snapshots at actual ownership boundaries

Temporarily archive and instrument only the minimum local owners, bounded to once per current renderer/screen generation, at most two records for a first-paint transition. No global getter, app route, public debug command, persistent logger, UI or per-frame work. Use a recognizable one-shot console JSON line so the lead can retain both main and worker console output through the existing browser connection; it contains no captured content or user/library data.

- GL: inspect `screen-mesh.ts` inside its existing onBeforeRender using the actual renderer/scene/material arguments, before early transform-notification return. This sees the material actually installed by the compositor, rather than `screenDefaultMaterial`. In `Device.tsx`, inspect the locally owned glass and studio snapshot once after commit, recording role identity comparisons (`glass.envMap === studio.screenTexture`, `glass.envMap === studio.texture`) and the exact bound glass object/UUID so it can be correlated with the rendered object. For the exact PR5 checkout, use its equivalent existing component owner rather than applying a current-tree source patch blindly.
- Native: inspect `device-render-worker.ts` immediately before the first painted render, from actual `graph.objects` screen/glass material slots, current studio owner, scene and renderer. Inspect raw native destination allocation/upload metadata inside `native-element-image.ts` once after successful upload, where actual `GPUTexture.format/width/height`, capture dimensions and destination alpha/color-space contract are available. No GPU readback at this stage.

Compare scalar fields, not cross-process UUID equality: glass color RGB, opacity/transparent/visible, roughness, metalness, transmission, thickness, IOR, attenuation color/distance, clearcoat/roughness, specular color/intensity, env intensity, toneMapped, side/depth/blending; bound environment role and texture mapping/type/format/colorSpace/dimensions/version; scene environment identity/intensity/rotation; exact screen material type/name/cache-key role, color/opacity/transparent/toneMapped/blending, map identity/type/format/colorSpace/flipY/premultiplyAlpha/filter/mipmaps/offset/repeat; renderer outputColorSpace/toneMapping/exposure/transmission scale and drawing-buffer dimensions. Bound direct-card light scalar dimensions/intensities/positions/rotations establish that glass receives the same light recipe. Record effective mesh/material visibility and screen/glass local transform/z separation as compact scalars. Omit undefined fields rather than guessing equivalent defaults. Use finite/null encoding for infinite attenuation distance.

The lead's existing browser expression can additionally read only the canvas/Panel opacity, filter, mix-blend-mode and logical/raster bounds. No storage or user text. Capture exact same settled Music view, colorway, pose and viewport for each backend. Restore every instrumented source byte-for-byte and verify archived hashes after both snapshots; evidence/report only are retained.

## Conditional second stage: bounded before-glass pixel comparison

Only if actual binding/role/output metadata match, run one owner-local offscreen comparison borrowing the current LCD material/texture with glass absent, preserving its real transfer/output pipeline. Use a small render target and a canonical quad solely for sampling, with identical UV sample locations corresponding to fixed background/divider/text regions of the unchanged Music screen. Read a fixed small pixel grid (e.g.8×8, or four small tiles); no full-screen GPU readback. Preserve target color/alpha format explicitly and normalize row origin before comparison. Do not reuse a tone-mapped default material or change the live material/scene, because either would invalidate the color-transfer diagnosis.

Each backend's owner must use its installed supported target/readback API, impose a short deadline, and dispose temporary target/quad geometry/material wrappers and buffers in finally. Borrowed live texture/material ownership is untouched; a copied material must retain the exact GLSL hook/node graph. If this cannot be guaranteed cheaply, stop at stage one rather than inventing an approximate sampler. Record RGBA tuples plus target transfer metadata, not a broad content dump. Different pre-glass output localizes capture/decode/alpha; matching pre-glass output makes glass/transmission/PMREM the next concrete boundary. Even identical scalar PMREM metadata does not certify equal GPU PMREM texels.

No application changes, browser calls, build, readback or claim of root cause were made for this proposal. Both stages require the lead's bounded scope approval; current GL/priming source freezes remain intact.
