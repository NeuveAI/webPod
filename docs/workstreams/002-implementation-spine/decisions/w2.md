## 2. Deviations from a 001 number

### 2.1 `Shift+Arrow` is one viewport of rows, not a flat 7

001 §4.4 says `Shift+Arrow` = **7 rows (one page)**. 001 §4.6 says
`Shift+↓`/`Shift+↑` = **one page (8/6/4 rows by density)**, and 001 §4.3 says
`⏭`/`⏮` page by "one full viewport of rows (8 / 6 / 4 by density)". Two of the
three agree with each other and with the words "one page"; the third does not.

**Chosen:** the density-based page — 8 / 6 / 4. `⏭`, `⏮` and `Shift+Arrow` all
land on exactly one viewport, which is what makes the gesture legible ("the
list moved by one screenful"), and it keeps the keyboard and the transport
buttons doing the same thing.

The likely origin of the 7 is visible one column to the left in the same §4.4
table: 7 is the top *acceleration* multiplier. A flat 7 would also be wrong at
`airy` density, where it skips 3 rows past the end of the viewport.

`⚠ DEVIATES` from 001 §4.4. Reversible in one line: `pageRows` is a parameter
of the key input, not a constant.

### 2.2 Announcement urgency for `source: 'system'`

001 §11.8 gives the human sentence and the agent sentence. It gives no system
sentence. `describeMovement` renders a system movement in the **human** form —
`Row 4 of 18. …` — rather than inventing a third voice.

Reason: a system-caused move (a queue advancing, a screen restoring) is
something that happened *to* the device, not something an actor did to it.
Naming an actor would invite the listener to look for one, which is the exact
failure class 001 §8.2.4 documents. Logged because it is a gap I filled.

### 2.3 `agent:unknown` when no origin is supplied

001 §8.4 specifies `actor: 'agent:<agentOrigin>'`. The platform supplies no
agent identifier — a page learns an agent exists only when a tool executes —
so the origin can only be whatever the tool layer knows about its caller.
`DetentInput` carries an optional `agentOrigin`, and when it is absent the tag
reads `agent:unknown`.

This asserts nothing about presence. It is a label on a movement that already
happened, and "unknown" is the honest value. Nothing in this stage emits it.

## 3. Choices made under uncertainty

### 3.1 `jotai` pinned to exactly `2.20.3`

The rest of the repo uses caret ranges. This one is exact because 2.20.3 is the
version of the clone I grounded against, and because of the hazard in §4.1.
`bun.lock` gained one entry; nothing else in it moved.

### 3.2 Device state is derived, not assigned

`deviceStateAtom` is a read-only derived atom over four primitives
(`holdEngagedAtom`, `connectionAtom`, `agentThrottledAtom`, `agentActiveAtom`)
rather than a writable atom the reducers set.

Deriving it makes "exactly one state at a time" structural: there is no
combination of the primitives that yields two, and no writer that can leave a
stale one behind. 001 §8.2.2 requires the property but does not say how.

**Precedence, which 001 does not specify:** `HOLD_ENGAGED` > `DISCONNECTED` >
`AGENT_THROTTLED` > `AGENT_ACTIVE` > `USER_ACTIVE`. Hold is the human's
physical override and outranks everything; disconnection outranks the agent
states because it changes what is *possible* rather than who acted last;
throttling is documented as a sub-mode of agent activity, so it sits directly
above it.

### 3.3 `AGENT_THROTTLED` is a plain boolean with no deadline

001 §7.4 is the rate limiter, and it is not in this stage. `agentThrottledAtom`
is a boolean the limiter will write. It deliberately carries **no** countdown:
a second copy of a deadline is a second thing to keep true, and the exact
seconds go to the caller in the refusal payload rather than to the screen.

This is also why there is no timer anywhere near it. The only `setTimeout` in
the package is the announcement debounce, and it lives in `startAnnouncer`.

### 3.4 The highlight and the scroll window live *inside* the frame

001 requires that `Menu` restores the exact prior highlight. Storing the
highlight and the window on the `ScreenFrame` makes that free: popping is a
stack pop and the position comes back because it never left. The alternative —
one global highlight plus a map of saved positions — has to choose a key, and
drifts the first time a screen is reachable by two routes.

### 3.5 `Center` is declined by the machine

`pressActionAtom` fully handles `menu`, `next` and `previous`, and returns
`handled: false` for `center` without changing anything.

This is a boundary, not a gap. The machine owns the stack; the layer holding
the data owns what a row points at. A row on the main menu descends into a
known screen — `MENU_ROOT`, `findMenuNode` and `menuFrame` are exported for
exactly that — but a row on an album is a track, and descending means playing
it. Guessing here would put half the navigation model in the wrong module.

### 3.6 The pure machine returns a bump *direction*; the store stamps the event

`ScreenTransition.bump` is `BumpDirection | null`, not a `BumpEvent`. The
machine has no clock and no counter, and `BumpEvent.seq` must be monotonic —
two identical bumps in a row have to be two distinct values or the second one
is swallowed as a no-change and the human concludes the button is broken. The
store is the only place that can guarantee that, so it stamps `seq` and `at`.

### 3.7 The announcer is pure; the one timer is in the store binding

`noteMovement` records a due time and `flushAnnouncer` asks whether it has
arrived. Neither schedules anything. `startAnnouncer` owns the single
`setTimeout`, re-aims it on every movement, and cancels it on teardown.

This is what lets the 30-detent gate be proved with plain numbers and no fake
timers, which makes the test evidence about the code rather than about a mock.
There is also a real-timer test of the driver itself, so the wiring is not
taken on trust.

### 3.8 Invented values, both flagged

- **`KEY_REPEAT_WINDOW_MS = 250`.** 001 §4.4 says a keypress announces
  immediately, "debounced only during auto-repeat", without saying how
  auto-repeat is recognised. Two key detents closer together than 250ms are
  treated as a repeat. 250ms sits below every OS auto-repeat *delay*
  (typically 250–500ms) and far above every repeat *interval* (30–50ms), so it
  separates the two cleanly. It is a constant in `contract.ts`, not a literal.
- **Empty-screen sentence: `"<title>. No items."`** 001 §11.8 has no row for
  an empty list. `Row 0 of 0` is a sentence about the implementation.

### 3.9 The window slides by the minimum, and lists clamp rather than wrap

Neither is specified. Minimum-slide rather than recentring, because recentring
makes a one-row movement look like the whole list jumped and forces the eye to
re-find the highlight after every press. Clamping rather than wrapping, because
a list that wrapped would make counted navigation ambiguous about where it
landed — "down four" from row 2 of 3 would be unanswerable — and 001 §4.3
already specifies hard stops with an elastic bump for the rating wheel.

### 3.10 A fifth commit for gate vocabulary

The plan named four commits. A fifth, `refactor(state): keep the universal gate
greps clean`, follows them: it renames the announcer's `pending` field to
`settling` and rewords comments so that 001 §15.0's U8 and U9 greps come back
clean. It is comment-and-identifier only, no behaviour, isolated per the
scope's rule that mechanical changes never ride along with behaviour.

## 4. Hazards handed forward

### 4.1 ⚠ W3: depend on `jotai@2.20.3` exactly, or do not depend on it at all

`packages/state` is React-free by construction — no `react` dependency, and a
test asserts React is not even resolvable from the package. The atoms are
created by *this* package's copy of Jotai.

Bun 1.4's isolated linker gives each workspace its own `node_modules`. Two
workspaces asking for the same exact version share one physical path in the
store and therefore one module instance, so atom identity holds. **Two
different versions would be two Jotai instances**, and `<Provider store={…}>`
from one would not be found by `useAtomValue` from the other. The symptom is
not a type error; it is a component reading a default value forever.

So: `apps/web` and `packages/panel` should pin `jotai@2.20.3` on the nose. If
that turns out to be fragile in practice, the fix is for this package to export
a bridge hook — the dispatch permits exactly one — and for nobody else to
import `jotai` at all. I did not build it pre-emptively, because keeping this
package React-free is the stronger proof of the property the slice exists for.

### 4.2 U8 has three standing hits in `contract.ts`, pre-cleared

`grep -rniE '\b(allow|deny|…|permission|granted|…)\b' packages/state/src/`
returns three lines, all inside TSDoc, all of them prose stating that the
permission model does **not** exist and why the states that assumed it were
deleted (§8.2.4, and the note that `B10` "granted standing permission for
actions that were never gated").

U8 is a manually-cleared gate. These are cleared: they are not agent-flow copy,
they are not strings any human will read in the product, and deleting them
would delete the warning that prevents the bug. Nothing else in the package
matches. `useState` returns 0; the agent-presence grep returns 0 repo-wide.

### 4.3 What is *not* built, and is not missing

No tool is registered and no `document.modelContext` call exists — the seam is
`DetentSource` and the `direct` input path, both unused by anything in this
stage. No haptics or clicker audio: `DetentOutcome` reports counts, and the
30/sec clicker limiter belongs with the sound layer when it lands. No React
bridge hook. No `pod-read-screen`; `readScreen` is the projection it will use.
