# Canonical development startup diagnosis

2026-09-06. A final lead gate failed before Vite printed readiness: root launch remained alive for the unchanged 45-second readiness deadline. App launch passed afterward. Reproduction did not assume a one-off slowdown: an initial root pass and root/app pair pass were followed by the same failure on the third fresh root repeat. A separate startup-only diagnostic reproduced it again, and a bundled-config control repeated it once more. All runners excluded user environment files/certificates and used unique source snapshots, installs, ports and SQLite paths; each owned process group was cleaned.

## Attribution and change
The stalled process tree consisted of the expected three Bun processes: root package script, app package script and Vite. Sampling showed idle outer script layers, an innermost Bun main thread waiting in `kevent64`, and Rolldown native workers waiting on condition variables. This does not establish an upstream Bun/Rolldown root cause. It does rule out a failure to launch the final Vite process and gives a concrete signature for the intermittent pre-readiness stall.

Cache attribution was checked during a stalled bundled-config control: root/app `node_modules` were real directories in that unique snapshot. The Vite dependency symlink resolved into the same snapshot's `.bun` tree. `.vite-temp` was local and empty; optimizer `.vite` did not yet exist. No user's cache/server was modified. The final material build/browser ran independently during part of diagnosis; the earlier repeated full-gate failure occurred without a coordinated browser/build overlap.

The shipped app dev command now adds `--configLoader runner`, avoiding the default bundled-config startup path while retaining the nested Bun launch. Root remains `bun --env-file=.env.local run --cwd apps/web dev`. Production build/runtime commands and Bun-only server boundaries are unchanged. No readiness timeout increase or automatic retry was added. The runner passed eight consecutive fresh root readiness probes at approximately 1.64–1.75 seconds.

A native-loader candidate also passed eight readiness probes, but was rejected after direct installed-Vite probes showed that rewriting a temporary main config from marker 1 to 2 returned marker 1 again. The reviewer independently reproduced cached imported-helper values with no tracked dependencies. Startup success alone was insufficient to accept that candidate.

The expanded canonical root/app gate verifies normal CSS HMR, editing the main Vite config, editing an imported config helper, and rendering again after both restarts. Each mutation affects only the credential-free snapshot. The first expanded harness raced CSS-triggered SSR program reload with config restart and left readiness response bodies undrained. The corrected harness waits for the real route to reach T1 after CSS HMR, consumes all probe bodies, and uses Connection: close for restart probes. A complete root run passed in 14.3 seconds. This establishes the corrected harness behavior; it does not establish an independent production teardown defect or the exact contribution of each harness change.

The final gate passed three repetitions: nine tests, 6,075 assertions and six fresh root/app launches in 84.84 seconds. Results are recorded in `startup-runtime-verification.json`. All servers render `/` and `/_spike/device`, load anonymous SQLite transport, and check executable client modules for server-only imports. A source contract test preserves Bun, root env/cwd semantics and the runner choice.

## Source grounding and limitation
Canonical Bun reference: `.better-coding-agents/resources/bun/docs/runtime/index.mdx` documents native TypeScript transpilation. Canonical Vite checkout `resources/vite/docs/config/index.md` documents `--configLoader runner` as an unbundled alternative, but still describes an older esbuild default. Installed Vite 8.2.2 `dist/node/chunks/node.js` uses Rolldown for `bundleConfigFile`, selects loaders in `loadConfigFromFile`, and watches the main config and config dependencies in `handleHMRUpdate`. Current official [Vite config documentation](https://vite.dev/config/) confirms the runner option and its module-runner behavior.

A direct temporary-config probe on the installed runner re-read marker 1 then marker 2 correctly. The actual server gate additionally verifies imported-helper change propagation, so the rejected native candidate's manual-restart limitation does not describe the chosen runner. No generic guarantee about other Bun/Vite versions is inferred.

Evidence: `evidence/tactile-collection/startup-runtime-verification.json`, owned process/sample files, and locally preserved diagnostic logs. No environment values, key contents or authenticated data were read or recorded.
