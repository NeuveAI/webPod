## Where the work actually went

**The branded `LocalKey`.** The packet says two things that cannot both be
satisfied by a literal transcription: "transcribe §14.2" and "verify by TYPE,
not convention". §14.2 writes `type LocalKey = string`, and against that a
`catalogId` typechecks in every key slot. I branded it, kept it assignable to
`string`, and wrote three `@ts-expect-error` assertions that a bare string, a
`catalogId` and a `libraryId` are each rejected. Logged as a deviation and
raised for the lead. It is the one place I knowingly did not transcribe.

**`ProviderId` needed a third member.** The fixture provider is what 002
renders from, so its `TrackRef`s carry `provider: "fixture"`. The alternative
was letting it claim `"apple"`, which would put a lie in the exact field §14.5
exists to keep honest. Widening cost nothing at call sites, which is §14.4's
own argument for `supports()` paying off on its first test.

**`artworkUrl`'s `actualPx` semantics were wrong on the first pass.** I had it
returning `min(requested, available)`, so asking for 100 against Spotify's
640/300/64 reported `actualPx: 100`. That reads fine and is wrong: the source
you get is the 300, and a caller told "100" has no way to know the asset is
sharper than the box. It is now the largest width at which the returned URL is
still sharp, which is what §14.2's own comment describes.

**The §14.3 table test is transcribed by hand, not imported.** Importing the
matrices to check the matrices proves a file equals itself. The test carries an
independent reading of all thirty rows — including the five that have no union
member, each asserted with the reason it has none — plus a coverage assertion
that every `Capability` appears in exactly one row, so no capability can be
added and left untested.

**The include hazard got a function with a deliberately missing parameter.**
`readSongRelationship` takes no HTTP status. Not "ignores"; there is no slot.
A test asserts its arity, so the enforcement survives a rewrite by someone who
has not read the comment.

## The shape of it, which is the finding underneath the findings

The reviewer's own summary is the accurate one: *"its research fidelity is the
best I have seen in this workstream, and its enforcement claims do not survive
being tested."* Twenty of twenty-six plants went red. **All four that did not
were guards rather than values** — the arity check, the third brand proof, the
`ProviderId` union, the duration tolerance — and I had written every one of them
believing it worked.

I never tried to break my own guards. That is the whole gap, and it costs a
minute per guard:

- `expect(readSongRelationship).toHaveLength(2)` looked structural. **`Function.length`
  stops counting at the first defaulted parameter**, so `(resource, name, status = 0)`
  satisfied it, and the reviewer reintroduced the exact D-029 mistake —
  `if (status === 200) return …data ?? []` — with `tsc` at 0 and 230 tests
  green. Now a closed parameter object plus two type-level assertions: the
  parameter tuple is exactly length 1 and `RelationshipRead`'s key set is
  exactly `resource | relationship`. Both of the reviewer's plants are compile
  errors. D-054 credits this lane with "prefer unrepresentable over forbidden";
  the removal was real and the *proof* of it was runtime introspection, which
  constrains nothing.
- Three `@ts-expect-error` were recorded as the brand's proof. **Two were.**
  The third passed a `libraryId`, which is `string | undefined`, so it was
  satisfied by the optionality rather than by the brand. Seven now, all seven
  load-bearing.

## What is now reachable that was not

The fixture is the only provider W3 can drive, so a state it cannot produce is a
state W3 cannot build against. Three were missing:

- **Signed out.** Everything but `configure`, `authorize`, `supports` and
  `unsupportedReason` raises `NotAuthorizedError`. Previously
  `{ authorized: false }` served all 42 songs and a full search, and so did the
  device after `unauthorize()`.
- **Signed in but silent.** `{ canPlay: false }` refuses `play()` with
  `PlaybackNotPermittedError` and keeps browse, search, library and queue
  working — §14.3 row 3's browse-only refuse posture. Previously it played.
  The tier is deliberately *not* a capability: `supports("transport")` stays
  `true`, because a matrix answers for the service and is the same for every
  user, while the tier belongs to the session.
- **Save doing something.** `saveToggle` wrote a set nothing read, in this
  package or any other, so the library total was 42 before and after. It writes
  library membership now, because §14.3 row 24 makes Save and add-to-library one
  operation with two labels. Un-saving needs `libraryRemove`, which is `false`
  on Apple — so on an Apple-matrix fixture you can Save and cannot un-Save,
  which is the parity gap rather than a bug. My existing test proved Love ≠ Save
  and never asserted Save moves anything, which is how a no-op passed.

## The failure protocol, which was two protocols

The stubs threw **synchronously** from members declared `Promise<…>`; the
fixture rejected. So `provider.search(q).catch(handle)` worked against the
day-one runtime and crashed the caller against the launch provider. Every stub
test used `await` inside `try`, which is the one shape that handles both.
Every `Promise`-returning stub member is `async` now, and the suite asserts the
promise directly and asserts all three implementations agree.
