## The finding

**The owner's browser almost certainly does expose the API — and it is not the API
the packet was written against.**

Chrome 151 with the flag on exposes exactly:

| Where | Members |
|---|---|
| `HTMLCanvasElement.prototype` | `layoutSubtree`, `onpaint`, `captureElementImage`, `getElementTransform`, `requestPaint` |
| `OffscreenCanvas.prototype` | `getElementTransform` |
| `WebGL2RenderingContext.prototype` | `texElementImage2D` (arity **3**) |
| `CanvasRenderingContext2D.prototype` | `drawElementImage` (arity 3) |
| `window` | `ElementImage` |

Absent: `updateElementGeometry`, `clearElementGeometry`, `getCanvasTransform`,
`onelementgeometryupdate`, `texElementSubImage2D`, `PaintEvent`,
`ElementGeometryUpdateEvent`.

Established by exhaustive `Object.getOwnPropertyNames()` enumeration, not by
probing the list I happened to think of.

**Two consequences.**

1. **RISK-02 resolves in our favour.** `texElementImage2D` at arity 3 is exactly
   three.js's `// Chrome 150+` branch. `HTMLTexture` works unmodified. The
   standing instruction to route through `HTMLTexture` rather than call the raw
   entry point is validated rather than merely prudent — the README's own IDL name
   `texElementSubImage2D` does not exist in any shipping browser, so any code
   written from the explainer would have failed.

2. **The W6 packet's mandatory call does not exist.** The packet's "property that
   must not be lost" section makes `updateElementGeometry({ canvasTransform })`
   mandatory and calls it "the difference between the thesis holding and not". It
   is not implementable in Chrome 151. What ships is the previous generation:
   `getElementTransform(element, screenSpaceTransform)` returning a matrix you
   write to `element.style.transform`. The element then is genuinely transformed
   DOM, so hit-testing, focus, selection and a11y geometry are native — the same
   destination by a different road, and the road three.js's `InteractionManager`
   already takes.

   **This is a lead ruling, not my patch.** W6.2 needs respecifying against
   `getElementTransform`, and W6.4's a11y re-review is what should confirm the
   thesis holds rather than my reasoning above.

## What bit me

**A bug that only exists when the feature exists.** The first flag-on run rendered
`Something went wrong! Illegal invocation` and nothing else. Reading a member off
`HTMLCanvasElement.prototype` to get its arity *invokes* the IDL getter behind
`layoutSubtree` and `onpaint` with the prototype as `this`. With the flag off
those members do not exist, nothing is read, and the probe is perfectly green — so
no amount of testing without the flag would ever have found it.

A detection function that crashes precisely when the feature is present is worse
than no detection at all. `arityOf()` now walks the prototype chain with
`Object.getOwnPropertyDescriptor` and reads only `descriptor.value`, which never
triggers an accessor. Recorded in `decisions/w6.md` W6-D5 because it is the best
argument in this workstream for running things rather than reasoning about them.

**Chrome Canary is not required.** `chrome://flags/#canvas-draw-element` is the
Blink runtime feature `CanvasDrawElement`, and
`--enable-blink-features=CanvasDrawElement` turns it on in Chrome 151 **stable**.
That is how the T1 branch in this code came to have actually executed. The
reviewer can reproduce both states on stable.

## High-DPI and responsive repair

I reproduced the mobile capture at 390×844 in flagged Chrome. Before changing
materials, I separated three pipelines: CSS layout, canvas backing store, and
HTMLTexture source raster. The canvas had no source-correct physical-pixel
observer; the 272×204 active panel was being uploaded at logical density; and
an intrinsic canvas descendant could widen the composite boundary.

The repair now observes the physical box with a DPR fallback, lets R3F resize
the renderer, reruns the existing `getElementTransform` geometry sync, and
creates a matching 1×/2×/3× DOM source for Three's HTMLTexture. A first version
reassigned the source transform on every observer pass and hung flagged Chrome
in a mutation/paint loop. Making density application idempotent closed that
failure and is now part of the implementation contract.

The final native measurements are exact: at 330×552 CSS pixels the backing
stores are 330×552, 660×1104, and 990×1656; source rasters are 320×240,
640×480, and 960×720. All three runs report a 390px viewport and scroll width,
with equal 30px side margins and no route edit.
