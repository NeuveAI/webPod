# Explicit glass environment semantics — independent source investigation

The installed Three 0.185.1 source rules out the proposed extra scene-intensity multiplier for the explicit glass PMREM. It does not establish equal generated PMREM texels or identify the visual gap's cause. This was a bounded read-only inspection; no renderer settings or application source were changed.

All Three paths below are relative to `node_modules/.bun/three@0.185.1/node_modules/three/src/`.

The live application supplies the explicit map through `physical-material-nodes.ts:73` and retains stock physical environment lighting through its custom lighting subclass. GL `StudioEnvironment.tsx:83–88` and native `render-backend-services.ts` both generate the body and separate screen maps from `createProductStudioEnvironment`, with the screen flag true for glass. Their generation implementations remain different renderer code paths. Matching settings and formulas cannot certify their sampled radiance, convolution, floating-point results or final physical lighting output.

Conclusion: do not compensate by multiplying/dividing glass intensity by .2 or removing the Node generator's Y correction on this evidence. No source-bound mismatch was found in these specific intensity, rotation, storage, tone-map-selection or roughness-selection semantics. The before-glass sampler's constant GL grid remains a separate unresolved diagnostic equivalence issue; its flat-field equality alone does not prove that all remaining differences arise in glass.

## Confirmed screen-output semantic mismatch

A separate, concrete mismatch exists after scene rendering. Installed `materials/Material.js:449–452` explicitly documents that `toneMapped` is ignored by WebGPURenderer. GL `renderers/webgl/WebGLPrograms.js:178` honors the flag when selecting a screen material's tone mapping; native `MeshBasicNodeMaterial({toneMapped:false})` does not receive that exemption from the renderer's final output pass.

The native call chain is explicit: `renderers/common/Renderer.js:1426` allocates an intermediate framebuffer when tone mapping or output color conversion is needed; scene materials render into it, then :1778 calls `_renderOutput`. At :1813 that method renders a full-target quad. `renderers/common/nodes/NodeManager.js:904` builds `texture(outputTarget, screenUV).renderOutput(renderer.toneMapping, renderer.currentColorSpace)`. `nodes/display/RenderOutputNode.js:123–132` applies the selected tone mapper followed by color-space conversion. The full-scene texture has no per-material LCD exemption. This is consistent with a linear offscreen background match but darker native screen output under global AgX; it does not numerically prove the screenshot's particular gray value or replace live mask-generation verification.

A quality-preserving correction must restore authored per-material tone-mapping eligibility: LCD stays exempt, physical surfaces retain AgX/exposure. Supported node authoring seams include `NodeMaterial.setupOutput` (:1184), `outputNode` (:545), and TSL `toneMapping`/`renderOutput`. These allow explicit output policies, but simply adding per-material AgX while disabling global tone mapping is **not yet an exact GL parity solution**. GL `ShaderLib/meshphysical.glsl.js:217–220` performs tone mapping, color conversion, fog and premultiplied-alpha processing before framebuffer blending; the native full-scene output pass converts after blending. Glass and other transparent materials therefore require an explicit matching output/target/composition ordering, alongside the per-material exemption. PMREM and other linear intermediate passes must remain unmapped, and final color encoding must happen exactly once.

Do not invert AgX or boost LCD brightness to compensate: that would conceal the renderer contract mismatch and may alter highlights/colors. A complete explicit output policy needs narrow implementation ownership, installed-source review and actual glass-on visual validation. No application changes, browser actions or new rendering experiment were performed for this finding.

## Independent proposal constraints (before implementation)

The proposed explicit fragment-output architecture is feasible against the pinned APIs, subject to the following contract. This is design-fit feedback, not source or visual acceptance.

- Keep standard lighting/deformation outputs intact, then apply AgX only for materials whose authored toneMapped is true; apply sRGB encoding to all displayed RGB, including the exempt LCD. Perform this on straight RGB before the original setupOutput fog/premultiplied-alpha handling, matching GL ordering. Do not call RenderOutputNode on straight-alpha lighting: its :112–140 unpremultiply/repremultiply logic assumes a composed premultiplied input.
- The final canvas must receive those already encoded fragments without a second full-scene transform. Installed WebGPUBackend:353 configures a plain preferred unorm canvas format with the existing alpha policy; WebGPUUtils:252 selects that format. Renderer._getFrameBufferTarget:1426 skips its global conversion only when both tone mapping and output color conversion are disabled. Using nominal working-space output for an explicitly encoded unorm transport must be documented and validated as such; it is not evidence that stored values remain linear.
- Wrap owned final-scene materials locally, preserving the original method receiver and cache invalidation identity. No global prototype mutation. Cover chassis, LCD, all packet/equipped/carry resources and detached compile/warmup roots before compilation. Shared material reuse must not wrap twice. Current custom lighting/position hooks still enter setupOutput; any outputNode override that bypasses this result needs explicit handling or rejection, not silent acceptance. Fragment-node outputs also need their actual alpha contract checked.
- PMREM room materials and linear intermediate computations remain unwrapped. Exclusion must follow explicit owner/purpose, not merely the render target present during an initial compile. Clear colors and scene backgrounds bypass ordinary material wrappers and require their own exact output policy; transparent zero clear is simple, arbitrary nonzero clear is not automatically covered.

Minimum acceptance evidence for this correction: identical opaque RGB output covering dark/light LCD backgrounds and highlight colors plus physical HDR inputs under AgX; exact ordered transparent glass-over-LCD and a second alpha layer with premultiplied-alpha/MSAA behavior; unchanged linear intermediate/PMREM output policy; coverage/lifecycle proof for current and later compiled material owners; and actual glass-on matched front screenshots in both colorways. An opaque-only white sample is insufficient to approve the composition policy. The lead retains full activation and live acceptance gates.
