In particular, **205 ms cannot be assigned to a specific component, geometry operation, or library list from this evidence**. The GL `StickerPackScene` / `PeelingPrint` React geometry path is not mounted as the rendering path when the native backend is effective. It must not be blamed for the native scheduler task. Similarly, `stickerCollectionsAtom` depends on inventory, not every peel pose (`sticker-collections-model.ts:49`); the 2,726-song library count does not demonstrate a song-list rebuild on pickup. `ProductionPanelView` is memoized. No observed stack connects that library to the measured task.

## What the broker callback actually does

`packages/device/src/sticker-transaction-broker.ts:101–117` distinguishes delivery acknowledgement from canonical computation result. A delivery acknowledgement resolves its promise. A canonical result calls `complete` (line 86), which stores exact buffers, resolves waiters, and **synchronously calls `pump`**. Pump can evict/admit the next job and call `Worker.postMessage` before the original callback returns (lines 120–148).

Thus the 30.3 ms may include result bookkeeping, bounded admission/eviction scans, and next-job structured cloning. The source does not reveal which branch/job the observed event used. Accounting enumerates buffer identities and byte lengths, not pixel values; it does not recompute damage fields. Repeated `storageCharge` calls inside eviction/admission are avoidable repeated metadata work in principle, but the collection is bounded and their contribution has not been timed.

For carry prints, `sticker-prepared-damage.ts:35–85` obtains cached artwork alpha, requests damage then exact contour computation from the same producer, and creates borrowed BufferAttribute/DataTexture wrappers. The main does not copy dense geometry in `borrowGeometry`. Contours referencing a live canonical damage entry avoid cloning the field; carry positions/UV may still need an independent structured clone when no canonical surface ID exists. That clone preserves ownership and is a plausible dispatch cost, not proof of the measured 30.3 ms. Moving full damage/contour mathematics is not a justified next change: they already execute in the worker on the healthy path.

### Exact synchronous carry initialization boundary

`native-carry-controller.ts` update → request → `createCarryPreparation.request` → `dispatch` remains synchronous until the first actual carry is posted. The request carries a small scalar/artwork-metadata descriptor; its JSON keys contain no artwork pixels. The first dispatch creates the sole carry Worker and initializes its immutable assembly context (`sticker-carry-preparation.ts:83–121`).

That initialization invokes `transferPaperGeometry(rear)` (`sticker-paper-transfer.ts:24–30`), which uses `Float32Array.from` for positions/normals/UV and `Uint32Array.from` for indices. It then posts the resulting context without a transfer list. The newly allocated rear arrays therefore undergo another structured clone, alongside a structured clone of the borrowed packed collision snapshot. Snapshot itself is a borrowed reference (`sticker-collision.ts:95–98`), not a recomputation. Copying/cloning the complete assembly context occurs inside the measured carry span before the normal scalar pose message. The capture does not split 73 ms into Worker construction, explicit copies, clone, recipe/query admission, or serialization; assigning all 73 ms to a single instruction would overstate the measurement. The dense double-copy operation is nevertheless directly established by source and is not required semantic UI work.

No deformation, damage calculation, or collision-tree rebuild should be moved back to main. Existing first-source retention and latest-only carry pose behavior are already correct and must survive the fix.

### Minimal proposed corrective scope; not implemented

A claim that complete direct worker-to-worker carry context can be wired using existing unchanged APIs would therefore be false. Adding that path requires explicit broker lifetime/accounting scope, not simply requesting another full-device renderer lease and ignoring unused resources.

The least-churn feasible correction is bounded one-private-snapshot preparation inside the existing carry owner, followed by a single transfer of its owned buffers. Replace the current rear-copy-then-clone boundary with exact chunked private copies of rear attributes and packed collision arrays; transfer those private arrays once to the existing carry Worker. Borrowed public query buffers must remain attached. Schedule preparation when the already-admitted visibility assembly becomes available, but ensure a genuinely cold pointer request only publishes the latest scalar intent and schedules that work; it must never synchronously drain a copy or await context preparation in the input callback. Suggested narrow ownership: `sticker-carry-preparation.ts` for context job/generation/admission, a small adjacent private-context copy helper if needed, `native-carry-controller.ts` for proactive preparation from the existing visibility owner, and `sticker-carry-worker.ts` only if explicit context acceptance is needed. Preserve zero-argument GL behavior and renderer failure policy. The existing copy-on-serialization helper is shared by worker output paths: changing it globally to return borrowed arrays would be unsafe.

## Read-only proposal: prepare carry context when the packet starts opening

The `a822` production pickup remains a valid native placement, with short input handler time but delayed presentation (lead report: EventTiming184ms, handler6.3ms; LoAF72.7ms includes MessagePort26.2ms and timers15.4/8.1ms). These names alone do not prove that all remaining time belongs to carry context. The following proposal removes a known cold dependency from the pickup critical path; it is not a claim that the whole presentation delay is solved.

Current source boundary: `native-carry-controller.ts` calls `nativeCarryInput` before doing anything with the runtime. With no active peel/source/placement/drag, that helper returns null, so the controller never supplies rear/visibility to preparation. `sticker-carry-preparation.ts` dispatch likewise requires `wanted`; therefore the initial bounded private context copy, Worker construction and transferable init message all occur only after the first real carry request. The cooperative snapshot yields first; construction and `postMessage` happen after its promise resolves. The same Worker's FIFO ensures its scalar job follows init, but there is no context-installed acknowledgement.

Proposed minimal API: add `primeContext(rear, visibility)` to the existing `createCarryPreparation` owner. It selects the same exact rear/visibility/revision identity as `request`, starts only the existing bounded context-copy/install path, and never creates a `CarryInput`, increments a gesture/job sequence, emits a carry state/frame, begins a render lease, or prepares artwork/deformation. Factor context installation out of the `wanted`-dependent dispatch branch; both prime and real request use that one job and one Worker. Preserve initial yield on both paths. Real input arriving during priming replaces `wanted` normally and gets the first scalar job once that exact context is installed. No second producer, copy, cache or new preparation budget.

Trigger in `native-carry-controller.ts`: the first actual packet-opening transition (`scene.pack !== null`, `workspaceVisible !== false`, presence >0 and progress >0), before the current `nativeCarryInput` early return. Do not use `preparedSheet`, mere inventory warmup, or renderer ready at entry: those coincide with material/catalogue/packet preparation and would add contention before any sticker intent. The open action supplies lead time before liner reveal and pickup while the existing packet animation remains active. Existing `visibility.ready/revision` and `visibility.subscribe` supply exact collision readiness; call its registered-mutation-aware `update(query.content)` only when this opening eligibility or pending prime exists. If collision is not ready, remember eligibility and wait for that existing callback rather than polling. No host/worker protocol or app state change is needed.

Deduplicate by exact rear object + visibility owner + prepared revision, and keep the current installed context across packet closing (it already remains resident after carry). Do not re-prime on every pose/projection/pack callback. A changed assembly cancels the old copy before replacing its reservation; an installed obsolete worker retires before installing another. Document hide/unmount retires context exactly as today. Clear speculative eligibility on document hide; resume alone must not repeatedly prime an unchanged open packet. A new open transition can prime again, and a real pickup always retains the bounded cold path. An in-flight real request remains eligible for the existing resume dispatch policy. Cancellation keeps pending bytes charged until generator unwind. Avoid speculative retry loops: a prime failure follows a single recorded unavailable state; a real request must observe the existing native failure/fallback semantics, not reuse a half-installed worker.

Proposed ownership is only `sticker-carry-preparation.ts` (separate context admission from pose dispatch) and `native-carry-controller.ts` (one packet-open eligibility latch). The existing context helper remains unchanged unless a concrete lifecycle need appears. No `device-native-input.ts`, material, visibility producer or main animation edits.
