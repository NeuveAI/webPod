# Rotation rendering diagnosis

Read-only source audit of the current local branch, Three0.185.1 and Fiber9.7.0. No new browser timing was collected in this lane; the lead's recording is the source for measured frame attribution. Earlier production recordings do not establish current branch costs. Geometry/effects/DPR/lighting remain unchanged.

## Existing GPU path and lifetime

`packages/device/src/DeviceCanvas.tsx:168` creates a demand-mode Canvas, antialiasing, alpha and DPR[1,3]. Installed Fiber `dist/events-*.esm.js:15736` creates `THREE.WebGLRenderer` when supplied configuration is not a custom renderer. This already uses the GPU for vertex transforms, rasterization, lighting, physical materials, reflections, glass and sticker wear. The renderer uses WebGL2; it is not software geometry rasterization on the JS thread. [Official WebGLRenderer docs](https://threejs.org/docs/pages/WebGLRenderer.html).

Fiber's `events-*.esm.js:16171` calls renderer.render after useFrame subscribers; `:16221` coalesces ordinary invalidations into one requested frame. The extra invalidate inside a running frame requests another frame. Demand mode stops after work settles; seeing a cancelled trailing RAF is normal, not proof of an animation bug.

`StudioEnvironment.tsx:82` builds two fixed product-studio PMREMs (body and separate screen environment), installs them once per renderer/scene/sigma/intensity identity, then cleans up both targets, generator and rooms. Orientation is absent from its dependency list (`:170`); normal rotation does not regenerate these environments. `Device.tsx:255` keys optional room texture construction by serialized room values. Finish/noise/anisotropy maps are useMemo-owned (`:266` onward). CPU map generation is startup work, not an established steady-rotation bottleneck.

`DeviceRenderWarmup.tsx:14` waits one RAF for sibling effects, calls compileAsync on the full scene, gathers material-owned textures, initializes them, then requests three useFrame callbacks. The third callback signals ready after two complete renderer.render calls because Fiber invokes subscribers before drawing. `apps/web/src/device-reveal.ts:92` waits for that signal and the1450ms minimum prelude. It has a10second escape hatch, not a guarantee the driver has completed every future operation.

Three's compileAsync starts with synchronous compile/material traversal (`WebGLRenderer.js:1487`) and polls program readiness every10ms. KHR_parallel_shader_compile reduces driver synchronization but does not move scene traversal, shader source generation or JS work off-thread. Built-in compileAsync has no cancellation handle; the component's disposed flag suppresses later publication, not the internal poll. The application's separate sticker preparation helper (`sticker-program-preparation.ts:40`) has abortable polling and retained cloned material ownership. [Official compileAsync contract](https://threejs.org/docs/pages/WebGLRenderer.html#compileAsync).

HTML LCD pixels are a separate path: `packages/composite/src/html-in-canvas.ts:92` creates HTMLTexture, sets sRGB and disables mipmaps. Mutation/resize changes coalesce layout fit and requestPaint into one RAF (`:145`); paint events dirty the texture. Normal device rotation should change the proxy transform, not rebuild the DOM pixel source. Whether parent subscriptions nevertheless cause LCD paints is a browser/motion-lane measurement question.

## Findings and falsified assumptions

1. **Concrete unnecessary startup shader preparation:** StudioEnvironment calls `compileEquirectangularShader()` at85, but uses only `fromScene()` at86/89. Installed PMREMGenerator.fromScene at109 renders its room/cube and blur pipeline; compileEquirectangularShader at194 prepares a distinct equirect conversion material. Removing that explicit unused warmup would preserve both PMREM outputs. Expected savings are one unnecessary material-program preparation, not a measured frame-time improvement. This does not explain sustained rotation jank.
2. **Warmup limits:** scene compile traverses hidden meshes (`WebGLRenderer.js:1437`), whereas render traversal exits invisible subtrees (`:1833`). Thus hidden packet geometry/material additions made after the warm snapshot are not covered by two earlier draws. Worker paper can also arrive later. Measure the first rear packet reveal separately from initial device entry; don't label all late uploads shader compilation.
3. **First-front transmission hypothesis rejected as a default explanation:** cover glass remains a visible mesh (`Device.tsx:922`) in the same scene while the model faces rearward. Three builds the transmissive render list before raster backface culling (`WebGLRenderer.js:1885`), and renderTransmissionPass (`:1973`) allocates its camera target regardless of whether those faces contribute pixels. Rear warm renders should therefore exercise that target already. Only trace evidence of a late size/material/visibility change would revive this hypothesis.
4. **Full-resolution glass carries real multipass work:** transmission renders opaque objects into a multisampled target, resolves it and generates mipmaps (`WebGLRenderer.js:1987–2048`), then draws the main lists. The app deliberately keeps transmissionResolutionScale1 (`renderer-defaults.ts:9`). Reducing it, DPR, samples or material effects is outside the owner's quality constraint. GPU timing is required before attributing jank to this pass.
5. **No proven PMREM leak/rebuild loop:** map and room cleanup exists and relevant dependencies are stable across orientation. Caching should target actual repeated mounts or scalar setting changes if traces establish them, not replace authored reflections with cheaper lighting.

## WebGPU compatibility, grounded in installed sources

The r185 official manual explicitly requires custom GLSL/onBeforeCompile materials to be ported to node materials/TSL and notes that some scene configurations still perform better with WebGLRenderer. WebGPURenderer can fall back to a WebGL2 backend, which is still GPU rendering, not CPU recovery. Its asynchronous initialization must finish before Fiber's render loop. Fiber9.7 supports an awaited renderer factory (`events-*.esm.js:15732`), so bootstrap is feasible. [Pinned official migration manual](https://raw.githubusercontent.com/mrdoob/three.js/r185/manual/en/webgpurenderer.html).

**HTMLTexture is not categorically unsupported.** Installed `renderers/webgpu/utils/WebGPUTextureUtils.js:659` implements it with `GPUQueue.copyElementImageToTexture`, both supported experimental signature branches, and a first-paint request. It returns without copying when that method is unavailable. The current capability probe (`packages/composite/src/capabilities.ts:381`) checks WebGL texElementImage2D on a WebGL context, so navigator.gpu alone cannot authorize this path. A WebGPU tier needs separate adapter/device plus experimental DOM-copy and paint capability validation, then pixel verification; retain the existing working WebGL tier on failure. Texture paint update behavior is documented in [HTMLTexture docs](https://threejs.org/docs/pages/HTMLTexture.html).

Specific migration work, preserving current quality:

- LCD decoding uses a WebGL RGBA8-specific ShaderChunk patch (`html-in-canvas.ts:410`). Port its color-management contract to TSL and verify actual WebGPU upload format before applying a decode; blindly retaining the old extra decode can change LCD colors.
- Polycarbonate subsurface/direct RectArea transport and screen reflection-card modifications use onBeforeCompile (`physical-materials.ts:36,117`). Both need equivalent node/lighting implementations; using the unmodified stock material would drop visible effects.
- Sticker locked/placed appearance and procedural wear/damage modify shader chunks (`StickerSurface.ts:60`, `sticker-wear.ts:12,71`). Port all variants and damage sampling, not just base MeshPhysicalMaterial.
- StudioEnvironment imports the WebGL PMREMGenerator from `three`; the WebGPU entry exports a different generator (`Three.WebGPU.js:13`). Replace initialization/API ownership appropriately and compare both authored environments. Existing WebGL PMREM internally uses ShaderMaterial/WebGLRenderTarget.
- Sticker readiness accesses renderer.properties/currentProgram/isReady and pins revision185. WebGPURenderer has a different pipeline readiness model, so this helper cannot be reused by type casting. Rebuild cancellation/lifetime readiness around its supported async compile path.
- CPU projection uses Three camera projection conventions and exact displayed geometry; test backend coordinate-system/depth assumptions and all editor probes. Browser readback/capture probes built on WebGL contexts require corresponding GPU validation.

A measured GPU-first experiment on visual paper can deliver useful work without the all-or-nothing migration. A full WebGPU prototype is justified if it establishes the complete LCD+material capability path and compares CPU submission, GPU pass time, memory and entry latency at identical output settings. No source evidence here establishes that WebGPU alone makes this scene faster.

## Implemented GPU paper and warmup cleanup

`sticker-paper-gpu.ts` now supplies the full96-segment static grid and identical perimeter triangles. The material patch replaces only position/normal inputs; ink, bump/roughness maps, clearcoat, studio environment, sides, opacity and UVs retain the CPU branch values. Vertex normals sum the same adjoining indexed triangles, including grid boundaries. Backing positions offset along those normals; edge normals use each actual front/back triangle, not a smooth approximation. The half-angle identity avoids cancellation in tiny curls. Curl changes a uniform, never rebuilds or uploads vertex arrays.

`sticker-paper-gpu-support.ts` shares one capability/program-link gate per renderer. Unsupported precision, driver-link failure, timeout or context loss keeps/returns the component to the existing worker/cooperative CPU branch. Its shaders and readiness timer are released; restoration reprobes. Pending readiness also uses the existing CPU path. This is an ordinary WebGL vertex shader GPU preference; no WebGPU migration or new browser dependency was added.

The CPU readback audit found a real consumer: return motion calculates Box3 of the paper workspace. Static shader positions alone would give wrong bounds. `sampleGpuPaperBounds` mirrors only perimeter points and their triangle adjacency, lazily when that existing Box3 consumer asks. Curl invalidates the cached box; no dense CPU mesh or GPU readback is needed. A1512-box comparison across72dimension/liner combinations and7curl values matches the full CPU reference boxes exactly. Frustum spheres use a separate conservative all-curl envelope; they do not determine return motion.

The isolated numerical WebGL experiment recorded an AppleM4Pro ANGLE Metal renderer,36front/back/edge comparisons across both liners and6curl values. After the stable half-angle calculation, maximum component differences were0.000030517578125 world units for positions and0.00003178417682647705 for normals. These are floating-point tolerances, not bit-identical GPU math. Full detail, triangle topology and authored material inputs are unchanged. This bounds geometric/shading-input error; it is not a screenshot comparison or measured frame-time improvement.
