# Decisions

- The artist album screen now starts with All. Its fallback preserves the displayed album order and each album's track order. Playlist duplicate occurrences remain intact. No provider identity branching was added to navigation.
- Neither current provider offers a complete artist-song relationship in the same library/catalog scope. Apple's artist views include top-songs, not complete songs; Spotify exposes artist top tracks, not complete songs. Neither adapter advertises `artistTracksPage`. The optional future-provider contract is exercised with a real30-entry mock; it is never substituted with popularity results.
- Sources: [Apple library artist relationships](https://developer.apple.com/documentation/applemusicapi/libraryartists/relationships-data.dictionary), [Apple artist relationships](https://developer.apple.com/documentation/applemusicapi/artists/relationships-data.dictionary), [Apple artist views](https://developer.apple.com/documentation/applemusicapi/artists/views-data.dictionary), [Spotify artist albums](https://developer.spotify.com/documentation/web-api/reference/get-an-artists-albums), [Spotify album tracks](https://developer.spotify.com/documentation/web-api/reference/get-an-albums-tracks), [Spotify playlist items](https://developer.spotify.com/documentation/web-api/reference/get-playlists-items). Research was independently provided by the lead/researcher. Artist album/single scope follows the existing displayed discography, excluding appearances as before.
- Optional paged methods extend the canonical MusicProvider/Page/Cursor contract. Legacy in-memory sources keep their complete-array compatibility path. Apple chooses library or catalog relationships from the existing ref identity. Spotify limits artist albums to10 and track relationships to50. Both normalize responses through existing validators. Apple bare MusicKit arrays require offset/fingerprint continuation; a full5-entry page is not completion. Cursors are opaque, entity/relation/session scoped and bounded to512 handles per adapter. Signals fence late MusicKit publication; Spotify passes composed abort signals and request priority through fetch.
- Warmup loads the first15 artist albums, then5 tracks from each first5 albums in display order, then enough ordered data for an actual15-track All prefix. A later album's sample never fills a missing middle of an earlier album. Following the user correction, root library boot requests 15 entries per collection and continuously hydrates all root collections one background page per collection per round. Continuation uses native batches (Apple 100; Spotify 50), yielding between requests. Foreground navigation shares any pending page and can continue its own collection independently. Fifteen is the first-render target, never a current-page cap. Neighbor scope is selected row and immediate preceding/following row, clipped at boundaries. Only selected playback targets reach provider.prepare.
- Existing BoundedAsyncCache was LRU, not LFU. Its implementation now lives in music-management and is reexported at the old panel path, retaining artwork/intent callers. LFU frequency determines eviction with recency tie-breaking. Relationship retention now has configurable estimated byte budgets: 48 MiB tracks plus 16 MiB albums by default, a 512-entry ceiling per type, and a 5-minute idle TTL. This 64 MiB total is an engineering default for evictable metadata, not a browser guarantee or a whole-process heap cap. Mutable progress, completion cursor, error posture and in-flight work share each LFU entry. Active relationship owners are pinned during pagination, so their child entries and TTL pruning cannot evict them. Source teardown still aborts relationship entries. Active accepted results can temporarily exceed retention while owned; oversized entries are dropped on release without dropping their returned data. All retains request-local child completion and only the current child result while slicing it, so eviction cannot become false incompletion or a repeated-fetch loop. No parallel unbounded artist relationship map remains.
- Warm prefixes render synchronously on navigation and refresh while remaining entries load. Selection and scroll offsets survive final replacement. Failures retain visible prefixes and offer Menu/retry copy; speculative failures do not trigger rejected-promise loops. Reentry retries only missing pages. Playback starts the selected visible queue synchronously and musicManager.playProgressive appends its continuation with manager-owned selection/queue guards; suffix failure cannot prevent a known playable prefix starting. The separately assigned playback investigator owns that manager code and evidence.
- The prescribed reference directory and legacy agent-context global/Jotai guide paths are absent. Skills were loaded from their installed locations; modern-web-guidance was run with bunx (repo bun-only rule overrides the skill's npx examples), retrieving its background-fetch priority guidance. A relocated source tree at /Users/vinicius/code/agentic-context was identified by research. No new external libraries or React state primitives were required; existing provider types/Jotai store/React lifecycle patterns were retained.

- Rendered album identity is independent of LFU residency. The source accepts an exact AlbumRef from the rendered artist/album frame, and nested track frames retain that ref for playback continuation. Retiring a cached discography cannot turn an on-screen album into a false empty result; stale key-only lookup reports expiry. No additional ref registry was introduced.

## Reopened live failure and cache assessment

The prior closure was invalidated by the user's AC/DC failure and root-count screenshots. Live DevTools proved the artist request was HTTP 200 with eight library albums and no continuation; the empty Back In Black resource legitimately omitted `artistName`. Strict normalization threw before publishing any of the eight. Normalization now uses the known parent artist name when that album field is absent, preserving all eight items and their order. No origin or cursor guard was relaxed. The regression fixture derives from that actual response, preserving the missing field and zero track count while removing unrelated personal addition timestamps and artwork URLs.

Root hydration now continues without visiting each category. Failed background collections stop rather than spin; accepted reentry retries the last committed cursor. Apple library cursor consumption moved after validated success, so transient I/O failure cannot permanently invalidate a saved continuation. Current-source guards stop background publication and further requests after account replacement.

The original count-only LFU was too small and did not account for entry size. The new byte estimator runs once on incoming page metadata, including nested artwork descriptors, and accounts page growth/replacements and eviction; snapshot reads do not serialize data. Entity references are reused across flattened arrays. Root inventory arrays, visible/back-stack frames, playback queues, provider identity maps, and decoded/streaming media are separate owners outside this evictable-retention budget. No metadata database or media cache was introduced.

A 1 GiB disk-cache target would be distinct from a 1 GiB JavaScript heap allowance. Browser storage quotas are per-origin, browser-specific and subject to eviction, and `navigator.storage.estimate()` reports an approximate storage estimate rather than a safe heap budget. See [MDN storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) and [StorageManager.estimate](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate). The user requested best-practice budgeting, so the lead scoped a configurable 64 MiB metadata-retention default rather than preallocating 1 GiB or introducing persistence.
