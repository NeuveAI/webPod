# Decision log — S1 · Apple Music capability spike

Judgment calls made while producing `evidence/apple-capability-spike.md`. Per the dispatch's "proceed but log" rule: any call between contradictory sources, and any call about a confidence label that a reviewer could reasonably disagree with.

---

## D1 — Labelling a *negative* finding `VERIFIED-docs` when Apple never states the negative

**The tension.** §14.0 defines `VERIFIED-docs` as "Apple's published docs state it plainly." Apple nowhere writes "you cannot remove a track from a library playlist." What Apple publishes is a *complete endpoint index* in which no such endpoint appears.

**Decision.** `VERIFIED-docs`, with the evidentiary shape written out at the top of the deliverable and again at each affected row, so no reader mistakes it for a quoted denial.

**Reasoning.** The Apple Music API reference is an exhaustive enumeration of a closed surface, not prose. For a REST API, "the documented endpoint set is exactly these three, and the section is titled *Creating and Modifying User Playlists*" is as plain a statement as the medium produces. Downgrading to `LIKELY` would imply the doc set might be incomplete, which would make every negative in the whole capability table permanently unresolvable and would let a future reader think a hidden `DELETE` might be found — which is worse than the small overreach, and is itself a form of inflation in the other direction.

**Applies to:** rows 10, 11, 18 (documented surface), 21a, 30, and the bonus row 7.

**How to falsify me:** find any Apple-published endpoint, in any version of the Apple Music API reference, that removes or repositions a library-playlist track. I enumerated `playlists-api`, `songs-api`, `albums-api`, `artists-api`, `music-videos-api`, `apple-music-stations`, `search`, `ratings-api`, `recommendations`, `history` and the top-level index; the only `DELETE` verbs in the entire API are the ten ratings deletions.

## D2 — Contradiction: Apple staff say removal IS supported (Jun 2022), the docs say no endpoint exists

**The two sources.**
- Apple staff, forums thread 707759, Jun 2022: *"Editing playlists does support removing tracks from a playlist."*
- Apple Music API reference: no removal endpoint.

**Decision.** Not a contradiction — a scope mismatch, resolved in favour of both. The staff reply is about **Swift MusicKit's `MusicLibrary.edit(_:…items:)`**, which is a different framework from the Apple Music REST API, and the same reply says so: *"this functionality is currently only available on Apple platforms."* I verified independently against the docs: `MusicLibrary.edit(_:name:description:authorDisplayName:items:)` lists availability **iOS 16 / iPadOS 16 / tvOS 16 / visionOS 1 / watchOS 9** and no web target.

**Why it does not rescue row 10 even in principle.** The same engineer's follow-up adds a second lock: *"You cannot edit playlists created via Apple Music API."* So even a native shim could not edit the playlists webPod would create. Two independent blocks: wrong platform, wrong provenance.

**Recorded because** a future reader who finds thread 707759 before finding this document will think row 10 was answered wrongly. It was not; the reply is about a framework webPod cannot run.

## D3 — Undocumented `Queue.splice()` found in Apple's shipped `musickit.js` v3

**The tension.** The published v3 reference documents the `Queue` class as seven properties and zero methods. Apple's own shipped runtime contains `splice`, `append`, `updateItems`, `removeQueueItems`, `clearAfterCurrent`, `clear`, and a `remove` that fires `deprecationWarning("remove", …)`. Apple's code contradicts Apple's docs.

**Decision.** Row 18 headline stays `VERIFIED-docs` **not supported**; the runtime methods are recorded as a separate `LIKELY` sub-finding; `supports("queueRemove")` and `supports("queueReorder")` are **`false`**.

**Reasoning.** Three independent reasons, any one sufficient:
1. §14.4 rule 1 — *"Never invent parity"* — an undocumented method is not a capability the provider offers us.
2. Apple's own code deprecates `remove`, so even the undocumented path is being withdrawn.
3. There is no `reorder`/`move` method at all, documented or otherwise, so `queueReorder` would be an emulation on top of an undocumented primitive — two layers of unsupported.

**Not taken, deliberately:** I did not propose a runtime feature-probe (`typeof queue.splice === "function"`) as a way to flip `supports()` to `true`. That is a real option and might be worth it for S17's swipe-to-remove, but it is a product/risk decision about shipping on undocumented API, and this spike's job is to report, not to choose. **Flagged to the lead.**

## D4 — Row 20 held at `LIKELY` rather than upgraded to `VERIFIED-docs`

**The tempting upgrade.** Both halves of the path are documented plainly: `Songs` has a `station` relationship, and `setQueue({station: 'ra.…'})` is a documented playback call with a code sample. It would be easy to call row 20 supported.

**Decision.** `LIKELY`, and `supports("stationSeedFromTrack") = false`.

**Reasoning.** The question in §14.3 row 20 is not "can I play a station associated with a song" — it is "is there an API for a station **seeded from** a specific track." Apple's total documentation of the relationship is *"The station associated with the song."* An "associated" station could be the artist's station or a genre station; the identical relationship name `station` also exists on `Artists`, which is a live reason to doubt. Upgrading would be inflating an unstated semantic into a stated one, which is 001 §15.3 failure mode 14.

**What I recorded instead:** the exact single call that settles it — `GET /v1/catalog/us/songs/{id}/station` with a signed developer token only (no music-user-token; it is catalog data) — run over three songs by three artists, comparing returned `ra.*` ids and `attributes.name`. Cheap, and it is the first thing to spend a developer token on once H-2 clears.

## D5 — 001 §14.3 row 21 asserts a lyrics endpoint "exists"; I could not find it

**The tension.** §14.3 row 21 says *"`/v1/catalog/{sf}/songs/{id}/lyrics` — **UNVERIFIED**: exists, but third-party display entitlement and time-sync availability must be confirmed."* That framing treats existence as settled and only the entitlement as open.

**Decision.** **Existence is not settled — it is documented as absent.** I corrected the premise rather than answering the narrower question 001 asked. "lyric" appears nowhere in the Apple Music API reference except the `hasLyrics` boolean, nowhere in the MusicKit v3 web reference, and nowhere in the Apple Music Feed reference.

**Reasoning.** Answering only the entitlement question would have carried 001's unverified premise forward as a fact — the precise failure mode the reviewer is told to hunt for. §14.3 was authored without primary-source access (§14.0 says so explicitly), so the premise was always provisional.

**Where the URL comes from:** third-party private-API projects — `rryam/MusanovaKit`, `binimum/apple-music-web-components` — both self-described as targeting private endpoints. Named in the deliverable, labelled `LIKELY` at best, and marked unusable. Per the dispatch, blog/repo/SO sources are named and capped at `LIKELY`.

**Sub-questions:** entitlement and time-sync are both left `UNVERIFIED`, and for the entitlement I recorded that **no API call can settle it** — it is a licensing question needing a written answer from Apple. Saying "call this endpoint to find out" there would have been a fake action item.

## D6 — Reading Apple's minified `musickit.js` at all

**The tension.** The dispatch says docs-only and forbids authenticated API calls. Is downloading and grepping Apple's published `musickit.js` bundle within scope?

**Decision.** Yes, and it is separately labelled. Fetching a public static asset over anonymous HTTPS is not an API call, needs no token, and creates no account — it violates neither H-2 nor any guardrail. But it is **implementation, not documentation**, so nothing derived from it carries a `VERIFIED-docs` label. Every finding from the bundle (D3's queue methods; the `offline: () => false` metrics field in row 30; the lyric-telemetry identifiers in row 21) is marked `LIKELY` and its provenance stated inline.

## D7 — `offline` is not a member of the §14.2 `Capability` union

**Observation, not a decision I was entitled to make.** Row 30 has no `supports()` key to be `false` in, because `"offline"` does not exist in the `Capability` union in 001 §14.2.

**Decision.** Flag it in the deliverable's closing notes and take no action. Adding a union member is an edit to a 001 document, which the guardrails forbid, and choosing between "add the capability, set it false" and "offline is out of scope product-wide, never a capability" is a PM call. **Escalated to the lead, unresolved.**

## D8 — Reporting a scope-relevant finding outside the six assigned rows

**What happened.** The evidence that settles rows 10 and 11 also settles §14.3 **row 7** (library remove on Apple), which was labelled `LIKELY` and is now `VERIFIED-docs`. Row 7 was not assigned to me.

**Decision.** Report it in a clearly-marked "Bonus finding (outside the six rows)" section; do **not** edit 001, and do **not** silently fold it into the six. Row 7's §14.3 posture — (c) hide on Apple — is unchanged by the upgrade; only its confidence improves, which lets it be built without a caveat.
