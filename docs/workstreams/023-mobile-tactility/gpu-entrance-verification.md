# Entrance execution and verification boundary

Source-grounded CPU016 note, 2026-09-11. This is an execution inventory and proposed verification, not self-review approval or a browser result. Owning source references: gpu-pose-coordination-plan.md and gpu-worker-scope.md dispatch F / recorded reveal decision (line115). No application code or browser state changed for this note.

## What the current implementation guarantees

The entrance is **main-clock coordinated, not autonomous under a main-thread stall**. This is the explicitly recorded scope decision, preserving the existing32ms-clamped trajectory while stage translation and portal opacity remain DOM-owned. Post-entry orientation/control programs are different: the worker advances their pure equations on its own RAF without projection-notification credit. Successful autonomous rotation is therefore not evidence of autonomous entrance.

`apps/web/src/device-reveal.ts:25` mounts the main owner. It waits for `data-wp-render-warm=ready`, then the remainder of the1450ms minimum warm interval. A preparing canvas is not skipped by the10s failed/no-canvas escape. This gate depends on preparation, native paint and complete compile/render readiness; its wall time must be measured separately from the reveal trajectory.

At `device-reveal.ts:54–75`, every main RAF computes the exact shared `deviceRevealFrame`, writes stage `--device-reveal-y` and parent `--device-reveal-glow`, publishes orientation/reveal intent, updates the preview store and schedules the next RAF. Logical elapsed increases by zero on the first frame and `min(now - previousFrame,32)` thereafter. The numerical equation is in `packages/device/src/device-reveal-motion.ts:1–28`: turn440, front1600, settled1900, hint2300/2720/2800, complete3460ms. These are logical times, not guaranteed wall-clock completion times. For example, a160ms main callback gap advances only32ms on the next callback;128ms is deliberately not caught up. This example follows directly from the equation, not a measured stall.

`device-page.tsx:485` consumes the translation as a CSS transform on the entire stage, including canvas and functional Panel. `styles/device-reveal-portal.css:83` consumes glow as portal opacity; the portal also retains its pre-existing independent CSS animation timelines for pool, edges, ripple and18 motes (`device-reveal-portal.tsx:14`). Their CSS transform/opacity declarations are suitable for compositor execution, but actual layer promotion/raster work is a trace question. Do not claim all portal motion uses the reveal logical clock: only the parent fade is driven by that clock, while decorative keyframes are started by the warming/entering selectors.

At1900 logical ms the stage state becomes complete and public reveal-active clears; orientation hint publication continues until3460ms. Reduced motion finishes at front immediately. Pointer/key interruption before settlement resets front; after settlement it retains the current pose. External/tool writes interrupt through the preview store. These remain correctness checkpoints, not opportunities to shorten or remove effects.

## Work and traffic on each side

| Owner | Actual current work |
| --- | --- |
| Main reveal owner | RAF/logical clamp, shared scalar curve, CSS custom property writes, public Jotai/preview notifications and lifecycle/readiness/input interruption |
| Main motion authority | `device-motion-authority.ts:52–68` publishes scoped intent, guards reentrancy, increments motion epoch and builds the model rotation matrix while preserving translation |
| Main native host | `device-render-host.ts` binding.sendPose applies immediate query pose and offers one latest pose; returning projections update exact query/Panel transforms and scalar subscribers. Layout measurement is a separate stable observer, not a reveal tick |
| Worker | `device-render-worker.ts:125–145` applies node matrices, traverses/render-submits the complete scene and offers bounded projection notification. `pose-update` at235 adopts the received main reveal pose; this live path does not start a worker reveal program |
| Browser compositor/raster | Applies stage/portal styles and CSS animations, composites the canvas/Panel, and services DOM screen paint/capture. Source alone does not quantify GPU or raster cost |
| GL fallback | `DeviceMotionBridge.tsx:13–29` subscribes to intent and mutates the single model root plus invalidation; the fallback renderer remains on main, unlike native worker rendering |

Normal `device-page.tsx:172–175` uses the appearance-only preview snapshot, so orientation does not intentionally rebuild the page/scene. DEV capture/diagnostic overrides intentionally select the full snapshot and must be absent in the representative trace. Narrow semantic consumers still run: collection front/rear admission, native query/input, and any active carry projection. Claiming zero main work would be incorrect. A pure tick's small code size also does not prove that downstream style, store subscribers or paint costs are small on the tested device.

`render-channels.ts:5–22` allows one in-flight pose plus one replaceable latest value. Main must receive pose-consumed to flush a pending value. During a blocked main thread it cannot compute new reveal samples, flush ACK-dependent outgoing samples, apply returning Panel/query projections or change CSS translation/glow. Worker rendering can still be triggered by independent animation/paint/resource work, but it cannot invent the next entrance pose. Repeated worker frames of the same reveal pose are not smooth entrance progress. Main CSS and worker pose publication share a logical sample, but cross-thread arrival/composition is not an atomic physical-presentation acknowledgment; visual pairing and resumed hit alignment remain measurements.

## Bounded correction proposal if entrance still stalls

First use the trace to remove any avoidable heavy subscriber/style/paint/preparation work on the main reveal path. That preserves the recorded clock semantics and needs only the concrete offending owner, not an animation rewrite. Keep readiness and all FX intact.

If an independent entrance is required, dispatch a separate renderer/presentation slice: make the existing shared reveal program the sole worker logical clock, advance the same per-worker-frame32ms clamp, and move the entire visible rise/portal presentation into that same renderer coordinate space. Derive the camera/model translation exactly from the original percentage stage translation, including clipping, viewport, screen projection and functional Panel hit geometry; port the existing portal gradients/mote timeline without dropping effects. Keep the real Panel/provider/main semantic authority and coalesced submitted query projection. Prove the associated DOM-screen capture/interaction remains valid when the visual stage no longer translates in CSS. This is substantial ownership across renderer, portal CSS, stage layout and native Panel—not a safe one-line enablement of the unused worker reveal variant.

There is a real constraint to resolve before implementing that proposal: exact prior wall-time behavior under a stalled main clock and autonomous progress through that same stall are mutually incompatible. Preserving the authored curve and32ms clamp on the worker clock preserves formula and phase order, but changes which frame timestamps advance it. The lead and separate reviewer must explicitly accept that clock-owner contract as the intended independence goal and verify visual equivalence at matched logical times. A wall-clock CSS animation, two independently advanced clocks, per-frame main ACK gating, reduced DPR or removed glow/motes are not equivalent corrections.
