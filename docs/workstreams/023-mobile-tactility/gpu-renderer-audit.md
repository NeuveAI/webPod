# GPU renderer and DOM screen execution map

Read-only architecture audit for WEBPOD-CPU-004. Read the full gpu-worker-scope.md. Resource catalogue searched first: no matching standalone Three/Fiber reference checkout exists there; installed Three0.185.1, @types/three0.185 and Fiber9.7 sources are authoritative. Modern guidance's interactive-content-in-3d-scenes guide was retrieved; it is useful orientation but its snippets do not override installed code or current browser IDL. No app edits, browser calls, builds, commits or performance claims in this audit. The draft PR context-loss obligation remains open independently of this architecture.

## Outcome

GPU rendering in a worker is technically feasible, including a proposed transferable native DOM snapshot path. It is not achieved by swapping the Canvas renderer constructor. Prefer a typed worker WebGPU backend only after all custom material ports and exact screen transport pass; retain the current WebGL appearance path until then. Worker WebGL is an intermediate/fallback GPU backend that can preserve existing GLSL patches. If the browser cannot transfer native panel snapshots, keep the working native DOM renderer on the main thread and move other heavy work off it; do not substitute an approximate rasterizer or blank LCD.

The current render loop already executes vertex transforms, lighting, transmission and paper curl on GPU. Main thread currently owns React/Fiber scene reconciliation, renderer submission, native DOM/layout/paint capture, event dispatch and projection. Worker rendering moves reconciliation and submission as well as resource construction; it does not move actual HTML layout, MusicKit/browser audio activation or accessible DOM into a worker.

## Native DOM transport: available path and real constraints

Current HTMLTexture owns an HTMLElement, reads its parent canvas and assigns onpaint. common/Textures.js sizes it through offsetWidth/offsetHeight; WebGPUTextureUtils calls renderer.domElement.requestPaint and queue.copyElementImageToTexture. InteractionManager reads clientWidth/clientHeight and element offset sizes and writes CSS transforms. None of those DOM operations can run unchanged in a worker. HTMLTexture's installed type is `Texture<HTMLElement>`; casting ElementImage to HTMLElement would hide both size and lifecycle bugs.

Current Chromium primary IDLs expose `ElementImage` to Window and Worker as Transferable, with width, height and close. HTMLCanvasElement exposes captureElementImage behind CanvasDrawElement, and GPUQueue currently declares both copyElementImageToTexture and drawElementImageToTexture. The copy source explicitly accepts Element or ElementImage. These are implementation-source facts, not proof that the user's exact browser enables every method. [ElementImage IDL](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/html/canvas/element_image.idl), [canvas IDL](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/html/canvas/html_canvas_element.idl), [GPUQueue IDL](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/webgpu/gpu_queue.idl), [copy source IDL](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/webgpu/gpu_copy_element_image_source.idl).

The WICG explainer specifies capture in the main canvas paint event, then transfer to a worker. It describes asynchronous OffscreenCanvas element-geometry updates and main-thread notification. Its newest GPU spelling is drawElementImageToTexture, whereas installed Three185 uses copyElementImageToTexture. Method presence/version and actual paint/transfer behavior must be tested independently. Keep one in-flight snapshot and at most one latest pending snapshot; close overwritten, rejected and consumed resources. Never clone DOM nodes through postMessage. [WICG proposal and worker example](https://raw.githubusercontent.com/WICG/html-in-canvas/main/README.md).

Transport branches after actual-browser validation:

1. **Detached staging canvas rejected on current Chrome.** The lead's five-argument probe successfully captured/transferred the existing panel but worker draw threw `InvalidStateError: The source was captured from a different canvas`. A new unattached OffscreenCanvas2D cannot rasterize a snapshot from the active device canvas. Do not implement that staging design as a supported fallback.

2. **Direct native snapshot texture upload.** Use an explicit ElementImage texture adapter with canonical width/height and backend-owned destination GPUTexture/WebGLTexture allocation. Current Chromium copy source supports ElementImage, but installed Three has no public ElementImage texture type. This needs a narrowly documented backend extension or coordinated dependency support, not arbitrary renderer internals patched from app code. This is the production candidate now that detached staging is rejected; prove allocation, format, upload, completion and disposal across both API signatures/backends.

If neither worker snapshot path passes, main-thread HTMLTexture remains the quality-preserving fallback. A CSS overlay loses glass/occlusion fidelity; html2canvas-like reconstruction does not establish identical text/layout output. Neither satisfies this task's quality constraint. Standard ImageBitmap transfer is useful for existing canvas/artwork pixels, but createImageBitmap(HTMLElement) is not a standard DOM rasterization solution. The HTML standard defines transferable OffscreenCanvas and its worker presentation model, not arbitrary DOM transfer. [HTML canvas standard](https://html.spec.whatwg.org/multipage/canvas.html#the-offscreencanvas-interface).

## Main/worker synchronization and lifecycle plan

Main owns Jotai/WebMCP/audio/clickwheel/haptics, pointer capture, real DOM layout, physical pixel observer and semantic panel state. Worker owns scene reconciliation/submission, geometry, textures, GPU deformation/shading, renderer warmup and one render scheduler. Commands carry stable object IDs, scalar settings, exact camera/viewport/density plus monotonically increasing renderer epoch, pose sequence and panel snapshot sequence. Geometry/assets transfer once per identity with bounded ownership; no full scene JSON per frame.

Native hit geometry must correspond to the displayed pose, not merely the latest requested one. Main can calculate small authoritative projection matrices while worker renders, but must associate updates with accepted/presented pose acknowledgments and reject old epochs; worker geometry APIs are asynchronous and need their completion event. A successful postMessage is not proof a frame was displayed. If direct transferred-canvas presentation cannot keep hit alignment within the existing exact contract, use a main presentation/pixel transport seam or retain main rendering for that capability tier. UI handlers and media activation remain immediate; never await worker scheduling before play/pause or pointer capture.

Start capability probing before taking the live canvas context. On worker init/renderer/transport failure, terminate that generation, close resources, create a fresh main canvas and reattach the existing DOM panel/state; do not attempt to undo transferControlToOffscreen. Hide/pause must cancel pending uploads/frames without losing the latest state. Restoration resets paint readiness for the new canvas/size generation and waits for a fresh native paint before first texture copy. This also addresses the existing stale-paint/context-loss obligation rather than silently layering over it.

Worker asset audit includes device/textures.ts and backplate-finish.ts (document-created canvas/text), sticker-alpha.ts (HTML image/2D readback) and sticker texture loading. Move procedural non-DOM maps to OffscreenCanvas or typed pixels without changing seeds; transfer main-produced native text artwork once if worker font parity cannot be proven. Preserve alpha extraction and damage semantics. Main-bound text/font rasterization is a documented browser/output constraint, not permission to keep unrelated preparation there.

## Implementation dispatch boundaries and gates

1. **Transport capability/typed adapter owner:** pixel-source/coordinator/capabilities and new message contract; test actual ElementImage capture/transfer/staging/direct upload/close and both API families on the existing Chrome. Establish first-paint, resize and context-reset generations before render migration.
2. **Renderer worker host owner:** worker createRoot+explicit size/DPR, init/compile/dispose/backend selection, event command routing and fresh-canvas fallback; no material simplification. Start with existing WebGL GLSL to separate worker-placement parity from shading migration.
3. **Material migration owner:** the six rows above, PMREM and readiness services. Use canonical node classes/functions and pair each variant with rendered parity evidence. WebGPU preference remains gated until every active variant is equivalent.
4. **UI/pose bridge owner:** coordinate with WEBPOD-CPU-005 for root subscription reduction, one latest pose and displayed-frame/native-hit synchronization. Keep keyboard, agent commands, release velocity and sticker gesture epochs intact.
5. **Independent acceptance:** exact geometry/bounds and deterministic lifecycle checks; real entrance, front/rear/edge rotation, clickwheel/LCD selection/focus, peel/carry/stick/wear, resize/zoom and playback; same currentChrome6× captures plus production comparison. Inspect CPU main/worker lanes and GPU timing separately. Select worker WebGPU when all capability/material/transport gates pass, worker WebGL when equivalent and available, otherwise current main WebGL with all feasible preparation off-thread. Report which gate prevented selection.

## Associated-canvas correction and next proof

Exact Chrome152 source resolves ElementImage ownership by its originating canvas node. GPUQueue::CopyElementImageToTextureInternal obtains that canvas's context via OffscreenCanvas::FromPlaceholderId in the same worker; without it, the copy reports no context. WebGL texElementImage2D likewise calls its own context GetElementImage, which enforces lineage. The production host must transfer the panel's associated HTMLCanvasElement before obtaining any context, then create the worker renderer on that same OffscreenCanvas. Existing live WebGL canvas cannot be retroactively transferred. [Exact152 GPU queue ownership](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.83/third_party/blink/renderer/modules/webgpu/gpu_queue.cc), [Exact152 WebGL copy](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.83/third_party/blink/renderer/modules/webgl/webgl_rendering_context_base.cc).

Supplied `/tmp/webpod-associated-webgpu-probe.js` for lead: transient native canvas/solid child on the existing route, transfer before context, real worker adapter/device initialization and associated WebGPU context, capture on main paint, ElementImage transfer and exact two-argument queue upload, one-row validation readback with expected pixel, explicit resource cleanup before result and10s outer timeout/removal. No live player canvas transfer. Success would prove only API transport and sampled color, not full LCD/material/interaction equivalence.

Independent reviewer also identified Fiber unmount does not call common WebGPU renderer.dispose: installed unmount waits500ms, handles renderLists/forceContextLoss/scene disposal. Worker host must explicitly own renderer/backend disposal after scene detachment, including delayed initialization, and await a dispose acknowledgment before normal worker termination. Forced timeout termination is the final resource/process boundary, never the normal renderer cleanup path.
