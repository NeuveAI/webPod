# Pinned Ammo memory/rebuild feasibility — 2026-09-07

Read-only assessment after the geometry engineer reported the fixed64MiB WASM artifact exhausting memory at step184; a128MiB supplied WebAssembly.Memory was rejected because the binary import fixes1024pages. This is an artifact/memory failure, not evidence against all soft-body runtimes. The unchanged150step partial recovery is separate geometry evidence and cannot pass the one-second probe.

**Preferred corrective architecture: a source-pinned WASM rebuild with three narrow SDF-cache operations and an explicit cell cap. It is not currently buildable with the discovered local toolchain without obtaining additional tooling.** No rebuild, engine execution, dependency installation, Docker pull or toolchain download was performed in this assessment.

Prerequisites for the proper build are therefore one digest-pinned Emscripten builder image/toolchain including CMake/Python, the exact Ammo source commit, and a small reviewed wrapper/IDL patch. Record the compiler version, image digest, all build flags, source/patch hashes and output JS/WASM hashes. Build only ammo-wasm. The cost includes obtaining that compiler environment, compiling the four Bullet libraries and binding glue, then repeating the capped diagnostic; there is no measured local download/build-time estimate. The wrapper is small; toolchain compatibility and full native-memory accounting are the meaningful costs.

## Source-backed bound and semantics

The pinned [btSparseSDF.h](https://github.com/kripken/ammo.js/blob/79190a1f03845794b1bba1777f30037349967658/bullet/src/BulletSoftBody/btSparseSDF.h) defaults to262144cells. Each btSparseSdf<3>::Cell contains64scalar distances plus coordinates, timestamp, hash and two pointers. With32bit float/pointer layout this is284bytes before allocator overhead: the default cell payload alone reaches71MiB. A32768cell cap reduces that payload to8.875MiB. Confirm sizeof(Cell) with the actual compiler; do not treat this ABI calculation as measured heap usage. The auto-reset allocation counter can be one cell behind after a reset, so budget at least cap+1 payloads and allocator overhead.

Reset deletes all cached cells, resets the counters and returns voxel size to.25. It retains the configured clamp. GarbageCollect(lifetime) removes cells old in logical GC-call generations; lifetime is not seconds or native simulation steps unless called once per step. It increments that generation after collection. Neither method is currently exposed by the pinned IDL. The cell cap is consulted during insertion and resets the cache when exceeded, so it bounds growth within a single step; periodic GC alone does not.

Expose exactly three checked helper operations on an explicitly supplied btSoftBodyWorldInfo reference: resetSdfCache; collectSdfCache with a nonnegative bounded generation lifetime; configureSdfCellLimit that first resets then assigns a validated positive cap no greater than32768 for this diagnostic. Keep voxel size unchanged at the source default. Do not expose raw fields, native addresses or template internals. Calling Initialize with a changed hash size is unnecessary; reset-before-configuration avoids altering hash-table storage with live chains. Invoke these operations only between synchronous world steps and reset before destroying collision shapes. They must not destroy the borrowed world info.

Start with cap32768 and collection lifetime2 called after each step, documenting these as cache-policy changes only. Recomputing evicted SDF values should preserve collision geometry within numerical tolerances; compare retained-cap versus frequent-reset trajectories before treating that as established. A cap can increase recomputation and produce spikes, so retain native/support timing and the existing CPU stop bound. Increasing the heap alone is not a cache lifecycle fix.

## A second allocation source prevents a whole-heap guarantee

The pinned [soft-concave collision implementation](https://github.com/kripken/ammo.js/blob/79190a1f03845794b1bba1777f30037349967658/bullet/src/BulletSoftBody/btSoftBodyConcaveCollisionAlgorithm.cpp) retains a convex child shape for every touched triangle in a per-callback shape cache. These are freed by clearCache/destruction, not by SDF reset. It extrudes each source triangle by.06modelunit in both normal directions and constructs a six-point hull. This is relevant both to contact clearance and the memory accounting. Clearing the SDF does not bound the entire native world; child-shape cache, shell BVH, soft-body constraints, clusters and allocator overhead still need measurement. Do not promise that32768SDFcells will necessarily fit the actual fixture in64MiB.

## Same-commit JavaScript fallback

The exact [builds/ammo.js](https://github.com/kripken/ammo.js/blob/79190a1f03845794b1bba1777f30037349967658/builds/ammo.js) exists (1,884,194bytes; read-only download SHA25682b1211f35886cd7268149028645f7c34f75028771a52da0a29bb279f7cb8337). It is the generated JavaScript fallback: its factory reads INITIAL_MEMORY and constructs an ArrayBuffer through its memory shim. Source inspection therefore supports passing128MiB at initialization without editing bytes or supplying a mismatched WASM import. This was not executed or benchmarked. It has the same missing SDF API and cache growth behavior, so a larger heap can postpone exhaustion and expose partial geometry but cannot establish bounded production memory. Its JS performance is also unmeasured. Prefer the proper bounded-cache WASM rebuild; consider the untouched same-commit fallback only as an explicitly labeled diagnostic continuation, not the accepted fix.

No binary byte modification, pointer access, substitute engine or automatic implementation is proposed. The immediate conclusion is that a proper rebuild is technically small at the binding level but requires a toolchain acquisition step that has not occurred; failure of the prebuilt artifact alone is insufficient to abandon the library.
