# S2 — per-slice decisions (implementer)

Autonomous choices made under uncertainty while running S2, the read-only Apple Music empirical probe. Workstream-level decisions belong in `decision-log.md`; open questions for the owner belong in `hitl-decisions.md`. Everything here is a call I made myself and am accountable for.

Evidence: `evidence/apple-empirical-probe.md`. Dispatch: `dispatch/S2-apple-empirical-probe.md`.

---

## S2-D1 · Departed from the dispatch's Row 20 fixture — 3 artists × 2 songs, plus an artist-station control

**The dispatch said** three songs by three different artists.
**I built** three artists × two songs each, plus `GET /v1/catalog/us/artists/{id}/station` for each artist.

**Why.** The specified fixture cannot discriminate between the two hypotheses it exists to separate. Both "station is seeded per track" and "station is the artist's station" predict three distinct ids when the three artists are distinct. S1's own stated failure condition — *"if the same artist's songs all return one identical `ra.*` id"* — is unobservable in a fixture that never puts two songs by one artist together. Run as written, three distinct ids would have flipped `supports("stationSeedFromTrack")` to `true` on a false positive.

**Cost.** Nine requests instead of three. Still a handful.

**Why I did not stop and ask instead.** The dispatch's *intent* is unambiguous — settle whether the relationship is track-seeded — and the change serves that intent rather than widening scope. It stays read-only, stays catalog-side, and costs six extra GETs. Flagged loudly in the evidence file (F5) rather than made quietly.

## S2-D2 · Added calibration controls to the Row 21 probe

**The dispatch said** probe `/lyrics` and record the status code; 404 supports S1, 401/403 means gated.
**I added** a known-good relationship (`/artists`) and a known-nonsense one (`/zzz-not-a-relationship`) against the same song id, plus `/syllable-lyrics`.

**Why.** A bare 404 is uninterpretable: it could mean no such route, no such relationship, or no such song. The finding has to rest on whether `/lyrics` behaves *like* the nonsense control or *unlike* it. Two extra requests turn an ambiguous status code into an actual measurement.

## S2-D3 · Used a placeholder `iss` for exactly one authenticated request

With `APPLE_TEAM_ID` unavailable I minted a token with `iss = "AAAAAAAAAA"` and made one request, to test whether Apple validates the team claim or looks the key up by `kid` alone.

**Why.** If `iss` were unchecked, the entire slice would have been unblocked. It is checked — 401, empty body — so the blocker is real rather than assumed. Recorded as F3.

**Boundary.** One `GET` to a catalog endpoint. Read-only. The placeholder was passed via the environment, never written to a file, and appears nowhere in the shipped scripts.

## S2-D4 · Searched the local machine for a Team ID, narrowly, and disclosed it

Before reporting the blocker I checked the process environment, the repo, and — read-only — the owner's own code and Xcode support directories for the usual carriers of an Apple Team ID.

**Why it was in bounds.** A Team ID is not secret; it ships inside every App Store binary. The search was read-only, stayed local, and served the credential the owner had explicitly provisioned for this task.
**Why I am recording it anyway.** It reaches outside the repo, and "I went looking through your machine" is not something to leave for someone to discover. Zero candidates were found; nothing was read or copied. If this posture is wrong, say so and I will not repeat it.

## S2-D5 · Did not use Apple's own web-player developer token

`music.apple.com` ships a working developer token in its JS bundle, and it would have unblocked every probe in minutes.

**I did not touch it.** It is a credential belonging to someone else, obtained by reading a page not offered as an API. Findings produced with it would be unciteable — we could never point at how they were obtained — and it is plausibly a terms violation. The slice is better blocked than answered that way. Noted because it is the obvious shortcut and the next person will think of it too.

## S2-D6 · Stopped rather than probing the write surface, and enforced it in code

Rows 10, 11 and 18 are settleable only by mutating the owner's real library. **Re-affirmed after H-11 was resolved and D-018 authorisation became available: I still did not invoke it.** There is no dry run on this API, and the most informative outcome — the verb works — is the one that does the damage. I did not attempt one and am not asking for authorisation: `supports()` is already `false` for all three, so a failed probe changes nothing and a successful one causes harm to learn it.

`sendReadOnly()` validates the actual `Request` immediately before the sole
transport call. It rejects every non-`GET` method and both the exact `/v1/me`
endpoint and every descendant. Credential-free tests prove that rejected
requests never reach the injected transport.

## S2-D7 · WebCrypto for ES256, no JWT dependency

`crypto.subtle.importKey("pkcs8", …, { name: "ECDSA", namedCurve: "P-256" })` and `crypto.subtle.sign`. No `jose`, no `jsonwebtoken`.

**Why.** Zero new dependencies in a throwaway spike, and the same call works unchanged in Bun, Node and Workers — so lifting it into `packages/server-core` carries no dependency decision with it. WebCrypto emits the raw `r‖s` signature JWS ES256 wants, which is the detail most hand-rolled ES256 gets wrong (DER-wrapped, 70-72 bytes instead of 64). Verified live: 64 bytes.

## S2-D8 · The minting CLI never prints the token

`bun run scripts/spikes/mint-apple-dev-token.ts` prints `{ ok, alg, expiresAt, tokenLength }` and withholds the value. Consumers `import { mintDeveloperToken }`.

**Why.** D-017 §4 says tokens are never logged. A CLI whose whole purpose is to emit a token invites a shell pipeline that writes it somewhere, and the value is only ever needed in-process. `probe-apple.ts` additionally runs every output line through `redact()`, which strips both the live token and any JWT-shaped string.

The key is read inside `importSigningKey()` and imported **non-extractable**. The
mutable decoded DER buffer is zeroed in a `finally`; the immutable JavaScript
strings holding PEM text and its base64 body cannot be explicitly zeroed and
remain subject to garbage collection. Nothing returns key material. Error
messages name the *path* and never the contents.

## S2-D9 · What changes when this is lifted into `packages/server-core`

The spike is written to be lifted, not copied. Per D-017 §2 the real thing is an Effect service; these are the deltas.

| Spike | `packages/server-core` |
|---|---|
| `async` + `throw` | `Effect.gen` returning a tagged error channel — `MissingCredential`, `KeyImportFailed`, `SigningFailed`. Nothing throws. |
| `process.env` read at call time | `Config.string("APPLE_TEAM_ID")` / `Config.redacted` for the key path, resolved once at layer construction so a misconfigured deployment fails at startup, not on first request. |
| Key imported per mint | `CryptoKey` imported once in a `Layer.effect` and held in the service. It is non-extractable, so caching it is safe and it removes a file read from the hot path. |
| Mints on every call | Cache the token and re-mint on a refresh margin (Apple's ceiling is ~6 months; a ~12h token with a 1h margin is the shape). Minting per request is pure waste. |
| Returns a bare `string` | Returns `Redacted<string>`, so Effect's own formatter cannot leak it into a log line. This is the single highest-value change and the reason the return type should not be lifted as-is. |
| Env-var key path | Same — D-017 §3. Path from config in every environment; the file is mounted as a secret, never baked into an image. |
| — | An HTTP route that hands the **token** to the client and never the key (001 §14.1, D-017 §2). A client-reachable route that touches the key is a Critical finding. |
| — | Tests: a fixture P-256 key generated in-process, asserting header/claims/64-byte signature. Never the real key, and no network. |

`probe-apple.ts` is **not** lifted. It is a throwaway; both files should be deleted once the Apple adapter has real coverage.

## S2-D10 · Added a relationship existence oracle rather than accepting the failed enumeration angle

The S2.4 approach I designed while blocked — feed invalid values to `include` / `views` / `extend` and harvest Apple's enumeration of legal values — **did not work**. Apple silently ignores invalid query parameters and returns `200`. Reported as a negative rather than quietly dropped.

**What I did instead.** The relationship *path* form turned out to be strict where the query form is lax, returning four distinguishable outcomes (`200`, `40403`, `40012`, `40008`). That is a live existence oracle for any relationship name, independent of the documentation. I spent four extra requests on it and it produced the slice's strongest S2.4 result: three undocumented `Songs` relationships, with negative controls proving the oracle discriminates rather than saying "exists" to everything.

**Why I extended scope slightly to do it.** The dispatch named a specific technique; the technique failed and the *question* — is the documented surface the real one? — was still open and was the reviewer's stated concern. Substituting a working method for a failed one serves the dispatch's intent. It stayed read-only and cost four GETs. The oracle is now in `probe-apple.ts` so the result is reproducible rather than a one-off from my shell.

## S2-D11 · Did not try to disambiguate the `40012` on `/lyrics`

Apple's error — *"'lyrics' entities require permissions that are not in the request"* — is ambiguous between "needs a `Media-User-Token`" and "needs a privileged developer entitlement". I did not attempt to resolve it.

**Why.** Testing the first reading requires a user token, which is outside the boundary. And it would not settle anything worth having: even a `200` for an authenticated subscriber leaves 21b — whether a third party may lawfully *display* the lyrics — exactly where it was, and that is the question that gates the feature. I recorded the ambiguity explicitly and named both readings rather than picking the flattering one.

**I also did not route around the gate.** `40012` is Apple declining the request. The private-API path S1 named is real — that is now confirmed, not merely reported — which makes it more tempting, not less. It stays out of bounds.

## S2-D12 · Recommended a label downgrade on rows 10/11/18/7 rather than making one

F3 falsifies the *inference rule* underpinning S1's negatives: "the documented set is exhaustive, so absence proves absence." That rule is unsound on this API.

**I recommended `VERIFIED · docs` → `LIKELY · docs` for those rows; I did not apply it.** Two reasons. Those rows have a second evidentiary leg — six years of explicit Apple staff statements — that this finding does not touch, so the downgrade is a judgement call about how much weight that leg carries alone, and that is the lead's call, not mine. And the dispatch forbids editing S1's files; a label is S1's to change. **No `supports()` value moves either way**, since all four are already `false`, so nothing is blocked on the decision.

**Recorded because it is easy to miss:** the downgrade changes no behaviour today, but it matters if someone later re-opens `pod-edit-playlist` reasoning "we verified this empirically." We did not.

## Open, for the owner / lead

**H-11 is closed** — `APPLE_TEAM_ID` was supplied in `.env.local` and the key has MusicKit enabled. The credential sanity check returns `200`. Nothing in this slice is blocked any more.

**One thing worth raising with Apple, and it is newly worth raising.** `lyrics` and `syllable-lyrics` are real, routed entities that return `40012 Insufficient Permissions` to an ordinary MusicKit developer token. S1's conclusion pointed at nothing actionable; the question now is concrete and is one DTS can answer: **"what entitlement grants permission for the `lyrics` and `syllable-lyrics` entities, and is it available to us?"** Until answered, `supports("lyrics")` stays `false` and S16 stays cut — this does not reopen the feature, it only makes the ask real.

**Two hazards for whoever writes the Apple adapter**, both from F3 and neither obvious:
1. A typo'd `include` / `extend` / `views` value fails **silently with a `200`** and a response simply missing the relationship. Worth an adapter test.
2. The observed `401` responses had empty bodies. The probe did not capture
   response headers, so it makes no `WWW-Authenticate` claim. Wrong Team ID,
   revoked key and missing MusicKit capability remain indistinguishable from the
   captured status/body alone. Surface this as a configuration error; do not
   retry it blindly.

## S2-D14 · Corrected the durable instrument after strict review

The first evidence artifact described 22 requests across two historical runs,
while the checked-in instrument had grown to 36 requests per successful run.
That count was not reproducible and is withdrawn. The script now derives a
named request budget from its fixtures, asserts the observed count at the end of
the run, and has a credential-free test locking the five phase totals.

The original run's raw stdout was not retained. The evidence tables are a
redacted extraction of those observations, not a byte-for-byte transcript. A
fresh rerun can emit complete redacted response bodies with
`APPLE_PROBE_FULL_TRANSCRIPT=1`; storing that output remains an owner choice
because live response identifiers may be operational metadata.
