## Supervisor trace mapping: marquee is now the first investigation target

The supervisor reports wp-title-marquee active approximately0.8–8s between sparse inputs,438 RAF callbacks with1.3s aggregate wall duration and786 Paint events with211ms aggregate duration during a15s capture. These are supervisor-observed values, not independently extracted here; this report does not attribute every counted callback/paint to the marquee or add these overlapping event durations into a total CPU claim.

**HIGH investigation priority, source-supported correlation:** [panel.css:165](/Users/vinicius/code/webPod/packages/panel/src/panel.css:165) gives each overflowing active label a12s linear,2s-delay, infinite wp-title-marquee animation. Its keyframes move the label and return it, with two stationary segments ([line247](/Users/vinicius/code/webPod/packages/panel/src/panel.css:247)). Despite the animation name, this includes the selected list row's primary text ([list-view.tsx:40](/Users/vinicius/code/webPod/packages/panel/src/list-view.tsx:40)), as well as the Now Playing track title ([Panel.tsx:848](/Users/vinicius/code/webPod/packages/panel/src/Panel.tsx:848)). Long playlist names can therefore start it while browsing with no further touch.

[OverflowMarquee](/Users/vinicius/code/webPod/packages/panel/src/overflow-marquee.tsx:10) measures overflow on text/active changes and ResizeObserver notifications; it has no application RAF or per-frame React state. The continuing work need not be React rerenders. CSS changes the HTML-in-Canvas raster; the app's [paint listener](/Users/vinicius/code/webPod/packages/composite/src/html-in-canvas.ts:189) calls fitPanelToNativeGrid, marks texture.needsUpdate and screen.invalidate. The installed Three0.185.1 [HTMLTexture constructor](/Users/vinicius/code/webPod/node_modules/.bun/three@0.185.1/node_modules/three/src/textures/HTMLTexture.js:46) additionally installs a parent.onpaint callback marking the texture dirty. Because the app appends the element before creating HTMLTexture, that constructor path is taken. The second WebGLTextures callback-registration path is conditional on reparenting and should not automatically be counted as another installed callback. [WebGLTextures](/Users/vinicius/code/webPod/node_modules/.bun/three@0.185.1/node_modules/three/src/renderers/webgl/WebGLTextures.js:1297) uploads HTML pixels using texElementImage2D. Demand rendering thus still renders whenever the animated LCD invalidates it.

This chain is a much stronger match to the supervisor's sparse-input continuous-paint observation than haptics, version polling, or full-list mapping. It still needs a controlled comparison of the same highlighted item and viewport with the animation paused before asserting causal savings. A check on the rear face may also matter: CompositeDevice keeps the T1 panel portal mounted independent of orientation, and marquee activation has no face-visibility gate. Whether Chrome skips those raster updates cannot be inferred from source alone.

Preserve readable overflow rather than blindly remove the feature. Candidate experiments, in order: (1) one complete crawl after dwell then a genuinely stopped/resting animation, with re-selection able to replay; pause while active wheel input is changing selection; (2) only run crawl while the LCD is facing the user and document visible; (3) reuse measured raster geometry during pure paint events instead of remeasuring dimensions on every animation paint. A lower-frequency stepped crawl is another option only if it visibly retains legibility. Throttling texture uploads alone may leave CSS raster/paint cost intact and should not be assumed sufficient. Need before/after DevTools comparison and visual reading check before choosing behavior.

## Other structural hypotheses

### MEDIUM — Full list mapping remains on the detent render path

[click-wheel-runtime.ts](/Users/vinicius/code/webPod/packages/composite/src/click-wheel-runtime.ts:164) handles each admitted pointer sample by publishing the angular delta to detentActionAtom. The authoritative state path changes the screen stack for accepted movement ([store.ts](/Users/vinicius/code/webPod/packages/state/src/store.ts:674)). [Panel.tsx](/Users/vinicius/code/webPod/packages/panel/src/Panel.tsx:293) subscribes to the complete current screen frame, so changing highlight/window coordinates renders the screen's list component.

[BrowserList](/Users/vinicius/code/webPod/packages/panel/src/Panel.tsx:589) maps every frame.rows entry into a new ListRowContent object, allocating optional chevron React elements, before [ListViewport](/Users/vinicius/code/webPod/packages/panel/src/list-view.tsx:73) slices down to the visible capacity. [NestedTrackList](/Users/vinicius/code/webPod/packages/panel/src/Panel.tsx:605) does the same; the queue path maps all active queue items at Panel.tsx:804. Thus bounded DOM does not mean bounded per-highlight JS preparation. The main menu has few rows and is a weaker concern; actual library size matters.

Potential change if trace confirms React/list allocation cost: separate stable row-content preparation from current highlight, or map only the visible window while preserving total row count/index/accessibility contracts. Do not replace the state-owned windowing logic or add independent scroll state. A trace showing long list render/map stacks with negligible GPU time would strengthen this hypothesis; short library lists or dominant shader/texture work would weaken it.

### MEDIUM — Sticker motion fans out through broad React subscribers and a second projection pass

[StickerCollection.move](/Users/vinicius/code/webPod/apps/web/src/sticker-collection.tsx:215) publishes a new pointer record with a bounded 12-sample array; peeling also publishes the full interaction, drag offset, optional source pull and held preview. It queries seat bounds and projects/fits the preview on the input path. [setStickerInteractionActionAtom](/Users/vinicius/code/webPod/packages/state/src/stickers.ts:40) validates and constructs a fresh normalized interaction object even when resulting fields are unchanged. The installed Jotai implementation detects value changes with Object.is (node_modules/.bun/jotai@2.20.3/node_modules/jotai/esm/vanilla/internals.mjs, setAtomStateValueOrPromise); publishing fresh objects can therefore notify readers. React may batch synchronous writes: this review does not assert one React commit per write.

[ProductionDeviceView](/Users/vinicius/code/webPod/apps/web/src/production-device-view.tsx:124) reads interaction, source pull/anchor, drag offset, pack progress/presence and several collection atoms at its broad scene boundary. Each motion render reconstructs preparedSheet arrays and the scene object ([line160](/Users/vinicius/code/webPod/apps/web/src/production-device-view.tsx:160)) and renders CompositeDevice plus StickerCollection. ProductionPanelView is memoized, so the inner panel's props are protected; there is no evidence every sticker update rerenders all panel content. CompositeSceneBridge nevertheless runs resyncGeometry after each of its commits ([CompositeDevice.tsx](/Users/vinicius/code/webPod/packages/composite/src/CompositeDevice.tsx:787)).

[StickerPackScene](/Users/vinicius/code/webPod/packages/device/src/StickerPackScene.tsx:233) notifies projection changes on placement/peel/landing updates. The app [coalesces these notifications into one RAF](/Users/vinicius/code/webPod/apps/web/src/sticker-projection-notifications.ts:7), but that next-frame notification updates the projection-version atom, read by the collection and [editor](/Users/vinicius/code/webPod/apps/web/src/sticker-editor.tsx:79). This is bounded cross-renderer synchronization, not a demonstrated infinite loop. There is an explicit unchanged-model-position guard in StickerPackScene.tsx:99 that prevents the known transform feedback cycle.

Potential change if trace identifies commits/projection reads as expensive: retain prepared sheet identity across physical-only updates; isolate motion readers; avoid publishing normalized no-ops; evaluate a single frame-admitted motion snapshot while preserving immediate gesture ownership/cancellation. Do not claim savings without comparing the same sticker gesture. If the trace is only front-wheel browsing, this lane should not be blamed for active sticker work that never occurred.

### MEDIUM — LCD changes couple broad DOM mutation observation to layout measurement and texture work

[HTML-in-canvas attach](/Users/vinicius/code/webPod/packages/composite/src/html-in-canvas.ts:115) measures panel content using scrollWidth/Height (falling back to offsets), then writes panel sizing and content transforms. Every requestPixels call repeats the fit and calls canvas.requestPaint; painted content marks the HTMLTexture dirty and invalidates the demand-rendered scene ([line141](/Users/vinicius/code/webPod/packages/composite/src/html-in-canvas.ts:141)). The paint callback fits again and updates the texture ([line189](/Users/vinicius/code/webPod/packages/composite/src/html-in-canvas.ts:189)).

The subtree MutationObserver watches all attributes/text/children. [mutationAffectsPanelPixels](/Users/vinicius/code/webPod/packages/composite/src/html-in-canvas.ts:336) excludes only the host's style attribute. Semantic-only mutations such as aria-activedescendant can therefore request pixels even though they need not change raster output. The review does not establish that a single detent necessarily produces multiple delivered paints: browser paint coalescing and mutation delivery determine that. Nor is a forced synchronous layout or self-sustaining paint loop established merely by the reads.

Trace targets: requestPixels/fitPanelToNativeGrid, Layout/Recalculate Style, canvas paint, HTMLTexture upload and renderer work immediately after selection updates. If dominant, consider dirty-category filtering and geometry-versus-content invalidation separation before touching React. Preserve accessibility updates even if raster notification can omit them. The renderer-side vertical should assess texture/GPU work.

## Idle and lifecycle checks / rejected shortcuts

- **INFORMATIONAL — Haptics are event-driven, not a continuous idle timer.** [interaction-haptics.ts](/Users/vinicius/code/webPod/packages/composite/src/interaction-haptics.ts:27) allocates its engine on first admitted pulse. Detents require human:touch, origin detent, and are capped at45ms intervals; peel requests at70ms. Native vibration creates no adapter RAF. The installed web-haptics0.0.6 fallback has an RAF only for the short pattern; cancel/destroy clear it and hidden switch DOM. Listeners have cleanup; wheel store binding is reference-counted in a WeakMap. On unsupported browsers a feature-check input element is allocated per attempted pulse before returning, but this is event-local, not idle work. No evidence supports blaming the new haptics for perpetual frames.
- **INFORMATIONAL — Update monitor is one visible-only 60-second check, not frame work.** [update-state.ts](/Users/vinicius/code/webPod/apps/web/src/update-state.ts:49) owns one QueryClient, one query key, gcTime0, retryfalse, a5s deadline and one in-flight request. Listener, timer and request cleanup exist. Same build sets the atom to the same null value. The dismissed-build Set grows only when the user dismisses distinct deployments during this page session; it is a low-cardinality retention tradeoff, not a pointer-driven leak. No evidence of a rerender cascade from idle update checks.
- **INFORMATIONAL — Demand rendering and bounded warmup exist.** [DeviceCanvas](/Users/vinicius/code/webPod/packages/device/src/DeviceCanvas.tsx:152) uses frameloop="demand". DeviceRenderWarmup uses useFrame only during startup warmup; this is not enough evidence for ongoing idle work. ControlPhysicsScope has explicit transient animation lifetime. Treat any measured perpetual rendering as a reason to find repeated invalidations, not to assert the canvas uses an always-on loop.
- **INFORMATIONAL — Playback has a real recurring source.** [Apple provider](/Users/vinicius/code/webPod/packages/providers/src/apple/apple-provider.ts:376) refreshes progress through a250ms interval while playing/loading and stops once neither status applies. While browsing, BrowsingTitleBar subscribes to playbackObservation, so progress publications may rerender it even if only the transport icon matters. This may matter during playback; it does not prove paused idle activity. The panel's own acquirePlaybackClock is fixture-only (Panel.tsx:655), so do not attribute that fixture clock to production Apple playback.
- **INFORMATIONAL — Sticker refresh is bounded by auth/visibility/lifetime.** [sticker-runtime.ts](/Users/vinicius/code/webPod/apps/web/src/sticker-runtime.ts:131) uses its refresh interval and a visible/auth guard; detach clears interval and visibility listener. No per-frame polling found there.
- **INFORMATIONAL — Audio has explicit caps.** interaction-audio.ts limits active/scheduled voices to12 and pending feedback events to8, uses one authoritative store subscription, and disposes runtime on composite unmount. Exact audio scheduling cost needs trace evidence.
- No atomFamily, atomWithInfiniteQuery or useInfiniteQuery found in reviewed app/panel/composite source, so their family eviction/maxPages warnings are not findings. Reviewed gesture sample arrays are bounded; no activity-proportional unbounded buffer or orphaned listener was established. Broad React closure scopes exist but mounted-lifetime listeners have cleanup; no heap-retention size or GC pause is inferred.
