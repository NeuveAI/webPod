# Remaining motion CPU work — source audit

Read-only audit on `codex/device-cpu-profile` after PR4 merge. Read rotation-result.md, rotation-motion.md and runtime-review references. The older documents describe pre-merge verification and cannot establish current localhost performance. The supervisor owns the existing Chrome session, iPhone16ProMax emulation and6× CPU profile. I made no browser calls or implementation edits. All costs below are structural candidates, not measured timings or an established priority ranking.

## Publication and React breadth

The direct drag path is [`onMove`→`updateGrab`](/Users/vinicius/code/webPod/apps/web/src/device-preview-orientation.ts:332), which publishes on each accepted pointer sample. `setOrientation` clamps, resolves preset, creates/freeze-publishes a new snapshot and synchronously notifies subscribers on a changed pose ([store](/Users/vinicius/code/webPod/apps/web/src/device-preview-orientation.ts:58)). Identical poses bail out, and pointer velocity history is capped at12 samples. Release motion already uses RAF. There is no basis to call the bounded sample array a leak or to assume every notification becomes a separate React commit.

[`InteractiveDevicePage`](/Users/vinicius/code/webPod/apps/web/src/device-page.tsx:170) subscribes to the entire preview snapshot. Each changed orientation therefore reaches ProductionDeviceView, CompositeDevice, DeviceCanvas and Device, whose geometry/material factories are largely memoized but whose component bodies/JSX still execute. [`DeviceCanvas`](/Users/vinicius/code/webPod/packages/device/src/DeviceCanvas.tsx:141) creates a fresh orientation context containing the full orientation plus derived interaction/visible-face values; context consumers update even when only the angle changes and the face/admission result is unchanged. This is real subscription breadth, not proof of expensive geometry regeneration.

**Trace discriminator:** inspect pointer event stacks and React `renderWithHooks`/`beginWork`/commit work, compare direct dragging with free rotation after release, and count commits versus visible renderer frames. Multiple expensive commits before one frame would support narrowing publication/render boundaries. One cheap commit per frame would falsify this as the dominant bottleneck. Keep public synchronous tool state, final pointer sample and release velocity semantics in any later dispatch; deferring the store itself is not automatically safe.

## Repeated object and scene preparation

[`ProductionDeviceView`](/Users/vinicius/code/webPod/apps/web/src/production-device-view.tsx:160) filters neighboring collections, maps slots, and builds new preparedSheet, pack and stickerScene objects on every render. This repeats with orientation even when sticker data is unchanged. It can propagate work into [`StickerPackContents`](/Users/vinicius/code/webPod/packages/device/src/StickerPackScene.tsx:50), which computes slot keys, refreshes refs and renders the pack subtree. Individual paper and sheet meshes have memoized geometry; do not equate fresh scene props with dense paper reconstruction.

[`ViewerLitDeviceFrame`](/Users/vinicius/code/webPod/packages/device/src/ViewerLitDeviceFrame.tsx:42) recomputes the fixed envelope and allocates three temporary RectAreaLight objects to derive lookAt rotations on each render ([helper](/Users/vinicius/code/webPod/packages/device/src/ViewerLitDeviceFrame.tsx:122)). Lighting parameters normally do not change while the model rotates. [`DeviceRevealPortal`](/Users/vinicius/code/webPod/apps/web/src/device-reveal-portal.tsx:33) also remaps18 fixed motes/style objects when its parent renders; CSS invisibility after entry does not prevent React work. These are bounded allocations, with no source evidence that they dominate.

**Trace discriminator:** samples in ViewerLitDeviceFrame, RectAreaLight/Object3D constructors, completeDeviceEnvelope, ProductionDeviceView and reconciliation/GC. Allocation or total-call evidence matters more than isolated function presence. Compare rotation with no active collection against an authenticated prepared pack to distinguish app-wide rerenders from sticker scene breadth.

## Sticker work still on the main thread

The GPU paper path avoids dense per-curl buffer reconstruction, and carry deformation/BVH work uses workers. The submission boundary still has CPU work. [`PeelingPrint`](/Users/vinicius/code/webPod/packages/device/src/StickerPackScene.tsx:414) serializes `[art, pack, dimensions, origin]` into an inputKey each render. On changed input, orientation or collision revision its layout effect recursively updates the entire content world matrix, updates the visibility signature, calculates camera/world inputs and submits the worker request. During return-to-sheet only, it additionally computes Box3 over the workspace. [`visibility.update`](/Users/vinicius/code/webPod/packages/device/src/sticker-visibility.ts:94) checks the assembly signature before reusing the collider; it is not automatically rebuilding the BVH on every orientation.

The lazy GPU paper CPU bounds sampler runs when Box3 requests bounds; it is not an unconditional per-frame dense operation. Bounds are cached by curl. A trace hot in sampleGpuPaperBounds during return motion needs to be separated from ordinary peeling/dragging and normal device rotation.

**Trace discriminator:** main-thread JSON.stringify, updateWorldMatrix/updateMatrixWorld, Box3.expandByObject, sampleGpuPaperBounds and postMessage/structured-clone stacks; separately inspect worker tracks for compute. Distinguish pointer-handler CPU latency, React layout-effect submission, worker turnaround, and accepted-result commit. A busy worker is not by itself a main-thread blocker. The output must retain monotonic gesture/pose acceptance and exact CPU collision/bounds semantics.

[`StickerCollection`](/Users/vinicius/code/webPod/apps/web/src/sticker-collection.tsx:148) evaluates rear admission each orientation and, when its JSON pose key changes, clears candidates, releases capture and dismisses the editor; source-placement carry can be cancelled. Repeated atom writes often bail out through equality, but callbacks still run. This is lower-priority structural work unless the trace shows atom propagation or cleanup stacks dominating. These actions preserve interaction ownership and cannot simply be removed.

## Existing work and profile confounders

The former duplicate LCD layout resync is already gone. The current [screen callback](/Users/vinicius/code/webPod/packages/composite/src/html-in-canvas.ts:196) performs one synchronous InteractionManager update for a rendered changed pose. It still reads DOM dimensions and writes the proxy projection; native hit/focus correctness needs that boundary. Look for actual forced style/layout under InteractionManager rather than presuming four property reads are four expensive layouts. LCD paint/requestPaint and texture upload are separate work; a continuous title marquee can produce them independently of rotation.

Projection diagnostics default off; do not profile with `projection-diagnostics` or capture flags unless deliberately measuring them. Local DEV still mounts [interaction telemetry](/Users/vinicius/code/webPod/apps/web/src/device-page.tsx:243): its [250ms sample](/Users/vinicius/code/webPod/apps/web/src/interaction-telemetry-browser.ts:12) queries DOM, reads several stores and serializes a snapshot. This is periodic development work, not a per-pose production cost. Preserve source/build provenance when interpreting it.

Three's renderer still traverses/updates world matrices and submits physical/transmission draws on CPU before GPU execution. A renderer.render-heavy main thread must be separated from React before proposing memoization.6× CPU throttling with phone viewport is not a measurement of the phone GPU. No severity, millisecond saving, FPS improvement or implementation recommendation is asserted before the supervisor's trace.

## Follow-up: why configure reaches DPR resizing

The supervisor's current six-key trace reports168–455ms key interactions, substantial development React instrumentation, and a73.299ms aggregate `setSize` attribution under `configure → setDpr → setPixelRatio → setSize`. These are supervisor/trace-review observations, not timings collected by this source audit. The trace contains no actual DPR argument values, so the following source mechanism is conditional rather than a fully proven value-level root cause.

Installed Fiber9.7 [`Canvas` layout effect](/Users/vinicius/code/webPod/packages/device/node_modules/@react-three/fiber/dist/react-three-fiber.esm.js:62) has no dependency array. It calls `root.configure` after every Canvas commit, including orientation changes even at unchanged measured viewport. However, configure does **not** resize merely because the `dpr` array has a new identity: [its numeric guard](/Users/vinicius/code/webPod/packages/device/node_modules/@react-three/fiber/dist/events-156d8d12.esm.js:15823) compares `state.viewport.dpr !== calculateDpr(dpr)`. The inline GL object does not recreate the renderer, whose setup is one-time; camera prop identity likewise does not explain this specific setDpr stack. Stabilizing JSX prop objects alone is not the sufficient fix.

There are two competing DPR authorities. DeviceCanvas supplies the default range[1,3], which Fiber resolves against `window.devicePixelRatio`. Meanwhile [`CanvasPixelDensity`](/Users/vinicius/code/webPod/packages/device/src/CanvasPixelDensity.tsx:26) observes physical pixel boxes and writes a separately resolved numeric value via setDpr. Its [resolver](/Users/vinicius/code/webPod/packages/device/src/pixel-density.ts:19) takes the maximum of the average physical/CSS ratios and window DPR, clamped to[1,3]. Fractional physical-box rounding/zoom can make the observer value slightly greater than window DPR below3. The next configure then resets it to the range/window value, and a subsequent observer notification can restore the physical value. If window DPR is3, both resolve to3, so this particular mismatch explanation is falsified. Actual `window.devicePixelRatio`, physical/CSS box dimensions and Fiber viewport DPR before/after a key are needed to identify the current pair. No browser inspection was performed by this agent.

There is also a concrete multiplier once a DPR change occurs. [Fiber's resize subscription](/Users/vinicius/code/webPod/packages/device/node_modules/@react-three/fiber/dist/events-156d8d12.esm.js:1158) invokes `gl.setPixelRatio` then `gl.setSize`. [Three0.185.1 setPixelRatio](/Users/vinicius/code/webPod/packages/device/node_modules/three/src/renderers/WebGLRenderer.js:628) itself invokes setSize; setSize assigns canvas.width/height even when the resulting pixel dimensions repeat. Thus one DPR transition can produce two buffer-size assignments. Repeated same numeric setDpr writes can still notify Fiber subscribers, but the resize subscriber's old-DPR equality guard prevents those alone from explaining repeated setSize.

**Minimal quality-preserving candidate, only after confirming values:** make the physically resolved numeric DPR a single shared authority used both by the Canvas prop and its physical-box observer. Preserve the existing fractional/zoom resolver, range ceiling and explicit numeric-DPR opt-out; only publish when resolved value changes. Use the existing shared-state conventions rather than component useState. This removes configure/observer disagreement while keeping the same final sharpness. Memoizing the default range alone or deleting the physical-box resolver would respectively miss the numerical cause or weaken the intentional zoom behavior. No patch is made here. A later verification should show zero setDpr/setSize during pure same-viewport orientation changes, correct real resize/DPR/zoom updates, unchanged physical buffer dimensions and immediate LCD hit projection.

Supervisor's permitted read-only DOM observation after rotation reports inner viewport440×956, window DPR3 and canvas drawing buffer1320×2664. This stable observed DPR hits the shared maximum, so it does **not** confirm a physical-versus-window reset loop in the recorded interaction. No resize-call arguments were captured. Two independent DPR owners and the duplicate setSize consequence are source-proven; the actual transient value causing this trace's configure/setDpr branch remains unresolved. Treat a single-owner change as a candidate requiring reproduction, not an established fix for these measured73.299ms.
