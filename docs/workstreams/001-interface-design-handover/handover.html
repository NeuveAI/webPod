01The three layers

Every element in the design file belongs to exactly one layer. If you cannot classify something in under two seconds, that is a design bug — raise it rather than guessing.

LayerRenders withContainsVisual law
Device react-three-fiber Body, wheel, Select button, steel back, cover glass Skeuomorphic. One key light at 12 o'clock. Gradients are material parameters or shaders — never CSS.
Panel real DOM Everything inside the 272×204 screen 2005 LCD discipline: flat fills, ≤3 gradient stops, no blur, no translucency.
Glass DOM · Tailwind · shadcn Sidecar, overlays, sheets, status bar iOS 26 Liquid Glass: blur, translucency, 1px border, soft elevation. No gloss, no bevel, no specular.

The law that makes this non-negotiable

The panel must remain genuine DOM, because it is the layer WebMCP actuates. A texture cannot be focused, read by a screen reader, or driven by a tool call. The moment the panel becomes pixels, the entire agent thesis dies with it.

How the panel meets the device

html-in-canvas is the bridge: layoutsubtree on the canvas, drawable on the panel root, then drawElementImage() in the paint event, with updateElementGeometry() to keep hit-testing and the accessibility tree aligned with where the pixels actually landed.

Flagged Not a dependency — and weaker than it looks

It is an unshipped WICG Community Group explainer, implemented only behind chrome://flags/#canvas-draw-element in Chrome Canary. No origin trial, no second implementer, an admittedly unfinished spec, and the WebGL entry point is mid-rename — the proposal's own example carries a runtime try/catch across the old and new signatures of texElementImage2D while the IDL declares texElementSubImage2D.

One API detail that bites: in a 2D context updateElementGeometry runs automatically, but 3D contexts must call it explicitly — the transform from a texture back to canvas CSS coordinates isn't available to the canvas API. Our device is a 3D context.

The finding that de-risks this entirely

The correct architecture is identical whether the flag exists or not. The local three.js clone (r185) already ships src/textures/HTMLTexture.js — feature-detected via 'requestPaint' in parent — alongside InteractionManager.js, which computes CSS matrix3d transforms each frame so the underlying HTML elements stay aligned with their meshes. Because those elements are real children of the canvas, the browser dispatches pointer events to them natively.

So hit-testing and accessibility need no flag at all. Three tiers, same scene, same components:

  1. Flag on — DOM pixels composited into WebGL. Best fidelity.
  2. Flag off — CSS-3D-transformed DOM overlay registered to the modelled bezel.
  3. Either way — nothing is lost in accessibility or WebMCP actuation. The only casualty is "pixels inside the material".

Build tier 2 first. Tier 1 is a swap, not a rewrite.

Two constraints that bind from day one

Cross-origin album artwork will not paint. Read-back-allowed rendering means artwork must be proxied same-origin through Bun. This affects Now Playing, Cover Flow, the sidecar and every list thumbnail — design the proxy in stage 1, not after the first black square appears.

DOM changes made during paint only appear the following frame. Never mutate state from inside the paint handler and expect it that frame.

02Build order

This sequence is deliberate — each stage is shippable and each de-risks the next. It is a real dependency chain, not a wish list.

Three things your training data has wrong

Every one of these was verified against the local clones. Assume the version in your head is stale.

  1. Effect is 4.0.0-rc.112, and HTTP has moved to effect/unstable/http — not @effect/platform. Services use Context.Service, not Context.Tag or Effect.Service. Schema imports from "effect" directly.
  2. TanStack Start server functions use .validator(…), not .inputValidator(…), in 1.168.49.
  3. Jotai's outside-React docs are marked published: false — so the store.get/set/sub pattern our whole state architecture rests on is likely absent from training data. It is real; it is in core/store.mdx.

Server functions

Server routes — not server functions — are the documented mechanism for anything called from outside the app.

The provider as an Effect service

// two Layer.effect implementations, swapped at the composition root

Only token minting and refresh are server-side; both music SDKs are browser-side, so the provider layer itself runs in the client.

The scene must not run at 60fps

The device sits still almost all the time. This is a mobile-first, battery-sensitive product, so an always-on render loop is a defect, not a default.

// scaling-performance.mdx: renders frames whenever it detects prop changes
<Canvas frameloop="demand">

// request a frame when something actually changed
invalidate()

Footgun from the local docs

invalidate() only schedules a render, it does not render immediately. For animations that start synchronously, the first frame can land after the animation has already advanced, producing a visible jump. Schedule the render pre-emptively, then start the animation on the next frame.

04State, and why useState is banned

The ban is architectural, not stylistic. Stating the reason properly is what stops it being quietly worked around at 2am.

The reason

WebMCP tool callbacks live outside React. A tool handler is a plain function the browser invokes; it must read and write the same state the UI renders. State trapped in a component closure is unreachable from there.

A store you can reach from a plain function is therefore a requirement. useState is not a worse way of doing this — it is unable to do it.

Jotai's store exposes exactly the three operations a tool handler needs, and no more:

// jotai/docs/core/store.mdx — "get for getting atom values, set for setting
// atom values, and sub for subscribing to atom changes"
import { createStore, Provider } from 'jotai'

export const store = createStore()

// inside a WebMCP tool handler — no React in sight
store.get(nowPlayingAtom)
store.set(queueAtom, next)
const unsub = store.sub(queueAtom, () => { … })

// the app is mounted against the same store
<Provider store={store}><App /></Provider>
Kind of statePatternNotes
Ephemeral UIatom()Highlight index, open sheet, scrub position. Still atoms — an agent may need to read them.
Derivedatom(get => …)Never recompute in render.
Server / asyncTanStack Query + atom bridgeCatalogue, library, lyrics.
Per-viewer persistedatomWithStorageColourway, clicker mode, density.
CollectionsatomFamily · splitAtomQueue rows, so one row changing doesn't rerender the list.

Reviewers: a single useState in a PR is a merge blocker, including in a "temporary" or "just local" case. The exception list is empty.

05Provider abstraction

Apple Music (MusicKit) ships first. Spotify must be addable without redesign — which means the seams are designed now, while there is only one implementation to be honest about.

The contract is one method — supports(capability) — and it drives both the UI branch and the tool registration. Nothing else in the app asks which provider is active.

interface MusicProvider {
  readonly id: ProviderId                     // "apple" | "spotify"
  supports(c: Capability): boolean              // ⚑ the contract
  unsupportedReason(c: Capability): string|null // reaches the human, never the agent

  authorize(): Promise<Session>
  search(q): · libraryList/Add/Remove(…)
  playlistCreate/AddTracks/RemoveTracks/Reorder(…)
  play/pause/skip/seek/setVolume(…)
  onPlaybackChange(cb) · onProgress(cb)
  queueRead/Append/InsertNext/Remove/Reorder(…)
  stationsList/stationStart(…) · lyrics(ref)
  ratingSet(ref,{love}) · saveToggle(ref,saved)
}

Star ratings are deliberately absent from the interface — neither service has them, so they live locally rather than being faked into the contract.

Where they genuinely differ

Resolve the two unverified playlist rows first

If Apple Music genuinely cannot remove or reorder playlist tracks, pod-edit-playlist is broken on the launch provider and the staged-diff screen loses half its purpose. This is a day-one spike, not a month-three discovery.

Identity — LocalKey, not provider IDs

Every internal structure holds a UUIDv7 LocalKey. TrackRef is the resolution record it points at, carrying provider, catalogue ID, Apple's separate library ID, ISRC, and denormalised title/artist/duration so a track can be re-resolved without a round-trip. Cross-provider matching ladder: ISRC exact → title+artist normalised + duration ±2s → flagged low-confidence.

The queue cannot survive a provider switch — and we don't pretend it can

It is provider-side state consumed in real time, and on Spotify it cannot even be reordered. A 78%-matched reconstruction would be neither the old queue nor one the user could repair.

So the queue is cleared, with a one-time card: "Your queue didn't come across. 14 songs were queued on Apple Music. 11 are on Spotify." → Rebuild queue · Start fresh. The Engraving is archived, not deleted — stamped with the old provider, read-only, and the ⟲ affordances removed, because a dead Undo control is worse than none.

The framing that makes this coherent: a provider switch is a new device, not a migration.

Unsupported capability ⇒ the tool is not registered. An agent never sees a tool it cannot use, never plans around one, and never has to interpret a refusal. Partial support narrows the inputSchema rather than registering-and-refusing — on Apple, pod-edit-playlist would register with remove and reorder simply absent as properties. A provider switch fires toolchange. No registered tool may ever return "unsupported".

The agent variants are props, not components

The design file lists Music Menu and Music Menu — Agent separately because a canvas has no props. In code they are one <MusicMenuScreen selectionActor="human"|"agent">.

Forking them is precisely how attribution drifts: the agent fork gets a fix the human one doesn't, and six months later the two selection bands behave differently for reasons nobody remembers. Same ruling for Now Playing / — Light Mode: mode is a prop, never a second component.

Shared sub-parts to extract once: <PanelTitleBar>, <PanelListRow> (selected, actor, provenance), <SplitPanePreview>, <Transport>, <ProgressBar>, <ActorSigil>, <HumanHalo> + <AgentTrail>. From shadcn: Button (review bar), Input (search field), Command (results), Badge (provenance).

Sigils are not decoration

● filled circle = human. ⬡ hexagon = agent. These carry attribution when colour fails — colourblindness, greyscale, 4% opacity. Any row whose origin is attributable renders one. Never substitute a colour swatch for the shape.

At risk if the panel is ever rasterised

  • <PanelListRow> — focus ring and accessibility tree vanish. DOM path stays primary, always.
  • <SearchField> — caret, IME and autofill break. Never rasterise; it belongs to Glass.
  • <ScreenTint> — mix-blend-mode does not survive. Pre-composite it.

Everything else in the panel is already canvas-safe — Panel Discipline forbids exactly the features that don't rasterise (blur, translucency, backdrop-filter). The 2005 constraint turned out to be the portability constraint.

08Interaction & FX

The occlusion rule

A thumb on the wheel hides the inner ring. Under the contact patch, render material state only — depression, bevel — which the finger supplies haptically anyway. Anything carrying information must render where the finger is not.

The thumb shaft subtends ±33° at the trail radius. This rule already killed three effects that had been drawn: the per-quadrant press glow, the lit Center button, and the in-wheel human rotate arc.

Ghost trails

Two rules that look like polish and are not

The two trails must not converge in smoothness. At equal blur the agent band becomes as smooth as the human halo and continuity — attribution channel 2 — collapses. The human reads as a continuous smear; the agent as a sampled sweep.

Arcs are exact-tiled, never overlapped. Overlapping alpha accumulates as 1−(1−a)ⁿ and produces bright seams. Rule: blur ≥ 0.5 × step arc length.

Persistent agent states cap at α ≤ 0.18, where the printed wheel labels stay at 3.37:1. Only transient acting states may obscure them.

Tactility

Shimmer is accelerometer-driven, never baked: DeviceOrientationEvent beta/gamma → light vector, low-pass filtered so it glides. Never request on load — iOS rejects a non-gesture call and the attempt is spent. Ask once, at first pointerdown on the wheel ring; never re-ask if denied; fall back to a static 135° key light with full specular, never a flat surface.

Agent actions are silent and never vibrate

Haptics and the clicker are the signature of a hand. If the agent buzzed the device, the user would reach for a phone nobody touched. Enforced at one call site — detent() already carries source, so both the clicker and haptic.trigger() gate on source !== 'agent' && source !== 'system'.

This is attribution channel 7, and the only one that works with the phone in a pocket.

09The agent surface

The single most misunderstood part of this product. Read this section before writing any agent code.

WebMCP has no permission model

There are no per-tool grants, no session/always/never scopes, and no protocol-level consent prompt. registerTool() makes a tool permanently callable; the only withdrawal is aborting its AbortSignal. There is no destructiveHint — annotations carry only readOnlyHint and untrustedContentHint. "User activation" appears nowhere in the normative spec.

The spec disclaims the area itself: "the spec does not include normative guidance against the misuse of tools that expose sensitive or high-privilege operations."

What follows from that

  • There is no confirm-before-tool-call screen, because there is no point at which the page could intervene. The call already ran; the page finds out by being called.
  • The honest substitute is gate nothing · show everything · make it undoable. Results land as reviewable proposals, governed by Assistant changes · Review first / Apply directly.
  • The front face has no confirmation surface at all — not for agents, and not for humans either. A modal in front of a fully undoable action is friction with no safety in it.
  • The page cannot detect that an agent is present. No attach event, no idle signal. It learns one exists only when a tool executes — so "agent idle" cannot be rendered, because it cannot be known.

The agent flag

// one boolean, two edges — not a state machine
ON   ← a tool call happens while the flag is OFF
OFF  ← a trusted user interaction happens while the flag is ON

It means who acted most recently — not who is present, not who is permitted. Because any human interaction flips it off, the human never has to reclaim control; touching the device is the reclaim.

isTrusted is true for automation-injected input, so this flag is a best-effort display heuristic and never a security boundary. Do not build authorisation on it.

Banned vocabulary in agent-flow copy — merge blocker

allow · deny · permit · permission · grant · authorise · request · ask · waiting · pending · approved · blocked

L0 — never imply a permission that does not exist.

The reviewer's question

On this project the plausible-looking answer has been wrong more often than the awkward one. Three drafts invented a permission model. One invented an agent-presence signal. One put the human's feedback underneath their own thumb. One gave the agent a voice you could feel.

Every one of those was internally coherent, and every one was fiction. So treat "this looks right" as the beginning of the check, and ask of any indicator: which API supplies this fact?

One gate cannot be met at a desk: the occlusion check must be done on a phone, in hand. A desktop review cannot pass it.

Gates every screen must pass

  • Reviewed in both colourways in one sitting — not on different days, where drift hides.
  • Greyscale attribution test: desaturate; human and agent must still be distinguishable. Hue is the 6th of 7 channels and never load-bearing.
  • prefers-reduced-motion and prefers-reduced-transparency variants both specified and built.
  • 44px minimum touch targets, wheel quadrants included.
  • Contrast floors: 4.5:1 text, 3:1 non-text UI. Agent text on light is green-800, never 700.
  • Every state present: loading · empty · error · offline · agent-active · success.
