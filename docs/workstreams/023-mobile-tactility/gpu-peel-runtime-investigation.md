# Native peel runtime investigation

Read-only investigation, 2026-09-11. Observed application revision: `f89be7f`. No application edits, browser actions, new trace, or performance acceptance. The lead observed successful native NightShift pickup/drop and packet replacement, with effective worker rendering and no fallback.

## What the observation establishes

Source evidence: `/tmp/webpod-sticker-frame-probe.json` and observer `/tmp/webpod-sticker-frame-probe.ts`; screenshot `/tmp/webpod-raw-current.png`. This was the development server under 6× CPU throttling. The roughly 4.07-second observation contains:

- Pointerdown processing about 51.6 ms inside React `dispatchDiscreteEvent`; Event Timing duration 256 ms.
- A subsequent 205 ms script in Scheduler `performWorkUntilDeadline`, in a 206 ms long animation frame. Maximum observed RAF gap 183.8 ms.
- A later 52.2 ms scheduler script.
- A later 30.3 ms `sticker-transaction-broker.ts` Worker message callback, within a 51.6 ms long animation frame, alongside a separate 9.2 ms scheduler script.
- Pointerup Event Timing duration 40 ms. Reported forced style/layout duration was zero for these scripts.

There are no sampled stacks, component render durations, transaction kind/ID, or callback child spans. In particular, **205 ms cannot be assigned to a specific component, geometry operation, or library list from this evidence**. Event Timing includes waiting for presentation and is not synonymous with handler CPU. Development/StrictMode overhead is not quantified; dividing by six would not establish production performance.

## Concrete peel path

1. `apps/web/src/sticker-collection.tsx:563` dispatches the slot pointerdown to `begin` and `start` (lines 210–229). The handler admits intent, clears details, resets carry, selects the art, captures the pointer, stores the initial pointer sample, publishes the peeling stage, and triggers pickup haptics. Reset and selection publish separate public-store transitions. These are synchronous semantic actions; normal React batching does not erase the synchronous Jotai notification work.
2. `apps/web/src/sticker-interaction.ts:55` resets several scalar atoms and republishes interaction; `updateStickerInteraction` at line 37 creates a new interaction object. The cold sheet pickup has no existing placement, so the conditional `commands.project` in `start` is skipped. Attributing a dense placement raycast to this pointerdown would be incorrect.
3. `ProductionDeviceView` (`apps/web/src/production-device-view.tsx:129–184`) subscribes to the entire interaction plus drag, sheet, workspace, and pack atoms. Each such render reconstructs `preparedSheet` and an inline `stickerScene`, and renders the composite and collection subtree. `StickerCollection` separately subscribes to interaction and projection-version changes (`sticker-collection.tsx:96–121`), and renders slot controls, presentation styles, and editor UI. These are concrete paths into React work after pickup, but their individual cost remains unmeasured.
4. `packages/composite/src/WorkerDeviceCanvas.tsx:27` forwards the latest scene in a layout effect dependent on the whole props object. `device-render-host.ts:182` synchronously fans that update to warmup, workspace, carry, equipped, and pack owners. Consequently, even a pose-only parent render runs each owner's admission logic. The pack owner constructs a recipe/key, offers a latest-only pose, and only prepares resources when its resource key changes (`native-pack-controller.ts:16–35`). The equipped owner has the independently verified semantic duplicate guard. It is not correct to infer that every render recompiles every sticker.
5. Native carry requests are deduplicated by exact input/revision (`native-carry-controller.ts:53–61`). The existing carry worker performs deformation and packed query bounds. A completed candidate goes through `native-carry-resources.ts:16–25`: private geometry acquisition, `preparePrint`, and private renderer damage delivery. Main adopts a lightweight query mesh only after renderer acknowledgement. Old displayed geometry remains retained until replacement.

The GL `StickerPackScene` / `PeelingPrint` React geometry path is not mounted as the rendering path when the native backend is effective. It must not be blamed for the native scheduler task. Similarly, `stickerCollectionsAtom` depends on inventory, not every peel pose (`sticker-collections-model.ts:49`); the 2,726-song library count does not demonstrate a song-list rebuild on pickup. `ProductionPanelView` is memoized. No observed stack connects that library to the measured task.

## What the broker callback actually does

`packages/device/src/sticker-transaction-broker.ts:101–117` distinguishes delivery acknowledgement from canonical computation result. A delivery acknowledgement resolves its promise. A canonical result calls `complete` (line 86), which stores exact buffers, resolves waiters, and **synchronously calls `pump`**. Pump can evict/admit the next job and call `Worker.postMessage` before the original callback returns (lines 120–148).

Thus the 30.3 ms may include result bookkeeping, bounded admission/eviction scans, and next-job structured cloning. The source does not reveal which branch/job the observed event used. Accounting enumerates buffer identities and byte lengths, not pixel values; it does not recompute damage fields. Repeated `storageCharge` calls inside eviction/admission are avoidable repeated metadata work in principle, but the collection is bounded and their contribution has not been timed.

For carry prints, `sticker-prepared-damage.ts:35–85` obtains cached artwork alpha, requests damage then exact contour computation from the same producer, and creates borrowed BufferAttribute/DataTexture wrappers. The main does not copy dense geometry in `borrowGeometry`. Contours referencing a live canonical damage entry avoid cloning the field; carry positions/UV may still need an independent structured clone when no canonical surface ID exists. That clone preserves ownership and is a plausible dispatch cost, not proof of the measured 30.3 ms. Moving full damage/contour mathematics is not a justified next change: they already execute in the worker on the healthy path.

## Narrow next step

No production code change is justified specifically as the fix for the 205 ms task yet. The smallest useful next measurement is one matching peel with component/commit and host-owner spans, plus broker spans recording only transaction kind/ID, input byte count, complete/admission/postMessage duration. Measure React render versus layout-effect host fan-out separately; keep all dense arrays/artwork contents out of diagnostics. Include initial down, first carry adoption, final drop, and replacement; a stationary comparison distinguishes projection-driven notifications from actual input changes.

A supported candidate for a subsequent narrow optimization is to isolate pose-only scene forwarding from the broad production React render: retain the same per-device Jotai authority, preserve current initial state/cleanup and immediate pointer semantics, and keep React subscribed to genuine UI/admission boundaries. Start with the measured hot subtree or host owner, not a wholesale rewrite. Merely memoizing an object containing changing peel/drag values will not eliminate those updates. Likewise, moving `pump` to a later task only redistributes latency; it should be considered only if dispatch spans show a long synchronous clone and candidate readiness/ordering remains correct.

Any change must retain exact source-to-carry handoff, public/WebMCP state, synchronous trusted-input actions, current displayed owners, final sample, cancellation, full packet replacement and fixed byte caps. The successful native drop is behavioral evidence; the observed gaps remain unresolved performance evidence.

The one 84 ms long task contains a 78.5 ms WorkerDeviceCanvas layout effect / host update, with 73 ms in its synchronous `host.carry` child and 5 ms in pack. ProductionDeviceView own render max was 1.5 ms; StickerCollection own render max 7.5 ms. Broker pump max 3 ms, admission max 2.1 ms, postMessage max 1.5 ms, complete max 1.8 ms. The host module reached its 512-entry cap; later missing host spans do not mean no later work. The valid first long span occurred before the cap. This capture does not reproduce or explain every previous broker timing, but it falsifies broad component rendering or the transaction broker as the dominant cause of this particular long task.

### Exact synchronous carry initialization boundary

`native-carry-controller.ts` update → request → `createCarryPreparation.request` → `dispatch` remains synchronous until the first actual carry is posted. The request carries a small scalar/artwork-metadata descriptor; its JSON keys contain no artwork pixels. The first dispatch creates the sole carry Worker and initializes its immutable assembly context (`sticker-carry-preparation.ts:83–121`).

That initialization invokes `transferPaperGeometry(rear)` (`sticker-paper-transfer.ts:24–30`), which uses `Float32Array.from` for positions/normals/UV and `Uint32Array.from` for indices. It then posts the resulting context without a transfer list. The newly allocated rear arrays therefore undergo another structured clone, alongside a structured clone of the borrowed packed collision snapshot. Snapshot itself is a borrowed reference (`sticker-collision.ts:95–98`), not a recomputation. Copying/cloning the complete assembly context occurs inside the measured carry span before the normal scalar pose message. The capture does not split 73 ms into Worker construction, explicit copies, clone, recipe/query admission, or serialization; assigning all 73 ms to a single instruction would overstate the measurement. The dense double-copy operation is nevertheless directly established by source and is not required semantic UI work.

No deformation, damage calculation, or collision-tree rebuild should be moved back to main. Existing first-source retention and latest-only carry pose behavior are already correct and must survive the fix.

### Minimal proposed corrective scope; not implemented

Prefer direct delivery from existing canonical worker authorities. The immutable assembly broker already supports private MessagePort delivery, but its current payload is the *whole* prepared device including unrelated textures/hardware (`device-preparation-data.ts`, `immutable-shell-worker.ts`). It has no rear-only lease. The collision producer transfers its result to main then terminates in `finish` (`sticker-collision-preparation.ts:31–34`); it currently retains no canonical snapshot and offers no private port API. A claim that complete direct worker-to-worker carry context can be wired using existing unchanged APIs would therefore be false. Adding that path requires explicit broker lifetime/accounting scope, not simply requesting another full-device renderer lease and ignoring unused resources.

The least-churn feasible correction is bounded one-private-snapshot preparation inside the existing carry owner, followed by a single transfer of its owned buffers. Replace the current rear-copy-then-clone boundary with exact chunked private copies of rear attributes and packed collision arrays; transfer those private arrays once to the existing carry Worker. Borrowed public query buffers must remain attached. Schedule preparation when the already-admitted visibility assembly becomes available, but ensure a genuinely cold pointer request only publishes the latest scalar intent and schedules that work; it must never synchronously drain a copy or await context preparation in the input callback. This removes a real extra rear copy and bounds remaining main work, rather than merely hiding the original long task earlier. Do not increase memory caps.

Suggested narrow ownership: `sticker-carry-preparation.ts` for context job/generation/admission, a small adjacent private-context copy helper if needed, `native-carry-controller.ts` for proactive preparation from the existing visibility owner, and `sticker-carry-worker.ts` only if explicit context acceptance is needed. Preserve zero-argument GL behavior and renderer failure policy. The existing copy-on-serialization helper is shared by worker output paths: changing it globally to return borrowed arrays would be unsafe.

Required independent proof: actual authored rear geometry and packed collision bytes equal on receipt; Float32/Float64/index representations unchanged; every private context buffer transferred exactly once and every borrowed buffer intact; no second producer; one active context preparation plus latest requested generation; fixed byte admission covering pending and installed context; copy chunks bounded with an initial yield; cold request cannot run any bulk copy synchronously; changed assembly/visibility, hide/resume, cancellation midway, late worker acknowledgement, failure, and disposal release exactly once with final zero; previous displayed source remains valid through delayed first result; final pending pose still drains. Existing real private-carry and geometry parity proofs plus matched production pickup/drop and first-input observation close the gate. Merely prewarming while leaving an unbounded cold path does not.

### Separate rotation input boundary

Read-only companion evidence `/tmp/webpod-native-production-rotation-verified-frame-probe.json` reports 71 ms and 67 ms tasks. Within them: DIV pointerdown 23.4 ms, CANVAS pointerdown 37 ms, CANVAS pointermove 45.2 ms in the device/composite chunk, plus 21.1 ms in the app chunk. These callback names and separate chunk locations narrow owners, but minified names alone do not uniquely prove every source instruction.

The native input adapter (`device-native-input.ts:63–89`) raycasts both registered shell meshes on down and hover move. Its `active` map tracks wheel/select only. After the app accepts an orientation grab, every captured orientation pointermove still enters the native hover path, because `acceptsDeviceOrientationHover` accepts touch and the adapter has no orientation-capture ownership flag. The app's separately installed orientation move listener (`device-preview-orientation.ts:362–376`) then applies the same sample to rotation. This is a concrete duplicate-purpose boundary: hover raycast/affordance updates continue during a gesture that already owns the enclosure. A minimal separate candidate is to track only this adapter's accepted orientation pointer and suppress its hover picking until matching release/cancel/lost capture, leaving the app's exact sample/velocity path untouched. Test concurrent pointers, declined grabs, wheel/select capture, front/rear admission, release outside, dispose and cursor restoration. Do not globally suppress hover based on unrelated pointer capture.

Down still requires exact shell picking and activation. Shell picking may use its prepared index or exact Three fallback; readiness at the observed sample was not recorded. Installed Three185 `Raycaster.intersectObjects` calls each object's custom raycast and sorts results; the custom prepared shell implementation delegates candidate leaves to exact Three Mesh.raycast (`shell-picking.ts`). A full dense fallback at this moment is possible but unproven. Do not replace it with approximate bounds to improve timing.

A source candidate for the DIV capture callback is `attachInteractionAudioRuntime` (`interaction-audio.ts:801–813`), which calls activation on trusted down. First activation constructs the backend and synchronously calls resume (`interaction-audio.ts:578–614`); those actions must preserve user activation. No audio changes are proposed from this evidence. The minimal rotation scope should first remove the proven redundant hover work, independently measure remaining exact down/query and required activation costs, and keep public orientation updates immediate.
