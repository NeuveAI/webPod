# Non-sticker interaction architecture mapping

Read-only investigation on 2026-09-07. This document records the existing implementation before the WebMCP work; it is not a claim that proposed integrations or regression commands have been implemented or run. No sticker implementation was changed. Paths below are relative to the repository root, `/Users/vinicius/code/webPod`.

## Five physical buttons and shared effects

`packages/composite/src/CompositeDevice.tsx` owns the private `CompositeInputController` and its `handlers`, `dispatchPhysicalPress`, `attach`, and `attachKeyboardControls` methods. Its attachment creates the wheel and interaction-audio runtimes, installs browser listeners, and disposes listeners, audio, gestures, and attachment state together. Async transport acknowledgments are protected by an attachment-generation check.

| Button | Existing human path | Semantic result |
| --- | --- | --- |
| Center | `onSelectStart` → audio down; accepted `onSelectEnd` → audio up → `pressActionAtom` | Emits `navigationIntentAtom`; Panel resolves list selection or Now Playing mode/action. Enter uses keyboard contact edges. |
| Menu | Cardinal start/end → audio contact edges → `onCardinalPress` → `dispatchPhysicalPress` → `pressActionAtom` | Pops the navigation stack, or restores standard Now Playing mode first. A hold of at least 600 ms calls `returnToRootActionAtom` and suppresses the subsequent short press. Escape/Backspace use the same short/long semantics. |
| Previous | Cardinal contact edges → `dispatchPhysicalPress` → `onTransportPress('previous')` | Production skips the provider queue when eligible; accepted transport records `acceptedExternalPressActionAtom`. A false result falls back to `pressActionAtom`, which pages the list backward. PageUp is the keyboard equivalent. |
| Next | Cardinal contact edges → `dispatchPhysicalPress` → `onTransportPress('next')` | Production skips the provider queue when eligible; accepted transport records `acceptedExternalPressActionAtom`. A false result falls back to `pressActionAtom`, which pages the list forward. PageDown is the keyboard equivalent. |
| Play/pause | Cardinal contact edges → `dispatchPhysicalPress` → `onTransportPress('play-pause')` | Production toggles playback and shows Now Playing. Accepted transport records `acceptedExternalPressActionAtom`; false results do not fall back to list navigation. Space is the keyboard equivalent. |

`apps/web/src/production-device-view.tsx` supplies the live transport callbacks through `toggleProductionPlayback` and `skipProductionPlayback`. Its provider write queue serializes commands; skip during loading waits for an actual playback-context change. Reproducing transport calls directly inside tools would bypass these behaviors.

**Physical actuation, contact audio, and semantic callbacks are distinct.** `packages/device/src/click-wheel-input.tsx` calls `controlPhysics.pressWheel` for the ring and `controlPhysics.pressSelect` for the center, followed by release/cancel paths. `packages/device/src/control-physics.ts` owns bounded physical travel and release animation. Calling the composite callbacks alone does not actuate those visual controls; calling state actions alone misses both physical travel and button contact audio. A tool needs a typed actuation entry point at the mounted physical control owner, feeding the shared semantic controller with explicit agent provenance. It should not fabricate browser events or label itself human.

## Sound and provenance

The composite controller feeds `InteractionAudioRuntime.buttonDown` and `buttonUp`; wheel sound subscribes to `interactionFeedbackAtom` through `attachInteractionAudioRuntime`. Existing policy blocks agent sound in two places: `packages/state/src/silence.ts:isSilenced` suppresses agent feedback budgets, and `packages/composite/src/interaction-audio.ts:scheduleWheelEvent` rejects nonhuman actors. The current user request explicitly supersedes that silent-agent policy. Update sound eligibility coherently while retaining the actor generated by `actorFor`, including `agent:unknown` when caller identity is unknown.

The audio runtime exposes activation state and structured silent/deferred/unavailable results. Browser autoplay restrictions cannot be defeated by synthetic input; tool results should report actual audio availability rather than promise audible output before activation. Preserve the user's sound-enabled setting and the existing contact/voice resource limits.

## List traversal and selection

`packages/state/src/store.ts:detentActionAtom` is the authoritative reduction, clamping, feedback, and announcement path. `packages/state/src/detent.ts` already has a `path: 'direct'` branch: it consumes discrete detents with no acceleration. This is a better candidate for paced agent traversal than raw mouse/trackpad gestures. Dispatch one signed detent per scheduled step with agent provenance, accelerate by reducing the interval, and enforce at least 200 ms between applied steps. Own abort, disposal, and competing-input cancellation; do not let catch-up scheduling produce bursts after a stalled frame.

`packages/composite/src/click-wheel-runtime.ts:createClickWheelRuntime` owns human arc/wheel lifecycle and coast frames and currently hardcodes human provenance. Its uncontrolled acceleration/coasting is unsuitable for guaranteeing the agent's five-items-per-second ceiling.

`currentScreenAtom` supplies the complete `ScreenFrame.rows` and `highlightIndex`; `screenSnapshotAtom.rows` is only the visible window. Full-list output must use the former, with separate `selected` and `items` attributes and the selected row retained in `items`. Define position indexing explicitly. Now Playing queue selection is distinct from ordinary frame rows and needs its own projection if exposed as a list.

`pressActionAtom` emits selection intent; `packages/panel/src/Panel.tsx:PanelSurface` consumes it and calls `selectNavigationImmediate`, pushes loading/result frames, resolves pending relationship requests, tracks playback attempts, and handles center-driven scrub/queue modes. Tools should enter the same center action and observe readiness rather than reproduce navigation branches.

## Readiness gaps

- `packages/panel/src/navigation.ts` exports `isNavigationLoadingFrame` and `navigationLoadingRequestId`. Request identity survives frame normalization and supports rejecting stale resolutions.
- `NavigationLibraryCollectionStatus` contains only `loaded` and `state: 'loading' | 'complete' | 'error'`. There is no total denominator. `apps/web/src/music-runtime.ts:createProgressiveAppleSource` updates collection counts/revisions as pages arrive. An in-progress percentage is therefore unknown, not zero or an inferred percentage.
- Provider playback status contributes loading/error/playing/paused information, but Panel additionally owns private `playbackAttemptAtom` (including pending/rejected) and `queueViewAtom` (including queue loading/error). Omitting these can falsely report readiness.
- `MusicRuntimeSnapshot.phase` and account status cover signing-in, signed-out, permission-denied, and errors. Background library loading can coexist with an interactable page and should be distinguished from interaction-blocking loading.
- There is no shared monotonic loading-start/elapsed tracker. Add request-scoped timestamps and a shared readiness projection at the panel/runtime boundary. Polling should report elapsed time from the operation's start, not restart a timer on every tool call. Report unknown percentages explicitly; avoid exposing arbitrary wait suggestions as readiness facts.

## Orientation, flick, and production lifecycle

`apps/web/src/device-page.tsx` owns `previewStore` and mounts `bindDeviceOrientationControls` in an effect. `apps/web/src/device-preview-orientation.ts:createDevicePreviewStore` exposes `setOrientation` and `setPose`; the orientation is `{pitchDeg, yawDeg, rollDeg}` and writes are finite-checked/clamped. Define tool x/y mapping and relative-versus-absolute semantics explicitly.

`bindDeviceOrientationControls` owns active grabs, bounded release animation, cancellation, reduced motion, and disposal. External orientation writes cancel its ongoing motion. `apps/web/src/device-orientation-motion.ts:beginDeviceOrientationRelease` and `advanceDeviceOrientationRelease` implement the existing opposite-face spring. Expose a semantic flick operation through that scheduler rather than instantly choosing a pose or reproducing its spring.

Mount tool registration in the production `DevicePage` lifecycle and pass a typed physical-actuation handle out of the composite boundary. Keep readiness of that handle explicit and cancel/unregister on disposal. The development-only `window.__webpodDevicePreview` API is not a production tool integration surface. `ProductionDeviceView` supplies live provider callbacks and `ProductionPanelView` supplies the actual provider/navigation source, so tool dependencies should track those owners rather than capture stale provider objects.
