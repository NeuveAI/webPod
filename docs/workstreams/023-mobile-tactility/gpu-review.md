# Independent GPU and worker architecture review

Status: architecture direction conditionally accepted; implementation and full-goal acceptance PENDING. WEBPOD-CPU-007 is in progress. This reviewer read the complete scope and both audits, checked installed Three 0.185.1/Fiber 9.7 source and the primary HTML-in-Canvas proposal, and authored no implementation. Moving CPU-006 changes have not been reviewed; review starts only after its frozen handoff.

## Placement decision

The audits correctly separate GPU raster/shader execution from CPU traversal, React reconciliation and render submission. OffscreenCanvas can relocate submission, while a renderer rename cannot relocate DOM layout or remove main-thread geometry work. Preserving immediate Jotai/tool/media state on main and moving immutable preparation, transactional geometry and render submission behind versioned ownership is appropriate. Preparation alone does not satisfy the full requested architecture.

Installed Fiber createRoot accepts an OffscreenCanvas and explicit size/DPR, with asynchronous renderer configuration. Its RootState gl type remains WebGLRenderer, and existing application material/readiness/InteractionManager consumers are not backend-neutral. Use a discriminated rendering service; do not hide the mismatch behind casts. Worker createRoot must provide worker-safe event management and numeric size/DPR. The standard DOM Canvas wrapper and its measurement/event wiring cannot simply be moved into the worker.

WebGPURenderer's WebGL backend fallback still consumes node materials; it does not execute the current custom GLSL hooks. Therefore worker WebGL using the existing shader path is a valid separately gated stage while node-material parity is established. All physical glass/LTC, sticker appearance/wear, paper deformation, LCD decoding and PMREM variants listed by the audit are mandatory migration work. GPU selection by navigator.gpu alone is rejected.

## Concrete lifecycle omission to address

Fiber's installed events ESM unmountComponentAtNode (around line 15971) waits 500 ms, disconnects events, disposes renderLists/scene and optionally calls forceContextLoss. It does not call gl.dispose. Three's common Renderer.dispose (around line 2533) releases backend, animation, geometries, pipelines, nodes, bindings, textures and framebuffer resources. The renderer worker host must explicitly own backend disposal after React/resource teardown; root.unmount alone is insufficient for WebGPU. Also guard asynchronous init/compile completion after cancellation: a late initialized backend still needs disposal and must never publish readiness. Document ordering so immediate worker termination does not conceal unacknowledged GPU/resource cleanup.

A single renderer-generation authority must cover backend/context loss, canvas replacement, geometry/texture adoption and pending panel snapshots. Gesture epochs are insufficient. Fresh-canvas fallback after transferControlToOffscreen must preserve the existing semantic DOM panel, focus, pointer-capture cancellation and media state; test replacement during active input as well as idle.

## Native screen transport gate

The proposed ElementImage route is plausible but remains a real-browser capability gate. The primary proposal specifies capture from a paint event, transferable snapshots, and asynchronous worker-to-DOM geometry updates with an elementgeometryupdate event. Staging draws must suppress automatic geometry changes, or a texture-staging operation can modify the live panel's hit geometry. The proposal's overloads and deployed browser signatures can differ; select verified overloads without treating a generic method-presence check as support. [Primary proposal](https://raw.githubusercontent.com/WICG/html-in-canvas/main/README.md).

Successful transfer or a nonempty bitmap is insufficient quality proof. Compare complete native raster dimensions, glyph edges, alpha/premultiplication, orientation, color decoding exactly once, clipping/overflow and filtering under the actual glass. Resource ownership must close overwritten/rejected/consumed ElementImages and any ImageBitmaps; bound both count and bytes. A pending resize/paint generation may not upload stale pixels to a new-size texture. Preserve a valid previous frame while preparing a replacement, or use the equivalent main-renderer fallback. The lead reports a current staging overload failure; this review neither re-ran that probe nor interprets failure as proof that all worker transport is impossible.

Submitted GPU commands, queue completion, posted messages and worker RAF callbacks are not presentation acknowledgements. The audit correctly calls this out, but implementation still needs an executable contract pairing displayed pose, native hit geometry and input routing. Test rapid direction changes, clickwheel admission, pointer capture/release, resize and loss/recovery. Asynchronous elementgeometryupdate alone proves DOM geometry application, not physical presentation. Do not silently weaken exact hit alignment to accept worker rendering.

## Preparation and compute acceptance checklist

CPU-006 must retain expanded geometry attributes, topology/order/groups, bounds and every procedural texel; texture adoption must preserve channel type/format, colorSpace, wrapping/filtering, flipY, premultiplication, anisotropy and mip generation. A DataTexture replacement is not equivalent merely because numeric channels match. Browser-only text/font raster is an allowed documented split only with exact pixel evidence; unrelated dense numeric fields remain off main.

Broker admission must bound queued bytes as well as job count and prevent subsystem-wide fallback oversubscription. Execution deadlines must begin at execution, distinguish queue delay from worker failure and never start duplicate monolithic main work. Cooperative fallback must yield inside dense vertex/texel/normal/indexing loops; timers around old constructors do not meet the requirement. Native allocations/sorts and a single oversized generator step remain possible long tasks and need measured maximum-step evidence.

Check shared cache ownership across StrictMode, same-form devices, discarded Suspense renders, form replacement and unmount. Transferred buffers must be private to the sending job; adopting them cannot detach displayed resources. Immutable source bytes, worker intermediate bytes and GPU resources have different lifetimes. A complete prepared asset recipe/version must key reuse, including finish-dependent texels and custom form fields. No geometry or texture swap may occur after warm-ready without an explicit new generation.

Packed collision and transactional sticker preparation are necessary remaining slices, not exemptions justified by the current scene API. Preserve exact provenance, side/alpha admission, source/target wear identity, latest valid final release and persistent-state publication only after the current transaction succeeds. Existing CPU worker/cooperative math is the parity reference for any GPU compute path; avoid synchronous dense GPU readback on the input path.

## Chrome 152 hit geometry: achievable submission invariant

The associated-canvas worker WebGPU snapshot upload now passed the lead's bounded probe, as recorded in gpu-browser-evidence.md. This supersedes the earlier pending upload gate, while full screen/color/material fidelity remains pending.

The installed browser version matters: Chrome 152.0.7977.83 OffscreenCanvas IDL exposes getElementTransform(element, draw_transform), but no updateElementGeometry/clearElementGeometry or geometry-update event. Its HTMLCanvasElement IDL likewise exposes the getter plus paint/requestPaint/captureElementImage. The newer proposal's worker-to-DOM mutation mechanism is therefore not a usable assumed primitive for this browser. [Pinned OffscreenCanvas IDL](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.83/third_party/blink/renderer/core/offscreencanvas/offscreen_canvas.idl), [pinned HTMLCanvasElement IDL](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.83/third_party/blink/renderer/core/html/canvas/html_canvas_element.idl).

Pinned OffscreenCanvas C++ validates a live ElementImage from the matching placeholder canvas and returns the derived DOMMatrix. It does not apply DOM geometry. Consequently, associated native snapshot upload solves source lineage, but does not eliminate the main-thread transform message. [Pinned implementation](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.83/third_party/blink/renderer/core/offscreencanvas/offscreen_canvas.cc).

The current baseline does not have a physical-presentation acknowledgement either. Installed Three InteractionManager.update (lines 129–206) derives the CSS matrix from the viewport, projection, camera inverse, mesh world matrix and element-to-plane mapping, then writes element.style.transform. The current screen callback runs during onBeforeRender. GPU execution and compositing still occur asynchronously afterward. Requiring proof of physical scanout from a worker would impose a stronger, unavailable guarantee than the baseline.

An executable worker contract should preserve **submission coherence**, while separating transactional acknowledgements from steady rendering:

1. Main retains immediate authoritative UI/tool state and separate last-submitted visual/admission state. Each render packet carries renderer epoch, pose sequence, viewport/density generation, panel layout/raster generation and the snapshot actually selected for that frame.
2. Worker derives both draw matrices and the complete native-hit/projection bundle from that immutable packet. It submits the render and emits that bundle with matching stamps. Autonomous animation may continue from the last accepted semantic command without awaiting main React. Ordered release/cancel commands retain their sequencing.
3. Main rejects wrong-epoch or wrong-viewport replies, then applies CSS geometry and native admission/projection records together in one task without awaiting unrelated work. It must never apply independently calculated latest-intent geometry to an older submitted frame. Geometry notifications can use one message in flight plus one replaceable latest pending bundle; an acknowledgement releases notification credit, not render-loop credit. Newer animation frames may continue while intermediate geometry notifications are coalesced.
4. Resizes/context replacement clear credits and old replies, establish a fresh viewport/panel generation, and wait for its valid paint before upload. Context loss and unmount close resources and prevent queued old callbacks from changing the new canvas.

This bounds notification memory and prevents mixed-generation admission records, but does not bound wall-clock staleness while the main thread is stalled. Rendering may progress beyond the latest applied DOM transform during that interval; input handlers cannot execute on the stalled thread either. When main resumes, the order of pending input and geometry delivery must be tested. A strict per-frame main credit would eliminate render-ahead but re-couple autonomous animation to main-thread stalls; it is an explicit diagnostic/alternative tradeoff, not the recommended unconditional scheduler. Neither mode proves compositor presentation. That is an empirical acceptance boundary: compare baseline and worker native hit corners/click targets during rapid turns, edge/front/back crossings, resize, keyboard interruption and pointer capture. Retain stamped diagnostics for submitted, applied and pending generations; verify at most one in-flight geometry notification and one latest pending bundle, no unbounded queue, and prompt convergence when main resumes. Reserve blocking acknowledgements for renderer/resource/resize transactions whose dependent work is invalid until adoption; do not freeze every steady worker frame on a main acknowledgement. If observable hit behavior regresses, revise presentation coordination or retain the equivalent main submission tier; do not redefine the product's interaction contract to hide the gap.

No physical-present acknowledgement is required for architecture acceptance. Correct shared transforms, bounded submission/apply sequencing, identical steady and interrupted native hit behavior, and explicit context/resize generations are required. CPU-006 implementation review remains pending its frozen handoff.

## CPU-007 worker-host plan pressure test

Reviewed gpu-renderer-host-plan.md against the current scope, CompositeDevice portal/input lifetime, CompositeCoordinator attachment state, HTML-in-canvas paint/geometry path and renderer defaults. This is architecture review before implementation, not review of CPU-010's moving source or approval to activate a native renderer.

The proposed imperative worker owner and shared scene descriptors are an acceptable implementation direction. A renderer-neutral discriminated boundary is necessary; a cast of Fiber's WebGL renderer would not preserve the current screen/material/readiness contracts. Main needs a prepared query view and scalar transform adoption, not a duplicate render scene whose full hierarchy is rebuilt or traversed each frame. Static descriptor parity must include control assemblies, all inserts, every sticker layer, material recipes, texture metadata and authored light identities. GL fallback must consume the same definitions. Preserve AgX, exposure 1, transmission resolution scale 1 and the existing physical backing/raster resolver explicitly, rather than inheriting a different backend's defaults.

The following refinements were sent to the host author before implementation:

- Ordered release/cancel commands must carry the exact final pose/sample or identify a barrier that the receiver can satisfy. Separate latest-only pose coalescing and command queues must not let a final action consume a newer or missing pose. Pose, gesture, layout and resource generations form one admissible transaction; projection notifications cannot authorize persistence.
- Native capture ownership begins before an asynchronous capture finishes. Account for its reserved count/bytes until resolution, stamp its target texture/layout/canvas generation, and close stale results after resize, hide or disposal. A dirty flag is not another captured resource. Generation changes must not silently reset counters while old captures remain unresolved.
- Preserve the same React portal host and CompositeInputBoundary across native-to-GL replacement. Current CompositeDevice renders the portal only when tier is T1; reusing the existing context-lost tier transition without changing that contract would unmount Panel. The new generation must not duplicate media/input runtimes, lose logical focus/state, or leave a held pointer/control pressed. Cancel incompatible held gestures explicitly while retaining authoritative application state.

Associated canvas lineage is mandatory, but does not supply a worker-to-DOM mutation API in the pinned Chrome build. Apply the submitted projection bundle and query state together on main; use resource/resize acknowledgements for dependent resource work and separate coalesced projection notification credit. Do not make steady animation wait for React or main acknowledgement. This keeps worker animation independent and memory bounded, but matching sequence numbers alone cannot guarantee input arriving before a queued projection message will hit the latest visible pose. The existing-route rapid-motion, edge/front/back crossing, resize, capture and resumed-input comparisons remain activation gates. No unavailable physical scanout acknowledgement is demanded.

Recovery should be a single generation transition with one stable authority: retire native, reject late worker and capture results, release explicit GPU/texture/geometry leases, reconnect the same Panel to a fresh GL canvas, and establish fresh paint/readiness. The current coordinator's screen/context references are local GL objects, so the new discriminated attachment must replace both atomically instead of carrying a stale screen handle into the fallback. Resource preparation may overlap recovery only through bounded broker leases; it must not detach a mounted query cache or restart dense main-thread factories.

Plan verdict: acceptable direction to implement after these protocol details are explicit; native activation and whole-goal completion remain pending actual source review and integrated evidence. No application changes, browser activity or performance claim were made by this review.
