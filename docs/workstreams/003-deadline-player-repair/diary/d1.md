# D1 diary — playback/data truth and stable-selection preparation

**Date:** 2026-09-03
**Implementer:** `/root/d1_playback_truth`
**Status:** correction round complete; independent re-review pending

## Outcome

The panel now preserves the exact selected queue occurrence before playback settles. Pending, rejected, timed-out, and later provider-error states retain the selected title, artist, artwork, queue position, and source context while presenting the transport outcome inline. Confirmed metadata replaces this retained model only when it comes from authoritative provider state.

A stable highlighted selection now starts preparation at exactly 700 ms. Identical panel leases coalesce, changing the selection cancels the prior timer and aborts or ignores stale work, and route cleanup releases both timers and active intent. Relationship data and artwork may prefetch broadly; Apple queue preparation uses only the public queue API and only when the player is truly idle.

## Implementation decisions

- Added a provider-level `prepare` contract that promises readiness work only. It deliberately makes no claim about buffered media, audible playback, or a number of prepared seconds.
- Implemented Apple preparation with exact target keys, in-flight coalescing, generation invalidation, and matching prepared-intent reuse from `play`. A stale or non-matching intent falls back to the existing serialized queue-and-play transaction.
- Refused queue mutation whenever MusicKit reports a current playing or paused item. Preparation never invokes playback and never fetches protected media directly.
- Kept deterministic fixture preparation as a no-op and preserved the stub provider's explicit unsupported-operation protocol.
- Cached selected relationship requests so dwell data work is reused by navigation rather than duplicated on Select. Failed requests leave the cache and may be retried.
- Derived home and nested-preview art from provider entities. If live artwork is unavailable, the panel renders a labeled neutral state instead of fixture art. Exceptional states no longer display invented counts.
- Used the shared Jotai store for the pending/rejected attempt model so tool and UI paths observe the same state. Provider/session/source resets clear stale attempt state.
- Used low-priority artwork fetch as progressive enhancement; correctness does not depend on browsers honoring the priority hint.

## Independent-review correction round

The first independent review found two Major identity gaps. Both were corrected without expanding the lane:

- Playback attempt state now distinguishes request resolution from occurrence confirmation. A retained duplicate occurrence stays authoritative and visibly pending after the transport promise resolves until provider state identifies that exact queue position. A stale copy of the same catalog song at another index cannot clear the attempt.
- Apple prepared-queue identity now includes the target and is checked against the SDK's observable queue/container and start position before reuse. External queue events invalidate an unrelated target. Station start, append, insert-next, skip, and shuffle invalidate and serialize behind any in-flight preparation so delayed preparation cannot overwrite the later user mutation.

Mounted and provider-level falsification tests reproduce both review cases, including completed and in-flight station mutations, before proving the corrected behavior.

## Residual risk

- Real Apple-account validation remains an owner-run browser step because this lane did not inspect credentials or use a live account.
- The public queue call itself cannot be cancelled once accepted by the SDK. Cancellation therefore invalidates intent and prevents later reuse; if the call has already crossed into the SDK, exact-target reconciliation and the serialized play fallback preserve truthful behavior.
- Exact duplicate-occurrence confirmation depends on the provider reporting queue position. If it withholds that position, the panel deliberately remains pending rather than guessing.
- Queue preparation intentionally does not run with a current paused item. This trades speculative latency reduction for the required non-interference guarantee.
- Browser support for fetch priority varies. It is only a scheduling hint; abort and stale-result handling remain the correctness mechanisms.
