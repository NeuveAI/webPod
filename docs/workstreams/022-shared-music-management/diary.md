## Spotify Play/Pause acknowledgement regression

User reported a JSON syntax error through physical Play/Pause after PR#2 publication. Source audit found no opaque identity parsing in common management or Panel. Lead sanitized live stack localized the failure to Spotify api.request JSON.parse, then safely observed PUT/v1/me/player/play HTTP200, no Content-Type,27-character non-JSON response; no payload or headers containing credentials were printed.

Added an explicit command acknowledgement mode to the existing Spotify request helper, preserving its authentication, retry and HTTP error handling. Play/resume and sibling void transport writes (shuffle/repeat/queue append) now consume success status without decoding opaque acknowledgements. Data reads, token decoding and playlist creation retain strict JSON semantics. No identity, common state, server credential or account behavior changes.

Deterministic physical toggle→common manager→actual Spotify adapter test failed before fix for synthetic200 opaque acknowledgement while documented204 passed; after fix both start/pause/resume paths pass. Command success alone still leaves target loading until native confirmation. API tests preserve malformed JSON read/create failures, token validation,403/429/500 failures and one-time401 retry.

User explicitly requested the same Play/Pause verification for Apple. Added three actual production toggle→common manager→createAppleProvider tests using existing MusicKit fixture: normal void native start/pause/resume with confirmation and retained selected counter; rapid second toggle while native start is pending; failed native resume followed by successful void resume. All17 production-control tests pass88 assertions. No Apple/common production source change was needed for these cases.
