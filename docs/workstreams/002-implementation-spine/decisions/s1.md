## D1 — Labelling a *negative* finding `VERIFIED` when Apple never states the negative

**The tension.** The dispatch defined `VERIFIED-docs` as "Apple's published docs state it plainly." Apple nowhere writes "you cannot remove a track from a library playlist." What Apple publishes is a *complete endpoint index* in which no such endpoint appears.

**Original decision.** `VERIFIED-docs`, with the evidentiary shape written out at each affected row.

**Original reasoning.** The Apple Music API reference is an exhaustive enumeration of a closed surface, not prose. Downgrading to `LIKELY` would imply the doc set might be incomplete, making every negative permanently unresolvable.

> ### CORRECTION 1 (revision 2) — the vocabulary was underspecified
>
> The label conflicted with H-2 and disarmed 001 §15.3 failure mode 14. **D-022 ruled**: labels carry two axes — evidential strength and provenance. The rows became `VERIFIED · docs`. **`docs` provenance is never "settled"; only `live` closes a row.** My reasoning had been answering only the strength question while silently asserting an answer to the provenance one.

> ### CORRECTION 2 (revision 2) — two counting errors in the enumeration offered as proof
>
> **"the ten ratings deletions" → nine.** **"exactly three entries" → five** (three endpoints plus two request objects). Neither touches the conclusion; both damage the one thing the argument runs on. Corrected.

> ### CORRECTION 3 (revision 2) — the closed-surface claim was over-scoped
>
> Apple documents API surface in its **guides** as well as its reference index. Scoped each enumeration to the pages actually read.

> ### ⚠ CORRECTION 4 (revision 3) — the reasoning above is FALSIFIED, not merely over-scoped
>
> **The premise "the documented set is closed" is now known to be false on this API.** A live relationship-existence oracle found **three relationships on `Songs` that are absent from the documented set of seven** — `lyrics`, `syllable-lyrics`, `credits` — with negative controls returning `40008` to prove the oracle discriminates.
>
> My original reasoning contained its own refutation. I argued that downgrading to `LIKELY` *"would imply the doc set might be incomplete."* **The doc set is incomplete.** I treated that as an unacceptable implication rather than as a hypothesis worth testing, and I did so while holding a counterexample I had found myself (see D14).
>
> **Consequence, per the lead's ruling: rows 10, 11, 18 and 7 downgrade to `LIKELY · docs`.** The enumeration leg is gone. The second leg — six years of explicit Apple staff statements plus the affirmative *"to the **end** of a library playlist"* — is untouched, which is why they stay `LIKELY` and not lower. **No `supports()` value moves.**
>
> **The rule that replaces it: an absence in Apple's documentation is `LIKELY` at best, never `VERIFIED`.** Only an affirmative Apple statement or a live observation earns `VERIFIED`.

## D4 — Row 20 held at `LIKELY` rather than upgraded

**Decision.** `LIKELY`, `supports("stationSeedFromTrack") = false`.

**Reasoning.** Apple's total documentation is five words — *"The station associated with the song."* "Associated" could mean the artist's station; the identical relationship name exists on `Artists`.

> ### CORRECTION (revision 2) — my settling probe could not answer its own question
>
> I specified *three songs by three different artists*, with the failure condition *"if the same artist's songs all return one identical id."* **The fixture never places two songs by one artist side by side, so that condition is unobservable in it.** The success condition was not diagnostic either: distinct ids across distinct artists is what the artist-station hypothesis predicts too. Run as specified, it would have returned the right answer for the wrong reason.
>
> Sharpest detail: I named `Artists.station` as *the reason to doubt* and then designed an experiment that never measured it. **Naming a confound and not controlling for it is worse than missing it, because it looks rigorous.**

> ### RESOLVED (revision 3) — SUPPORTED, `VERIFIED · live`
>
> The corrected design was run. **`supports("stationSeedFromTrack")` flips `false` → `true`** — the only value that moves in the matrix.
>
> The decisive evidence is **structural, not correlational**: the station id is `ra.` + the song's own catalog id, for all six songs. Two songs by the same artist return different stations in all three artists tested, and the artist's own station is a different resource under a different naming convention (*"… & Similar Artists Station"*).
>
> **My holding the label at `LIKELY` was correct** and is the one part of this row that needed no correction — the semantics genuinely were unstated, and `supports()` correctly stayed `false` until demonstrated. **My experiment was the part that was wrong.** Judgment sound, instrument faulty.

## D5 — ⚠ WITHDRAWN (revision 3): my correction of 001 §14.3 row 21 was itself wrong

**What I claimed.** 001 §14.3 row 21 says `/v1/catalog/{sf}/songs/{id}/lyrics` *"exists"*. I found it in no Apple documentation and **corrected the premise**, labelling it `VERIFIED`: *"no public lyrics endpoint exists."* I argued that answering only the narrower entitlement question would carry an unverified premise forward as fact.

**What is true.** **The endpoint exists.** `GET /v1/catalog/us/songs/651880159/lyrics` returns `400` with `code: 40012`, `"Insufficient Permissions"`, *"'lyrics' entities require permissions that are not in the request"* — while a nonsense relationship on the same song returns a **different** code, `40008`, *"No relationship found matching…"*. Apple's routing layer recognises `lyrics` as a real entity. `syllable-lyrics` behaves identically.

**001 was right. My correction is withdrawn in full, and the `⚠` placed on 001 §14.3 row 21 on my evidence comes off.**

**Why this entry stays in the log rather than being deleted.** It is the most instructive failure in the slice, and deleting it would hide the mechanism.

**What actually went wrong — precisely.** Not carelessness, and not a missed source. The reviewer independently re-checked four ways and found the same zero hits: 0 across the Apple Music API index (608 nodes), 0 in the Feed index, 0 across all 19 MusicKit-web modules, 1 in Swift MusicKit (`var hasLyrics: Bool`). **Two people read the documentation correctly and both got the wrong answer, because the documentation is incomplete.**

The error was **an inference, not an observation**. My observation — "no lyrics endpoint appears in Apple's documentation" — was and remains true. The step from that to *"no public lyrics endpoint exists"*, at `VERIFIED` strength, is the falsified rule in D1.

**The aggravating detail.** I applied the rule most aggressively exactly where I had least warrant. Rows 10/11/18/7 had a **second leg** — years of Apple staff statements — so their conclusions survive at `LIKELY`. **Row 21 had only the enumeration leg**, and I labelled it `VERIFIED` anyway and made it the headline correction of a primary spec. **The row with the thinnest evidence got the strongest claim**, because absence felt more total there. That is the inversion to watch for.

**What replaces it.** The live finding, in row 21a. `supports("lyrics")` and `supports("lyricsSynced")` **stay `false`** — a capability gated behind an entitlement we do not hold is not a capability (§14.4). S16 and the four→three centre-cycle are **unchanged**. Only the *reason* changes, and it must change everywhere it is recorded, including the matrix comment: from *"no public endpoint"* to *"exists, `40012`, entitlement unresolved"*. See D15.

**21b is unchanged and remains the real blocker** — `UNVERIFIED · docs`. Whether a third party may lawfully *display* Apple Music lyrics is a licensing question no status code resolves.

## D14 — I held a counterexample to my own inference rule and did not recognise it as one

**This is the entry I would most want a future spike to read.**

Revision 1's row 18 sub-finding records that Apple's shipped `musickit.js` contains `splice`, `updateItems`, `removeQueueItems` and a deprecated `remove` — **none of them in the published v3 reference.** I found that myself, before any live probe. I labelled it correctly, kept it out of `supports()`, and was praised for the posture.

**And then I did not generalise it.** I treated it as a local curiosity about one class rather than as evidence about how completely Apple documents anything — while, in the same document, resting four negative findings on the premise that Apple's documentation is complete. **The refutation and the claim sat forty lines apart.**

**Why I think it happened.** The runtime methods arrived as a *risk to be contained* — the question in front of me was "should this flip `supports()` to true?", and the answer was no. Having disposed of it as a risk, I never asked what it implied about my method. **A finding that is correctly handled locally can still be evidence you have not spent.**

**The check that would have caught it:** after each finding, ask not only "what does this change about the product?" but "what does this change about how I am reasoning?" A documented-vs-shipped mismatch is a fact about the documentation, not just about the class.

**Cost.** One wrong headline finding, a wrongly-flagged primary spec, and four labels a grade too high — all recoverable, and all avoidable from evidence already in hand.

## D17 — Promoting the `include`/`views`/`extend` hazard to its own section

**Decision.** The silent-`200` behaviour was a parenthetical inside row 20. It is now its own section, addressed to whoever builds the adapter.

**Reasoning.** It is a **correctness trap with a disguise**: a typo'd `?include=station` returns success and a payload merely missing the relationship, which reads as *"this song has no station"* — a plausible data condition. On row 20 specifically, that would silently disable the one capability this spike just confirmed, and it would look like Apple's fault. **The rule stated for the adapter:** assert the relationship is **present in the payload**; never infer it from the status code. Prefer the strict path form `GET …/songs/{id}/station` over `?include=station` where correctness matters more than round-trips.

## D19 — ⚠ `displacedCount`: I picked a reading of an undefined term without noticing there was a choice

**The claim, as I made it.** Revision 2 stated flatly and **without any label** that `pod-queue-insert`'s `displacedCount` "can only ever be 0" on Apple, so the `REVIEW if displacedCount > 3` escalation is dead code on the launch provider. The lead recorded it as settled in D-027.

**The problem.** **`displacedCount` is undefined in 001.** Two occurrences, both `pm-spec.md:774` — the return shape and the gate — and neither defines the term. I read it as *items removed or overwritten* and never registered that I had chosen.

| Reading | Consequence on Apple |
|---|---|
| **(a)** items **removed or overwritten** *(mine)* | always 0 → the `> 3` trigger **never fires** |
| **(b)** items **pushed to a later index** | `playNext` of 4 into 20 → 19 → the trigger **fires constantly** |

**Opposite consequences, and (b) has the better textual support.** The same cell justifies its sibling threshold with *"a 60-track insert **is** a queue rewrite even when it is **technically additive**"* — 001 reasoning explicitly about the harm of *additive* operations, which is displacement-by-shifting, not destruction. Under my reading the gate is dead on Spotify too, so 001 would have specified a REVIEW trigger that can never fire on either provider. Possible; improbable.

**Three things make this worse than its size.**

1. **It is an agent-safety control**, not a UI detail, and it is **wrong in the dangerous direction.** My reading retires half the staged-REVIEW net for agent queue inserts on the launch provider, leaving the `> 10` item count carrying the whole load — an agent could `playNext` ten tracks, displace an entire queue, and cross no gate.
2. **It was the last claim in the document still resting on the falsified inference rule.** "MusicKit documents no insert-at-arbitrary-index" is exactly the inference revision 3 declares unsound in its own opening section — and the counterexample, `splice(start, deleteCount, items = [])`, is **in this document's own row 18 sub-finding, forty lines above.** After writing D14 about failing to spend that counterexample, I swept the document and **missed the one place it still applied.** Naming a bias does not clear it; you have to go and look.
3. **It was owed the treatment I gave two other rows and withheld here.** `offline` (D7) and `ratingStars` (D10) both got *"an observation, not a decision I was entitled to make — escalated, unresolved."* An undefined term in a primary spec is the same category. I flagged the two that were about *capabilities* and asserted the one that was about *semantics*, which is a distinction with no principle behind it.

**Decision.** Label it **`UNVERIFIED · docs`**, state both readings and their opposite consequences in the deliverable, and **escalate the definition to the lead as a 001 ambiguity. Do not pick a reading.** Whoever builds the WebMCP surface must resolve the term before relying on either trigger, and must not cite this document as grounds for relaxing the `> 3` gate.

**Also relabelled while I was there:** the `position: "index"` narrowing in the same cell rests on the same weakened leg and is now **`LIKELY · docs`** rather than asserted — the undocumented `splice` is literally an insert at an arbitrary index.

## D23 — Adopting the structural-vs-testimonial distinction, and why "per the lead's ruling" was not a reason

**The finding, which was against the lead rather than against me, and which I should have raised myself.** Rows 10/11/18/7 and row 30 all lost the same enumeration leg and all have a surviving affirmative leg — yet they land on different grades. Revision 3 justified that with *"per the lead's ruling."* **That is a citation, not a reason.** D16 recorded my discomfort honestly and then discharged it by deferring, which left the document unable to answer the obvious question: why does one falsified-leg row keep `VERIFIED` when four others do not?

**The principle, now D-045 and standing law.** The surviving legs are not the same *kind* of evidence:

- **Testimonial** (rows 10/11/18/7) — Apple staff stating what the API does. **Ages silently.** A 2020 forum reply sits unchanged on the page the day Apple ships the endpoint, and nothing about the artifact signals that it has stopped being true.
- **Structural** (row 30) — offline audio is EME/Widevine-gated; offline would need a `persistent-license` session Apple's licence server does not issue. **Cannot go stale invisibly**, because a mechanism cannot change without the mechanism changing, and a change of that size could not happen quietly.

**A statement about a system ages; a property of the system does not.** That is the whole distinction, and it is a better rule than the one I was applying — which was really "how confident do I feel about this row."

**Recorded because the failure shape is one I have now hit twice in this slice.** In D19 I picked a reading of `displacedCount` without noticing there was a choice. Here I accepted a label split without noticing there was a principle — and, worse, I had *already noticed the inconsistency* (D16 says so in as many words) and then filed it under deference instead of chasing it. **Flagging a tension and then treating the flag as the resolution is a way of not doing the work while appearing to.** The right move was to ask what property of row 30's evidence differed, which took one paragraph once someone finally asked.

**No labels moved.** Only the reason did — which, per D15, is the part that survives into `packages/providers` and gets read in a year.

## Closing note — what four revisions cost and what they bought

Revision 1 was wrong about the lyrics endpoint, about `§5.1 row 10`, about `Remove from Playlist`, and about four confidence labels. Revisions 2 and 3 were each forced by findings that overturned the one before. **Every one of those errors was `docs`-provenance, and every one was corrected by `live` or by a grep.**

The reviewer's closing line is the honest summary, and it belongs in this log rather than only in the review: ***"the gap between 'I re-fetched every source and they agree' and 'I asked the API' was the whole distance between right and wrong here."*** Three GETs closed it.

The method was sound and applied carefully by two agents who checked each other, and it still produced a confident wrong answer, because both were reading the same incomplete surface. **That is not an argument against rigour on the `docs` axis; it is the argument for never letting it masquerade as the `live` axis.** D-022's provenance axis is what made every one of these corrections legible instead of embarrassing, and D-038 is what makes the underlying habit — spending a finding locally and never asking what it implies about your reasoning — something the next slice can be checked against rather than something each agent has to rediscover.
