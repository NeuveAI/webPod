## Identity and credentials

Apple Music authorization is not Sign in with Apple account identity. The existing Apple provider passes `authorize()`'s returned string into the public `Session.userIdentifier` (`apple-provider.ts`, `sessionOf` and `authorize`). Treat that string as sensitive authorization material, remove it from public Session, and expose no token through Jotai, diagnostics, WebMCP, URLs, or logs. Apple's [MusicKit authentication documentation](https://developer.apple.com/documentation/applemusicapi/user-authentication-for-musickit) describes the Music User Token as authorization for personalized requests; [MusicKit's instance documentation](https://js-cdn.music.apple.com/musickit/v3/docs/iframe.html?path=%2Fstory%2Freference-javascript-musickit-instance--page) describes the authorization flow and persisted SDK authorization.

Recommended initial product contract: a **browser-bound webPod collection**, not a globally identified Apple account. Generate an unguessable server-side account id and a separate random opaque session secret. Persist only a hash of the session secret, expiry and revocation server-side; issue HttpOnly, SameSite=Lax, path=/ cookies, Secure on HTTPS. Never accept userId/accountId in a mutation as authorization. Require same-origin POST, JSON content type and bounded body sizes, including session bootstrap.

Bootstrap collection ownership only after the server verifies current MusicKit authorization against an Apple personalized endpoint. Transfer the token directly to the server in a dedicated POST from a private provider callback/method; keep it out of public session state. Prefer not storing the token: perform bounded import with that request's token and refresh authorization for subsequent sync. If jobs must survive process restart with autonomous Apple calls, encrypted token persistence requires a separate runtime encryption key and explicit key rotation lifecycle; avoid silently inventing this subsystem for the first slice.

On page reload use the HttpOnly collection session and restored MusicKit authorization to resume the same browser collection. Rotate the collection session on a fresh authorization; never recreate a starter grant when merely refreshing. On MusicKit sign-out/expiry cancel client import/listening subscriptions, clear private token memory and collection UI, revoke active collection session, and retain server records according to the stated persistence policy. Reauthentication needs a browser-only recovery credential or a retained restricted continuation cookie if sign-out is expected to preserve ownership. That credential must not authorize collection reads/writes while signed out; re-enable only after fresh Apple verification. **No scheme here proves that the reauthorized Apple account is the same person:** clearly document browser collection semantics and do not claim cross-device restore/account matching. Hashing the Music User Token is not a durable Apple ID and will break on token rotation. Cross-device ownership requires a separate real account login.

## Ingestion, enrichment, accounting, distribution

Suggested ownership boundaries:

1. `packages/server-core/src/stickers/{schema,database,repository}.ts`: users/sessions; import batches; normalized track metadata; observed listening events; per-genre credit; grants/inventory; placements. Unique `(owner,eventId)` and `(owner,grantKey)` indexes; foreign keys; all writes ownership-scoped. Store stable provider catalogue IDs and storefront, not provider runtime LocalKey. Library-only IDs remain owner-scoped and explicitly unresolved.
2. `.../{apple-import,enrichment}.ts`: fetch Apple library/recent resources with fixed HTTPS host and constrained known endpoint paths; do not blindly fetch client/upstream next URLs. Bounded page size, overall resource/page/time ceilings, deduplication, resumable progress, typed partial/error state and rate-limit backoff. Preserve provenance (`library`, `recent`, `observed`), observedAt and schema/version. Library/recent membership contributes taste only, **zero inferred listening milliseconds**. Resolve catalogue metadata for genre classification server-side; no client-declared genre or duration grants. Stable explicit mapping to the twelve manifest genres; unknown remains unknown. Use primary supported genre deterministically to avoid multiplying one listen across genres.
3. `.../{listening,policy,distribution}.ts`: receive sequential observations, not arbitrary claimed lifetime totals. Mint server listening stream ID; sequence + event ID replay protection; validate track identity, playing state, monotonic progress, client elapsed bounded by server elapsed, duration and maximum heartbeat gap. Credit the smaller plausible elapsed/playhead delta; pauses, seeks, stalled progress and stale gaps give zero or capped credit. Multiple tabs must not multiply wall-clock credit. This remains client-observed telemetry, not fraud-proof Apple history. Persist event and derived credit/grant atomically so retries cannot duplicate earned inventory.
4. `apps/web/src/sticker-runtime.ts`: subscribe to existing provider `onPlaybackChange`, `onProgress`, and session lifecycle; batch heartbeats (e.g. 10 seconds) with pause/track-change flush; generation guards for logout; bounded pending queue; retry identical event IDs. Existing runtime progressively hydrates library after both `selectMusicRuntime` restoration and `authorizeAppleRuntime`; trigger sticker bootstrap there without delaying successful music playback.
5. `apps/web/src/routes/api.stickers.*.ts`: thin Start endpoints for bootstrap/sync/status, observations, inventory/pack opening, placement, and session end. Responses no-store; errors omit raw upstream bodies/credentials. `packages/state` owns externally readable inventory/placement state; pure public contract/catalogue belongs in a client-safe package/module independent from server-core.

Owner approved a genre starter pack plus measured-listening progression. Provisional named/versioned policy recommendation: starter is **one pack from the strongest supported genre** in the bounded imported library, initially containing its first catalogue sticker; if no classified taste exists, show pending/choose-genre rather than pretending a taste result. Count distinct catalogue tracks, stable tie-break by manifest genre order. Grant exactly once per browser collection (`starter:v1`), after completed taste import or clearly labelled bounded snapshot. Subsequent stickers within each genre unlock at cumulative **15, 60, 180 and 600 verified-observation minutes** (five per genre including starter-tier first sticker). For a genre absent from the starter, its first sticker unlocks at **5 minutes**, then the same subsequent thresholds. Constants should remain editable server policy, included with progress in responses; never derive thresholds from artwork captions. Use deterministic next-unowned sticker ordering and transactional unique grant keys. Replays of a genuinely listened track can count; replaying HTTP requests cannot. Pack opening must be idempotent and should change reveal state, not reroll contents. Thresholds are provisional implementation choices, not historical owner-approved figures.

Placements accept only owned sticker IDs, known surface, finite bounded coordinates/scale/rotation and a capped total. Server validates domain constraints; the renderer owns the exact physical shell projection. Persist placement revision for stale-write conflict detection. Inventory is the authority for client equip actions.
