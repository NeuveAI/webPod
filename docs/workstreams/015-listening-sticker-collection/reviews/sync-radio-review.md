The original unfiltered `/v1/catalog/{storefront}/stations` request violates Apple's documented request shape. [Live radio discovery](https://developer.apple.com/documentation/applemusicapi/get-the-apple-music-live-radio-stations) requires `filter[featured]=apple-music-live-radio`; [multiple station lookup](https://developer.apple.com/documentation/applemusicapi/get-multiple-catalog-stations) requires `ids`. The changed provider supplies the documented discovery filter through current MusicKit and the existing legacy facade, preserving normalization, optional-library behavior and station transport. No unfiltered fallback was added.

## Sync and cancellation evidence to resolve

- Apple's [all-library-songs contract](https://developer.apple.com/documentation/applemusicapi/get-all-library-songs) defines `offset` as a string. The original importer rejects all nonnumeric offsets. A bounded opaque cursor must remain confined to the fixed Apple origin and songs pathname with allowed query keys. Apple's example inconsistently names an albums continuation; this is not authorization to fetch unrelated paths.
- Existing `partial` means only the declared 25-page/2,500-track cap. A retry starts from the same bounded prefix, so this is distinct from recoverable failure. The displayed banner merges `partial` and `failed`; the owner's screenshot alone establishes neither a particular upstream failure nor a shared cause with radio/cancellation. Explicit failure diagnostics must remain bounded and exclude Apple payloads and tokens.
- The existing five-second bootstrap cooldown returns an active inventory unchanged. This must not turn a failed-sync retry into apparent successful recovery. Failed and capped import behavior require distinct, honest user status and tested retry semantics.
- Installed srvx 0.11.22 `dist/adapters/node.mjs` binds its request signal to a premature response close and exposes POST bodies through `Readable.toWeb`. Installed Start server core 1.169.31 `createStartHandler.ts:779` checks `request.signal.throwIfAborted()` after handler/middleware work. `request-response.ts:121-141` wraps the result in H3 `toResponse`. Installed H3 2.0.1-rc.20 `dist/h3-Bz4OPZv_.mjs:216-227` classifies unknown errors as unhandled and logs them before an outer server-entry wrapper can observe the response. Therefore an outer catch alone cannot suppress this logged cancellation path. This tracing is separate from reproducing the user's exact failure.
- The installed Start plugin 1.171.39 dev adapter directly constructs srvx `NodeRequest` and calls the server entry. Actual shipped development POST and disconnect tests are required; prior anonymous GET and alternate built-server tests did not exercise this seam.
