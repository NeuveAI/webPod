# Remaining sticker CPU work after PR4

Read-only source audit on `codex/device-cpu-profile`,2026-09-11. Prior responsiveness and rotation reports describe earlier experiments; their timings are not measurements of this build. Lead owns the new6× Chrome capture. No application changes, browser instrumentation, tests, builds or commits in this lane.

## First profile target: unchanged wear surface becomes a new resource every carry frame

For an existing placed sticker, `sticker-carry-worker.ts:24` caches the source geometry and :25 caches the target. Nevertheless :27–30 copies/transfers that same source/target as `wearGeometry` on **every** pose result. `sticker-carry-preparation.ts:75` restores a new BufferGeometry for each result, then PeelingPrint passes it into StickerPrint. `StickerSurface.tsx:77` runs a layout effect keyed by wearGeometry and calls `prepareStickerSurfaceDamage`.

`sticker-alpha.ts:115` caches surface damage by **geometry identity** and texture. A newly restored unchanged wear surface therefore misses. It copies base onset, iterates boundary candidates (:93–112), allocates a second Uint8Array, vertically copies every mask row and creates a fresh DataTexture (:120–126), which is uploaded on rendering. Base fields are capped to1024 on their longest side (:34), so the structural upper bound is up to1,048,576 bytes for each of those byte buffers; actual artwork dimensions determine real work. It runs even at wear0. Old resources are disposed, so this is repeated allocation/upload churn rather than an established leak.

This is a concrete duplicate-work path supported by code, **not yet a measured bottleneck**. It is most relevant to peeling an already placed sticker and landing on a target. A collection sticker with neither source nor landing target has no wearGeometry and follows the base resource path instead. Compare those gestures in the capture.

Profile stacks to confirm: worker message → `restorePaperGeometry` → React commit/layout effects → `prepareStickerSurfaceDamage` / `createSurfaceStickerDamage` → Uint8Array copies/DataTexture → WebGL texture upload. The replacement damage field identity can also defeat `stickerAlphaContours`' field-keyed cache when the editor contour is shown, multiplying this work.

Specific next boundary if confirmed: publish stable source/target wear resources once per source/target revision, with subsequent pose messages carrying a revision/reference. Retain/dispose them independently of transient shown geometry; preserve epoch/assembly invalidation, texture identity, and worn hit/contour parity. This removes redundant copies, CPU damage work and GPU texture churn without reducing quality. Alternatively compute the immutable damage resource once alongside source geometry. Do not cache merely by artwork ID because placement normals affect damage.

## Scene preparation still repeats before worker dispatch

`PeelingPrint` serializes its complete art/pack input at `StickerPackScene.tsx:415`. Its layout effect calls `content.updateWorldMatrix(true,true)` (:421), then `collision.update(content)` (:422). `sticker-visibility.ts:31` performs **another** `content.updateWorldMatrix(true,true)` in inspect, traverses the entire content scene, checks ancestor visibility, builds an array of meshes and compares every local-transform/geometry/material signature. The numeric signature avoids rebuilding an unchanged BVH, but the traversal/signature work still happens on each requested pose. A changed assembly calls prepare, which inspects again (:73/98); prepared-result validation also inspects once more.

This establishes a duplicate recursive update per dispatched pose, even when the expensive geometry calculation runs in a worker. Count `updateWorldMatrix`, `inspect`, `traverse` and matrix multiplication stacks in the trace. A shared per-commit assembly observation or explicit assembly revision could remove duplicate work, but it must catch physics control transforms, material/visibility changes, geometry replacement and local ancestors. Device world rotation alone must not invalidate local collision topology.

Return-to-sheet additionally computes `new Box3().setFromObject(workspace)` at `StickerPackScene.tsx:427`. GPU paper intentionally invalidates its boundingBox on curl changes (:356); inspect whether Box3 work scans attributes or uses supplied object bounds in the installed Three path. Do not assume that a GPU shader eliminated CPU bounds queries.

The input pick wrapper also reads canvas bounds at :178 and the uncached implementation reads them again at :144. Same-task caching still updates matrices/reads bounds/builds a key before checking the cache, and expires at the next microtask (`sticker-pick-cache.ts`). It does not merge queries from separate DOM callback microtask checkpoints. These are smaller concrete batching opportunities, subordinate to measured hit/geometry work.

## Worker output still causes CPU and GPU work

Carry uses one active+one latest pending job and publishes monotonic completed poses within an epoch. Each accepted result creates fresh BufferGeometry/BufferAttribute wrappers, React updates, GPU buffer creation/upload and retirement of the prior geometry. Worker transfer avoids a main-thread geometry calculation but does not eliminate allocation or rendering submission. Inspect `restorePaperGeometry`, `WebGLAttributes.createBuffer`/`bufferData`, geometry disposal and React commit stacks alongside worker timings. Stable-topology displayed buffers could potentially be reused with in-place attribute updates, but epoch correctness, old-frame lifetime and buffer ownership require explicit design.

Cold collision preparation also still copies collision inputs on main (`sticker-collision-preparation.ts:12`) and restores the returned BVH on main (`sticker-visibility.ts:86`). Normal unchanged assembly does not repeatedly build that BVH. A15s worker failure switches to cooperative CPU computation; generator checkpoints do not preempt native allocations/normals/bounds. Verify worker success/failure and whether captured samples belong to main or worker threads before calling this a regression.

This moves collision handoff ahead of the unmeasured steady-carry wear hypothesis above for **first move**.

The exact source chain is `createCarryPreparation.dispatch` → worker initialization (`sticker-carry-preparation.ts:81`) → `visibility.snapshot()` (`sticker-visibility.ts:69`) → `collider.snapshot()` (`sticker-collision.ts:146`) → `serializeNode` (:28). Every node constructs a new object, a fresh six-number bounds array assembled from two temporary Vector3.toArray arrays, and recursively allocates children. Prepared collision already arrived from its worker as a serialized tree. Main thread restores it into Box3 nodes (:32/110), then immediately serializes the entire tree again at first carry handoff. The comment that context is sent once per assembly does not prevent this cold synchronous roundtrip.

Important frequency correction: normal pose dispatch **does not** serialize collision on every request. Context lives inside `if (!worker)`. Serialization happens on first worker creation and after assembly/visibility revision changes, hidden/resume or remount recreate that worker. The worker-failed cooperative path calls `contact.snapshot()` on each job (:43), so that path currently repeats it more often. `request` compares rear identity, visibility identity and visibility.revision (:92) before restarting; trace repeated stalls should be checked for those changes or worker failure rather than attributed to every normal pose.

### Minimal ownership-safe change to prepare

Cache the serialized root **inside each immutable collider instance**, initialized from `prepared.root` when restoring a worker snapshot. `snapshot()` should still call `ensure()` so disposed colliders throw, then return the already prepared serialized root. A collider built synchronously without a prepared snapshot can serialize lazily once and cache that root; its worker-only initial snapshot is then computed off main as before. Coordinates, provenance and metadata already belong to that collider instance. No public signature or per-request version protocol needs to change.

Collision contents do not mutate in-place; assembly change constructs a new collider in visibility.prepare/update, increments revision and disposes the old one. Thus collider identity is the cache version. Dispose must clear the cached root reference as well as live root/arrays so no second tree is retained after disposal. Prefer reusing `prepared.root` over serializing the restored Box3 tree even once—the serialized representation already exists at the worker boundary. This may retain two tree representations while the collider is live; that bounded memory tradeoff should be measured using actual node count, not estimated JS object sizes.

Snapshots remain **borrowed immutable** unless the sender relinquishes the collider. Carry must continue structured-cloning its context (no transfer of live visibility arrays). Cooperative temporary colliders must continue cloning metadata before disposal; the previous metadata-ownership fix remains necessary. Never cache globally by geometry alone or overwrite a shared snapshot with transferred/detached arrays. A visibility-layer equivalent could retain the original preparation result per revision, but core collider caching is smaller and also fixes repeated cooperative snapshot requests.

Verification boundary: restore a prepared collider and prove repeated snapshots reuse the original serialized root without `serializeNode`; prove identical contact/query output, disposal rejection, replacement revision isolation, old worker rejection and metadata ownership. Re-profile first keyboard move with the same6× settings. This removes the demonstrated recursive allocation path; it does **not** prove the whole529.497ms dispatch self cost is gone. `postMessage` still structured-clones the nested tree and arrays, `transferPaperGeometry(rear)` still copies rear attributes, and receiving workers still restore their own runtime BVH. Attribute-copy/native structured-clone costs need separate attribution after the minimal fix.

If clone cost remains substantial, the next boundary is a flat immutable BVH representation with numeric node bounds/child/leaf arrays and explicit owned transfer copies, or a direct preparation-worker→carry-worker handoff. Both are larger changes requiring exact query/provenance parity and lifecycle ownership; they should not be bundled into the minimal serialization-cache fix without evidence.
