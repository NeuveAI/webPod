FINDING 1 — the WebGL entry point that shipped is texElementImage2D, 3-arg
-------------------------------------------------------------------------
  texElementSubImage2D   ABSENT   (this is the name in the current README IDL)
  texElementImage2D      PRESENT, arity 3

Arity 3 is three.js's `// Chrome 150+` branch
(three.js src/renderers/webgl/WebGLTextures.js:1298). Chrome here is 151, which
matches. So three.js HTMLTexture works against this browser unmodified, and the
"which signature" half of RISK-02 is answered: the new one.

RISK-02 as written in decision-log.md describes the churn as
`texElementImage2D` <-> `texElementSubImage2D`. That is the NAME axis and it is
real, but the try/catch in the spec repo's own Examples/webGL.html:59-72 spans
two SIGNATURES of the same name `texElementImage2D`, not two names. Both axes
exist; the evidence cited for RISK-02 is evidence for the second one.


FINDING 2 — BLOCKING for W6 — updateElementGeometry does not exist
-----------------------------------------------------------------
The W6 dispatch packet, under "The property that must not be lost":

    "So: updateElementGeometry({ canvasTransform }) is mandatory, must be
     recomputed every time the device moves, and is what makes the composited
     panel screen-reader-navigable. Skipping it yields a panel with content
     and no positions. That is not a cosmetic gap — it is the difference
     between the thesis holding and not."

updateElementGeometry is NOT IMPLEMENTED in Chrome 151. Neither is
clearElementGeometry, getCanvasTransform, onelementgeometryupdate, or
ElementGeometryUpdateEvent. They exist only in the explainer.

What ships instead is the previous generation of the same idea:

    canvas.getElementTransform(element, screenSpaceTransform) -> DOMMatrix
    // then: element.style.transform = returned.toString()

The element becomes genuinely CSS-transformed DOM, so hit-testing, focus,
selection and accessibility geometry are native and come from the transform —
the same outcome the packet wants, reached by a different mechanism. This is
also exactly what three.js examples/jsm/interaction/InteractionManager.js
already does: it computes the MVP itself and writes matrix3d to
element.style.transform. It never calls updateElementGeometry.

So W6.2 is buildable, but the packet's mandated call does not exist and W6.2
must be specified against getElementTransform. Raised to the lead, not patched.
